## 需要处理

### P1：新试片排在整片前时，顶部、侧栏和修改入口对“最新”的判断不一致

- 位置：`frontend/src/views/Workbench.tsx` 中 `stageLead` / `deliverableLead`（约 704–724 行）、`isHistoricalVersion`（约 1254 行）、`submitRealModify`（约 2201、2234 行）和 `RightPanel` 历史提示（约 4665 行）。
- 场景：最新场景整片为 v4；后生成编辑器试片、其导出次数为 v2，试片按时间排到 `stage.visuals[0]`。顶部使用 `deliverableLead`，能显示最新整片 v4，但工作台历史判断和修改前置校验仍使用 `stageLead`（试片 v2）。切到场景 v4 时，界面可能把它错误称为“历史 v4，最新 v2”；提交帧或时间段修改会因 `viewedPreview.id !== stageLead.id` 被拒绝，尽管 v4 是当前场景。
- 处理方向：分别表达当前工程版本、最新可交付整片、当前预览及编辑器试片，只有同一来源的版本才能比较。能力提示、侧栏、恢复入口与提交校验使用各自正确基准；提交仍须以服务端当前场景及原子版本校验为准，不要简单把所有 `stageLead` 机械替换成 `deliverableLead`。
- 回归：场景 v4 + 较新试片 v2；查看场景 v4、旧场景 v3、编辑器试片三个状态，核对顶部、侧栏、AI 目标能力、提交与恢复入口；增加场景版本不存在或整片落后于当前工程的情况。

### P1：顶部仍跨来源比较不同版本号

- 位置：`frontend/src/views/WorkbenchTopBar.tsx` 约 180–187、190–192 行。
- 顶部历史状态直接比较任意 `viewedPreview.revision` 与整片 `revision`，未判断来源。编辑器试片的第 2 次导出、工作流修订号和项目场景 v4 并非同一版本序列；因此试片可能被标为“历史”，或缺少合理的回到整片入口。`deliverableLead` 本身允许 workflow 与 scene 的 final 共同按时间选择，也不能直接证明其 `revision` 是当前项目场景版本。
- 处理方向：展示画面来源和对应编号；仅对可确认同一场景版本序列的项目版本标记“历史/最新”，对试片与工作流产物使用其自己的身份，不把它们的 revision 当场景版本。需要区分“最新可下载整片”与“当前工程版本”。

### P2：`已下载`并非已确认保存成功

- 位置：`frontend/src/views/Workbench.tsx` 约 2913–2936 行。
- `fetch` 成功和非空 blob 只能证明前端取到字节；随后 `a.click()` 无法确认用户接受保存、目标路径可写、下载未被取消或文件已落盘。当前立即显示“已下载 vN”会误报；非空 HTML 错误页也可能被当视频保存。
- 处理方向：如无可观测下载完成事件，文案改为“已获取 vN，已发起下载”，真实完成/取消仅在原生下载接口能返回结果时报告；按后端契约判断返回内容，避免将错误页面当成视频。大文件 blob 全量占内存的影响留作后续性能评估。
