# 参考片「选定片段多帧分析」设计与实测记录

> 基线 `605fb76 / 9e1fa2b`（分支 `feat/three-libraries`）。
>
> 本文分成两类内容，严格区分：
> **「已实测」只写我真实跑出来并看到输出的**；**「设计」是尚未实现的主张**。
> 不要把本文当成"已经做完"的证明。

## 0. 结论先行

1. **DSH 图片通道可用，且模型确实在读图**。单图能准确读出画面物体与字幕原文。
2. **但输出形态极不稳定，这是第一版最大的技术风险**：
   - 单图 + 「单行 JSON」→ 稳定成功（2/2）。
   - 多图 + 「单行 JSON」→ **3 次全部失败**，模型无视格式要求，改回编号自然语言，且只答第一问。
   - 多图 + 「三行回答」→ 同上，只答第一问。
3. 因此**不能**设计成"直接让模型输出结构化参考卡"。第一版必须假定模型会返回**自由文本**，由后端做宽松解析，解析不出的字段保持 `pending`。
4. `Observation` 目前是裸 `String`，**无法**承载"这条观察是模型说的还是用户说的"。这是必须改的数据结构，否则第 4 步的"人工修改不能被覆盖"无从实现。

## 1. 实测记录（真实命令与真实输出）

### 1.1 环境

| 项 | 值 |
|---|---|
| DSH 通道 | `DshSdkSession.prompt(sessionId, text, List<InlineImage>, listener, timeout)` |
| provider / model | `agent2api-ecs` / `deepseek-v4.1-flash`（`application.yml` 默认值） |
| 模型声明能力 | `input: [text, image]`（`cordis.patch.yml`），**未声明视频或音频** |
| ffmpeg | 系统 `/usr/bin/ffmpeg` n9.0.2；随包 `desktop/electron/resources/ffmpeg/ffmpeg` 同为 n9.0.2，可直接执行 |
| 抽帧 | `ffmpeg -ss <t> -i <video> -frames:v 1 -vf scale=640:-1 out.jpg` |
| 样本 | `morning-poem-30s.mp4`（1920×1080 / 30fps / 30s）、`fengmotion-brand45.mp4`（1920×1080 / 60fps / 45s） |

### 1.2 单图：模型确实读到了画面

一次真实调用（`ffmpeg -ss 29` 抽出的帧）：

```
prompt: 这是一张视频截图。请回答：1) 画面中间偏下有什么物体？2) 底部字幕的文字原样抄下来。
输出:   1) 画面中间偏下是一个白色茶杯，带碟子，杯中装着深色液体，像是咖啡或茶。
```

字幕那一问没在正文里出现（被截断）。但物体识别正确 —— 该帧画面确实是窗台上的一只咖啡杯。

### 1.3 单图 + 单行 JSON：稳定成功

```
prompt: 只输出一行 JSON，不要任何解释、不要代码块：
        {"object":"画面里的物体","subtitle":"底部字幕原文，看不清就填 空字符串"}
输出:   {"object":"窗边桌子上的一杯咖啡","subtitle":"他把第一杯放在窗边，像每天一样，没有说话。"}
```

**字幕原文与人眼核对完全一致**（我另行查看了该帧图像）。这一条同时证明两件事：
模型真的在看图；**单行 JSON 约束是有效的**。

### 1.4 多图：能理解，但拒绝结构化输出

样本：同一视频 1s（空房间）与 29s（有咖啡杯）两帧，差异显著。

| 尝试 | prompt 要求 | 实际输出 | 结果 |
|---|---|---|---|
| 1 | 三行回答（物体变化 / 字幕 / 背景位置） | `好的，我会对比这三帧画面，然后按三行回答。` | ✗ 空壳 |
| 2 | 两张图 + 单行 JSON | `1) 多了一杯放在碟子上的咖啡，位于窗前的桌面上…` | ✗ 无视格式 |
| 3 | 同上，重跑 | `1) 画面中多了一只盛着咖啡的白色杯子（连杯托）。` | ✗ 只答第一问 |
| 4 | 同上，再重跑 | `1) 多了一个白色的咖啡杯…第一张左上角的窗帘或百叶窗在第二张里不见了` | ✗ 只答第一问 |

注意第 2、4 次的输出**在内容上是正确的** —— 它确实识别出"多了咖啡杯"、"少了一扇窗"。
**失败的是格式与完整性，不是视觉理解。**

### 1.5 一个易误判的坑（留作教训）

首次探针打印 `Outcome.text()` 得到空串，我一度以为"多图没有正文"。真实原因是我在监听器里
打印的 `onAssistantMessage` 参数，而 `Outcome.text` 在另一处被赋值 —— 探针自身写法有误。
**探针空结果先怀疑探针。** 后改为在监听器里累计 `onTextDelta` 并同时打印 `Outcome.text` 才看清真相。

## 2. 关键推论

### 2.1 输出协议：以"自由文本 + 宽松解析"为第一版，不赌结构化

多图场景下结构化输出遵从率实测为 **0/3**。因此：

- 不允许让"模型返回合法 JSON"成为分析成功的前提。
- 后端提示词仍要求 JSON（单图有效、多图也许将来更稳），但**解析失败不报错、不回滚**：
  转成"整段模型原文"存入参考卡的 `rawModelText`，可用字段照常为空（`pending`）。
- 界面显示"模型已回应，但未能结构化，以下是原文"，而不是"分析失败"或编造的卡片。

### 2.2 多图上限与降级

既然多图时模型会"只回答第一问"，第一版**不依赖"一次给出全部结论"**。可选路线：

- **路线 A（推荐先做）**：单次请求只问**一个问题**，用同一组帧，多次调用拼成参考卡。
  单图 + 单问已被证明稳定。
- **路线 B**：一次多图 + 自由文本，接受"只有部分结论"，其余 `pending`。

路线 A 的代价是请求次数 ×N（每次约 8–14 秒），收益是每项结论都可独立验证。
第一版按 A 实现，把 B 作为"减少请求"的优化项后置。

### 2.3 帧数与尺寸

- 默认抽 **3 帧**（起点、中点、终点；`durationMs < 600` 时只抽 2 帧）。
- 宽度固定 640，JPEG 质量默认。实测单帧 ~9–17 KB，base64 后仍在合理范围。
- **记录实际用了哪些帧**（时间码 + 文件哈希），写进参考卡证据，不只写"抽了帧"。

### 2.4 明确的能力边界（必须写进界面与文档）

抽帧分析**不等于**看视频。以下内容第一版无法得到，且不允许模型猜：

- 精确速度曲线、缓动函数
- 遮罩/转场的中间态（3 帧之间发生的事）
- 音频内容、音乐节拍、人声
- 快速运动的连续轨迹

界面必须标注：**「基于抽帧分析，运动细节待核实」**。

## 3. 数据结构改动（必须先做，否则问题 4 无解）

### 3.1 现状问题

```java
String observation   // 裸字符串，无来源、无时间、无版本
String inference     // 同上
```

`AnalysisValue` 有 `source`，但 `observation` 没有。于是：

- 模型写的观察与用户写的观察**在数据上不可区分**，界面只能靠"谁最后写的"来猜。
- 重新分析时，无论是覆盖还是保留，都是错的：覆盖会丢掉用户修改，保留会让旧模型结论冒充新结论。

### 3.2 改法：把 `observation` 变成带来源与历史的列表

```java
record ObservationEntry(
    String id,
    String text,
    ReferenceStates.AnalysisSource source,  // model | user
    String evidence,                         // 帧时间码等；用户手写可为空
    Instant createdAt,
    boolean superseded                       // 被用户改写后置 true，不删除
)
```

- `observation` 字段对外仍返回**当前生效的那条**（保持前端兼容），另外新增 `observationHistory`。
- **用户修改不覆盖模型条目**，而是新增一条 `source=user` 并把模型条目标 `superseded=true`。
  这样"模型当初说了什么"永远可追溯。
- 重新分析产生的新模型结论**不删除任何用户条目**；若用户已手工写过观察，
  新结论进入历史并标记为"较新但与用户条目冲突"，由用户决定是否采纳。

### 3.3 并发与覆盖

- `reference_segments` 加 `revision INTEGER NOT NULL DEFAULT 0`，每次写入 +1。
- 分析请求携带 `expectedRevision`；完成时若当前 revision ≠ 期望值（用户中途改了范围或观察），
  **不写入**，把结果标记为"已过期"，返回给用户而不是静默落地。
- 同一片段重复发起分析：已有 `running` 任务时返回该任务，不并行起第二个。

## 4. 任务归属：参考片是工作区资源，现有任务系统绑定项目

### 4.1 实测确认的问题

- `tasks.project_id TEXT NOT NULL` + `FOREIGN KEY (project_id) REFERENCES projects(id)`。
- `TaskService.submit` 首先 `projects.findById(projectId)`，不存在直接 404。

所以**不能靠"传一个假 projectId"绕过**：外键会拒绝，伪造项目更不可接受
（会在项目列表里出现幽灵项目）。这必须改表，不是改校验。

### 4.2 方案：任务表增加"作用域"，项目级与工作区级并存

```sql
-- 新增
workspace_scope INTEGER NOT NULL DEFAULT 0;   -- 1 = 工作区级任务，不属于任何项目
-- 修改
project_id TEXT;                              -- 允许 NULL（工作区级任务）
-- 外键改为：project_id IS NULL OR EXISTS(projects.id)
```

约束用触发器或应用层校验实现（SQLite 对可空外键 + 条件约束支持有限，
应用层 `TaskService` 里统一校验更可控）。

- `kind=analyze` + `workspaceScope=true` 才能出现在工作区级。
- 端点：`POST /api/workspace-tasks`（新），`GET /api/workspace-tasks/{taskId}` 复用现有查询。
- **不新建"参考片专用任务系统"**：任务的事件流、取消、恢复、历史查询全部复用，
  否则会出现两套任务语义。

### 4.3 与分析端点的关系

现有 `POST /api/reference-videos/{videoId}/analyze` 返回 422，应改为：

- 请求体：`{ "segmentId": "...", "expectedRevision": 3, "frames": 3 }`
- 返回：`202` + `TaskAcceptedResponse`（`taskId`、`kind=analyze`、`workspaceScope=true`）
- 能力不可用（无 ffmpeg / 模型不支持图片 / harness 关闭）→ 仍然 `422 capability_unavailable`，
  `details.capability` 明确是 `referenceAnalysis.ffmpeg` 还是 `referenceAnalysis.model`。
  **两种不可用原因不能合并成一个**，否则用户不知道是自己机器缺 ffmpeg 还是模型不支持。

## 5. 参考卡：字段与来源

第一版参考卡 = 现有六维 + 四块创作导向内容，全部带来源与证据。

| 字段 | 回答什么 | 来源 |
|---|---|---|
| `seeWhat` | 画面里有什么、主体位置/大小怎么变 | model 或 user |
| `technique` | 手法是什么（如遮罩揭示、位置跟随） | model 或 user |
| `transferable` | 哪些机制可迁移、适用条件 | model 或 user |
| `doNotCopy` | 品牌标识、具体文字、人物、整套风格 | model 或 user |
| `analysis.*`（六维） | 沿用现有六维 | measured / model / user |
| `evidence` | 片段范围、实际抽帧时间码、帧文件哈希 | measured |
| `limitations` | 「基于抽帧分析，运动细节待核实」 | measured |

- 任何一项模型没答出来 → `pending=true`，`value=""`，**不填"无"**（沿用 `AnalysisValue` 已有约束）。
- `evidence` 只在真有帧时填写，不许出现"关键帧 00:02"这类没有实际抽帧的假佐证。

## 6. 验收样本：三类真实片段

只测一种视频会得出偏乐观结论。至少三类：

| 类别 | 样本 | 关注点 |
|---|---|---|
| 连续运动 | `fengmotion-brand45.mp4` 8s–14s | 主体位移/缩放能否被正确描述；是否编造速度曲线 |
| 明显切换 | `morning-poem-30s.mp4` 0s–2s | 能否看出镜头切换；是否把切换说成"渐变" |
| 动态图形 | `frontend/public/fx/motion/fx-dolly-zoom.mp4` 全片 | 能否说明"手法"而非只描述画面元素 |

异常路径必须覆盖：

- 不支持图片的模型（`spark-x2.6` 在 patch 里没有 `input: image`）→ 明确 `422`，不尝试发送。
- 模型超时/失败 → 片段保持 `pending`，任务 `failed` 带真实原因。
- 取消 → 任务 `cancelled`，**不留下半张参考卡**。
- 分析期间用户改片段范围 → 结果标"已过期"，不写入。
- 分析不可用时：导入、播放、人工切片、收藏必须照常（回归测试）。

## 9. 设计验证期间顺带修掉的两个素材缺陷

这两个缺陷是在跑全量测试时暴露的，与参考片分析无直接关系，但会直接影响
"三库资源可靠"，所以同批修掉。**都是我自己在 `605fb76` 引入的。**

### 9.1 删除一条记录会连带删掉另一条的共用文件

`keepSeparateRecord` 让同内容记录共用同一份文件目录。原 `delete()` 无条件删除整个目录，
于是删掉「甲」时，「乙」的记录还在但文件没了 —— 界面能看到、点开打不开。

修复：删除前用 `countSharingHash(hash, id)` 判断是否还有别的使用者，有则只删记录。

### 9.2 命中已有记录时不再校验文件是否真的可用

原逻辑「哈希命中即复用」。若文件已被外部删掉（或目录存在但文件为空壳），
导入会返回一条死记录，界面却报成功。

修复：复用前检查 `storage.resolve(fileUrl)` 是常规文件且大小 > 0；不可用则重新落盘。
「保留独立记录」分支同样校验 —— 它会抄已有记录的路径，文件已丢时抄过来也是死记录。
