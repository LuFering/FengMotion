# 工作流与创作工作台的边界：待讨论

> 记录日期：2026-11-11。本文记录已提出的产品诉求、当前代码调研和后续讨论方向，**不是已批准的架构决定或开发排期**。后续开始相关开发前，应重新核实代码现状，并与作者讨论取舍。既有工作流产品规范参见 [workflow-spec.md](workflow-spec.md)。

## 产品诉求

工作流的初衷是可由用户自定义和编辑的执行流，以适应不同用户及不同视频类型。对话区、工作台和编辑能力不应被某一种固定流程的节点、步骤或文件格式绑死，导致切换工作流后无法适配。

目前仍以“说清想法 → 看作品 → 指出问题 → 继续修改”为主要用户体验；是否支持某种局部修改、画面引用或特定产物，应由实际能力决定，不应伪装可用。

## 本次调研观察（需随代码变化复核）

- 对话区和工作台分别调用现有创作接口并组装创作请求：`frontend/src/views/Conversation.tsx` 与 `frontend/src/views/Workbench.tsx`。两处各自掌握执行细节，未来增加执行方式时可能需要同时调整。
- 工作台在项目没有已有工作流时会创建默认 Prompt-first 流程。默认路径有助于快速开始，但应明确区分它与用户主动选择的流程。
- 当前真实创作 Agent 依赖 `prompt.original.md`、`corrections.md` 和 Remotion 工程等约定，见 `backend/src/main/java/com/fengmotion/server/workflow/service/CreateAgentRunner.java` 与 `WorkflowProjectService.java`。这些可作为默认执行方式的约定，不宜预设为所有未来工作流的强制格式。
- `frontend/src/services/workflowService.ts` 中的 `startDemoRun` 混合真实能力与明确标注的演示节点；当前不能据此认定用户在画布中编辑的任意工作流都已能逐节点真实执行。真实执行边界应逐项核验。
- 本次观察依据源码，不等于已完成跨工作流的端到端测试。

## 建议的职责边界（待讨论）

1. **对话区和工作台**：收集用户意图、项目与会话、目标引用；展示任务状态、问题和结果。界面应基于能力呈现可用操作，不直接依赖特定流程节点的顺序或内部文件名。
2. **统一创作任务入口**：作为候选方案，负责接收不同界面发来的请求，明确项目、会话、目标、请求身份及选用的工作流版本，并查询能力、管理任务和结果关联。是否需要新服务、接口和数据结构，应在实施前核查现有能力后决定。
3. **工作流执行**：根据指定工作流及其版本执行具体步骤；向上提供真实状态、需要用户处理的问题及产物。Prompt-first 可作为一个默认执行适配，不代表所有工作流必须使用相同约定。

合理的关联仍然需要保留：任务属于项目和会话，记录所用工作流及版本；工作台能接收执行反馈；用户修改工作流后，历史任务的执行依据不应被悄悄改写。

## 需要一起讨论的问题

- 项目如何选择默认工作流；一个项目能否同时使用多条工作流、何时允许切换？
- 工作流定义、版本快照、单次任务和实际产物如何关联？运行中编辑是否只影响后续任务？
- 通用任务输入与结果至少包含哪些信息；时间段、画面区域、素材及审批等能力如何声明？
- 自定义节点如何接入真实执行、取消、中断恢复和错误处理？哪些当前仅是演示？
- 选择的工作流不支持局部修改或目标引用时，是引导选择其他流程、退回支持的范围，还是提供其他处理方式？不得静默扩大作用范围。
- 旧项目、旧任务以及缺少工作流关联的历史记录如何兼容，不能凭空推断历史使用了哪个版本。
- 默认 Prompt-first 执行方式如何作为适配器保留，现有工程和已存任务如何平滑迁移？

## 后续讨论与验证建议

- 当前草稿、目标和会话工作可继续推进；实现新功能时尽量避免在对话区和工作台重复增加特定工作流的执行判断。
- 在涉及多个真实流程之前，先审阅现有任务、工作流运行和消息接口，提出具体迁移方案，再确定是否引入统一入口。
- 用一个步骤确实不同的第二种最小流程验证边界：同一工作台能否发起、显示真实状态、处理追问并查看产物；切换流程是否需要修改界面代码。
- 验证任务运行中编辑工作流、多项目切换、不支持的目标、失败和恢复，以及历史任务版本追溯。
- 第三阶段当前另有待修项：工作台“关于此提问”需真实触发对话回复；对话区提交前应先完成版本核查，并在无法确认时明确处理。这些是现有交互问题，不应误写成工作流架构已定的结论。
