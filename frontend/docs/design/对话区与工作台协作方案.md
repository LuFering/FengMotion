本主线的目标是让同一次创作在完整对话区与工作台侧栏之间连续：项目、会话、消息、任务、作品版本和目标的归属清楚，用户能够边讨论边查看作品、提出修改并核对结果。它不是要把工作台侧栏做成第二套独立聊天系统，也不是扩充传统剪辑器。

**已修：刷新后草稿正文不回填输入框（2026-11-12，读官方 bundle 后定位）**

现象：草稿在 localStorage 里完好、React 的 `draft` prop 值也正确，
但输入框显示为空，用户会以为草稿丢了。

排查链路与结论（逐项有运行时证据）：

| 检查 | 结果 |
| --- | --- |
| 真实键盘输入是否落盘 | ✅ 正常 |
| 刷新后是否自动接回会话 | ❌ → 已修（新增 `fengmotion:active-session:v1`） |
| `LeiBoxComposer` 收到的 `draft` prop | ✅ 值正确 |
| shadow DOM 内 textarea 的 `value` | ❌ 空 |
| `textareaRef.current` 指向 | ✅ 有效，且就是页面上那个节点 |

根因有两层：

1. **会话 id 未持久化**：`activeId` 只存在内存，刷新后为 null，没有会话被选中，
   草稿自然无处显示。已新增 `active-session` 存储，并在选中变化时写入。
2. **官方输入框是受控组件**：读 `composer-engine.js` 确认组件签名是
   `hse({value, onChange, ...})`，textarea 为 `value: ne`（内部 state）+ `onChange: Cse`，
   且上方还有一层镜像 div（`data-message-composer-content`）负责**真正显示文字**，
   textarea 自身文字是透明的。直接改 `textarea.value` 不会更新内部 state，
   镜像仍是空的。必须用原生 value setter + 冒泡 `input` 事件驱动受控层。
   另外 `mount` 返回的 `update()` 只接受 `models` / `selectedModel` / `value`
   （后者写入 `thinking_depth`），**没有任何文本通道** —— 不能靠它注入草稿。

修法：新增 `writeComposerText()`，用原生 setter 改值再派发冒泡 input 事件；
草稿回填改为每次渲染都校验一次（不写依赖数组），以覆盖「textarea 异步挂载完成
之前 draft 已有值」这种时序。

实测：刷新后输入框正确显示草稿、镜像层同步、`--empty` 类移除、发送按钮激活。

**本轮顺带修复：执行中没有停止入口，以及两通道混淆**

`busy` 一直传给了 `LeiBoxComposer`，但包装层从未传 `onStop`，执行期间用户只能等。
补上停止入口后暴露出第二个问题：**工作台的 `busy` 混了工程任务状态，而停止回调只停会话流**
—— 工程任务运行时出现停止键，点了却什么都没停。

读官方 bundle 后确认它的实现是 `A ? 停止键 : 发送键`（A = busy），
**并不检查 `onStop` 是否存在**；`disabled` 表达式是 `A ? !B || E`（B = onStop）。
所以「不传 onStop」并不能隐藏停止键，只会得到一个点了没反应的按钮。

最终按两条通道分开处理：

| 场景 | 按钮 | 可点 | 说明 |
| --- | --- | --- | --- |
| 纯提问流在跑 | 停止键 | ✅ | 点击真的停止该回复流 |
| 工程任务在跑（改工程/渲染/工作流） | 发送键 | ❌ 宿主 `inert` | 整体锁定，阻止重复提交；取消入口在下方任务面板 |

实现：包装层新增 `canStop`，与 `busy` 分离；能停时传 `busy + onStop`，
不能停时用官方的 `disabled`（映射成宿主 `inert`）锁住输入框。
`canStop` 翻转时重挂官方组件（它没有暴露重新绑定回调的接口）。

实测：工程任务运行中 `label=发送 / inert=true`；纯提问运行中 `label=停止 / disabled=false`；
任务结束后 `inert=false` 自动解锁。

**停止必须打到后端（2026-11-12 补）**

原先两个停止按钮的调用链是 `chatStreamManager.stop()` → 流的 `close()` → 只 `AbortController.abort()`。
那只断开浏览器侧 SSE，**后端回复进程并不知情**，会继续跑完并把回复落库 ——
用户看到按钮变回「发送」以为停了，历史里却多出一条没等到的回答。
后端本来就有 `POST /chat-sessions/{id}/stop`，但代码里**从未被调用过**。

修法（2026-11-12 复审后重写，首版有三处不符）：`chatStreamManager.stop()` 改为 async，
**先 await 后端结果，再断本地连接**；并读取响应里的 `stopped` 字段区分四态。
首版的问题与实际代码对照如下：

| 首版声称 | 实际（已修） |
| --- | --- |
| 先请求后端再断本地 | 原为**先断本地、再请求**，界面可能提前解除忙碌 |
| HTTP 200 即视为已停止 | 原**忽略 `stopped` 字段**，`false` 被当成成功 |
| 只有一处调用点 | 实际有多处：`startServerReply`、`newSession`、切换会话各调了一次 |

最终四态与对应文案：

| status | 含义 | 界面行为 |
| --- | --- | --- |
| `stopped` | 后端确认终止了正在运行的回复 | 回到可发送 |
| `not_running` | 后端没找到在跑的进程（可能刚好跑完，也可能停止早于进程注册） | **不谎报已停止**，提示并重新读取会话 |
| `failed` | 请求失败，后端状态未知 | 提示「后端可能仍在执行」 |

调用点也做了收敛：`startServerReply` / `newSession` / 切换会话改为**只清本地 ref**，
不再请求后端 —— 换会话或开新会话不等于放弃那条回复；真正的停止只由用户点击触发。

**另一种重复：同一轮起了两条流（重启后实测发现）**

早停时出现 2 条 `stream` + 2 次 `/stop`。根因不在停止逻辑，而在**起流**：
发送路径（`chat.appendMessage` 之后）和自动起流 effect 都会调 `startServerReply`。
effect 的守卫是 `chatStreamManager.has(sessionId)`，但那一刻 stream 还没注册，
守卫为 false，于是起了第二条。修法：发送路径**先登记 `servedRef` 再起流**，
并把 effect 守卫从 `servedRef.has(id) && pending` 改为只看 `servedRef.has(id)`
（`pending` 是 React state，要等一次渲染才更新，不能当同步守卫）。

**五种停止场景实测（重启应用后，安装态 + 网络拦截）**

| 场景 | 结果 |
| --- | --- |
| 正常停止 | 1 次 `/stop`，按钮回到「发送」 |
| 刚启动就停止 | 1 条 stream、1 次 `/stop`（修前是 2+2） |
| 流自然结束后 | 停止键消失，按钮为「发送」 |
| 停止接口失败 | 提示「停止请求没有送达（…）。后端可能仍在执行，请稍后重新读取会话确认」，不谎报成功 |
| 切换会话 | 0 次 `/stop`（修前会重复请求） |

后端 `stopped:false` 语义单独核对：空闲会话调用 `/stop` 返回 `{"stopped":false}`，
代码据此判为 `not_running` 而非「已停止」。

**清理不能只靠 SSE 事件（2026-11-12 复审后补）**

后端一确认停止，管理器就断开连接；而「撤掉未完成回复 + 显示已停止」原先只挂在
SSE 的 `onStopped` 回调上 —— 连接已断，那个回调可能不再执行，半截回复会留在界面。
修法：管理器在确认停止时登记「哪一轮被停止」（`takeConfirmedStop`，读后即删），
对话区与工作台在收到 `stopped` 广播时读这个标记做清理，并与事件路径去重。

**后端接口直测三种状态（隔离会话，绕过 UI 输入）**

| 场景 | 请求 | 结果 |
| --- | --- | --- |
| 空闲会话停止 | `POST /stop` | `{"stopped":false}` HTTP 200 |
| 真实运行中停止 | 启动流 → `POST /stop` | `{"stopped":true}`；SSE 收到 `stopped{reason:"user_stopped"}` |
| 停止后是否落库 | 查 `/messages` | **只有 1 条用户消息，没有 AI 回复** —— 后端进程确被终止 |
| 会话不存在 | `POST /stop` | 404 `not_found`「会话不存在」 |
| 后端不可达 | 指向无效端口 | 连接失败（前端判为 `failed`，提示「后端可能仍在执行」） |

**关于 `stopped:false` 的产品语义（待确认）**

用户点停止，理想结果是该轮停止。当前实现遇到 `false`（后端未找到进程，
可能是停止早于登记）时保持连接、等真实终态，**不谎报停止**。
但这意味着回复可能随后仍出现。长期更可靠的做法是让后端按本轮请求身份
记录取消意图，覆盖启动前的时间窗口 —— 这需要后端配合，未在本轮实施。

两处调用点据此处理：

- 成功：界面回到可发送；
- 失败：如实提示「已停止等待这条回复，但后端可能仍在执行（原因）。请查看执行记录确认」，
  不谎报停掉。
- `onStopped`（服务端确认的 stopped 事件）里不再调用 stop，避免重复发请求；
  切换会话时停旧流也会通知后端。

实测（真实应用 + 网络拦截）：点击停止后确实发出
`POST /chat-sessions/{id}/stop`；随后该会话历史里**没有**新增那轮未完成的回复
（最后一条仍是更早的完成消息），证明后端进程确实被终止而非继续落库。
后端契约单独验证：`POST /stop` 返回 200 `{"stopped":false}`（无在跑流时）。

**文案修正（保存边界）**

原提示写「这一轮没有保存到会话里」，不准确：**用户消息在启动回复流之前就已写入服务端**，
停止后不保存的只是那条未完成的 AI 回复。对话区与工作台两处文案均改为
「已停止生成。你的消息已保存，这条回复没有保存。」，工作台的 `onStopped`
也补上了移除占位消息与可见反馈（原先只调了 `stop`，侧栏会留下半截回复）。

**仍未验收**

- 双向切页时若正处于执行中，流是否连续、状态是否一致，尚未专项验证。
- 断线重连、后端进程崩溃后的恢复路径未验证。

**轮次竞争：迟到的停止响应不能关掉新一轮（2026-11-12 复审后补）**

停止请求是异步的。等待后端答复期间，SSE 的 `stopped` 事件可能先到、界面恢复可发送，
用户立刻发出下一条 —— 此时该会话登记的是**新一轮**的流。
原实现响应回来后按 `sessionId` 现取当前流并关闭，会把用户刚发起的新回复掐掉、
还标成 `stopped`。这是最难排查的一类 bug：现象是「偶尔刚发出去就没了」。

修法（`src/features/chat/services/chatStreamCore.ts`）：

1. **固定目标轮次**：`stop()` 一进入就把要停的那条流抓住，响应回来后只认它 ——
   当前流仍是同一对象才收尾，否则返回 `supersededRound: true`，本地什么都不做。
2. **在途去重**：同会话已有停止请求在途时复用同一个 Promise，连点只打一次 `/stop`。
3. **期间保持忙碌**：`isStopping()` 让输入框在结果未定时继续忙碌，
   从源头不给「停止中发出下一轮」这个机会。两层叠加才真正闭环。

为让这条时序能被真实代码覆盖（而不是测试脚本里另写一份副本），
状态机抽成不依赖 React 与路径别名的 `ChatStreamCore`，
`chatStreamManager.ts` 只负责接后端接口与接 React。
测试 15 现在直接 `import { ChatStreamCore }`，用可控的假传输层复现交错顺序。

**停止后必须清掉「本轮痕迹」（真机验收发现）**

真机点停止后，正文撤掉了，但「思考 / bash · 1 次 / 11.5K 上下文条 / token 用量」
还留在界面上 —— 用户看到的是「停了但没停干净」。三处根因都修了：

| 残留 | 根因 | 修法 |
| --- | --- | --- |
| 上一轮的思考文本 | `lastThinking` 从末尾往前找第一条带 thinking 的 AI 消息，会**越过本轮用户消息**取到上一轮 | 只在本轮用户消息之后找 |
| 工具调用列表 | `toolCalls` 是独立 state，不随消息撤销 | `clearRoundTrace()` 统一清空，两条停止路径共用 |
| 上下文条 / 用量 | 卡片画在列表末尾，撤销回复后退回「最后一条带 usage 的 AI 消息」= 上一轮读数 | 末尾不是 AI 回复时不画；实时 `breakdown`/`contextUsed` 随本轮一起清 |

实测（安装态）：停止后消息区只剩用户消息 + 「已停止生成。你的消息已保存，这条回复没有保存。」，
后端 `/messages` 也只有用户消息，无 AI 回复。

**`stopped:false` 文案已改（用户确认）**

原「后端没有找到正在运行的回复（可能已自然结束）」偏中性，容易被读成「没事了」。
现改为：**「这次没有停止到正在运行的回复；回复可能继续，也可能已经结束。」**
并保留「可以再点一次停止」的路径 —— 不改变停止行为，只让现有状态如实可理解。

**⚠️ 新发现（未修，需决策）：刷新后「已停止」的那一轮会自动重新开始**

真机验收时反复出现：停止后刷新页面（或切走再回来），那条被停止的用户消息
**又自动开始生成**。原因不是停止失效，而是两条既有机制撞在一起：

1. 前端「自动续流」：页面重载会清空模块级 `servedRef`，effect 看到
   「最后一条是用户消息、后面没有 AI 回复」就判定为「流断了要接上」，于是重新起流。
2. 后端侧「停止」没有留下可识别的痕迹：停止后该会话的状态就是
   「最后一条用户消息没有回复」—— 与「刚发出去、还在排队」**完全一样**。

所以前端无法区分「这一轮被用户主动停了」和「这一轮还没开始」。

修法有两条路，需要产品决策：

- **前端记**：把被停止的用户消息 id 持久化（localStorage，按会话），刷新后跳过自动续流。
  改动小，但属于本机记录，换设备/清缓存后失效。
- **后端记**：停止时给该轮次打标记（如 `stoppedAt`），前端据此不续流。
  更可靠，但要动后端接口与数据模型。

未实施。当前行为是「停止本身可靠（不落库、界面清干净），但刷新后可能重跑一轮」。

“阶段收口”表示当时同意继续推进，不代表全部异常场景已通过最终验收。阶段 2、3 不在此补写未经确认的封版结论。

### 第五阶段盘点结果（2026-11-12，源码 + 安装态对照）

口径：按第五阶段第 1 条，核对同一会话在**完整对话区**与**工作台侧栏**的会话标识、
消息层次、目标引用、状态呈现。证据为源码位置 + 安装态截图（同一会话
`用 bash 执行 sleep 30…`，项目「制作能力验证」）。

#### 一、会话标识：两处不是同一套概念

| | 完整对话区 | 工作台侧栏 |
| --- | --- | --- |
| 入口形态 | 左栏**按项目分组的会话列表**（`cv3-group` / `cv3-session`），当前项目排最前、默认展开 | 顶部「控制台」右侧一个**下拉框**（`ConsoleChrome` 里的 `<select>`），只列当前项目的会话 |
| 标题来源 | `t.title`；未命名时显示「未命名对话」 | 有真标题用 `title`，否则取**首条用户消息前 14 字** |
| 时间 | `fmtAgo`（「3小时前」） | `toLocaleTimeString`（「14:32」） |
| 归属项目 | 分组头显示项目名 + 会话数 | **不显示项目名**（隐含「就是当前项目」） |
| 其他状态 | 「已归档」「仅本页」标记、置顶图钉 | 无 |

**结论**：同一会话在两个界面**名字可能不一样**（对话区叫「未命名对话」，
侧栏显示首句摘要），时间格式也不同（相对 vs 绝对）。
用户切到工作台会看到「这是哪个会话」的困惑。这是本轮要收的第一项。

#### 二、消息层次：AI 回复的呈现差别最大

| | 完整对话区 | 工作台侧栏 |
| --- | --- | --- |
| 用户消息 | `ChatMessage` 气泡 | 同一个 `ChatMessage` —— **一致** |
| AI 回复 | `cv3-ai-block`：**过程区（思考 + 工具调用 TaskList）+ 正文 + 用量 + 上下文条** | `ChatMessage role="ai"`：**只有正文**，无思考、无工具调用过程 |
| 停止后的说明 | `cv3-demo-note` | 侧栏走 `onNotice` 顶部提示 |

**结论**：侧栏看不到「它做了什么」——而工作台恰恰是用户最关心
「AI 到底改了什么」的地方。这是**功能缺口**，不只是视觉差异。
但侧栏空间窄，不宜直接塞进完整 TaskList，需要折叠形态。

#### 三、目标引用：对话区弱于工作台

| | 完整对话区 | 工作台侧栏 |
| --- | --- | --- |
| 目标展示 | `TargetSummaryPill`，**仅当 `targetSnapshot` 存在**才渲染 | 输入框上方常驻「v8 · 全局工程」胶囊 + 「修改此目标」「关于此提问」 |
| 意图切换 | 在 Pill 里（目标存在时才可见） | 常驻两个按钮，无目标也能选 |
| 无目标时 | 仅「继续调整」模式下给一条琥珀色提示 | 默认显示「全局工程」，语义明确 |

**结论（已按用户 2026-11-12 复审修正）**：工作台**永远知道这次意见作用于什么**；
对话区在没有目标时**什么都不显示**。风险不在于「没有目标 = 整片修改」——
发送路径并不是这么判的——而在于**用户看不到这次实际会执行什么**。
详见下方「五、发送意图的真实判定链」。

#### 四、状态呈现：各有独占项，但关键事实两边都该能查到

| 状态 | 完整对话区 | 工作台侧栏 |
| --- | --- | --- |
| 思考中 / 工具调用中 | `ThinkingIndicator` + TaskList 实时推进 | 无（但 `executedTools` 数据其实在，只是没渲染） |
| 停止中 | 输入框忙碌 + 停止键（本轮已接） | 同（本轮已接） |
| 工程任务执行中 | 不涉及 | `wb-real-execution-status`（分析中 / 渲染中） |
| 未改动工程 | 无 | `wb-ai-attached-note`「本轮未改动工程 · 没有新版本」 |
| 回复补存失败 | 无 | `wb-unsaved-reply-alert`（逐条补存） |
| 上下文占用 | `cv3-ctxmeter` | `wb-ctxmeter`（同一组件） |

**结论（已修正）**：「未改动工程」与「回复未保存」**不是侧栏专属信息**。
原方案要求两边都能找到影响判断的事实 —— 用户在工作台发起、回到对话区后
同样需要知道「这轮没有新版本」「这条回复没存进服务端」。
侧栏可以保留更紧凑的形式，但对话区不能没有。

⚠️ **实施前必须核实数据来源**（本轮已查，结论如下）：

| 状态 | 数据来源 | 能否按「这一轮」可靠关联 |
| --- | --- | --- |
| 未改动工程 | `awaitingInfo` —— **项目级单值 state**（`Workbench.tsx:993`），只记最后一次 | ❌ 不能。它没有消息 id，历史上每条回复都会读到同一个当前值 |
| 回复未保存 | `unsavedReplies`，按 `userMessageId` 关联 | ✅ 可以，本来就有消息身份 |
| 过程数据 | `executedTools`，**每条消息自带**（`useChat.ts:26`，从服务端读回） | ✅ 可以，天然按消息隔离 |

所以「未改动工程」要搬到对话区，**先得让它带上消息身份**
（例如后端在任务结果里回写 `userMessageId`），不能把当前项目的临时值
当成每条历史消息的结论，更不能把「没生成新版本」解释成「AI 在追问」。

#### 五、发送意图的真实判定链（本轮核实）

对话区与工作台的意图规则**一致**，但对话区的可见性只在有目标时才存在。

真实判定顺序（`Conversation.tsx:1762-1784`）：

1. `continuationScopeMode === 'target_required'` 且无目标快照 → **直接拦截报错**，
   不当作普通聊天吞掉；
2. `effectiveIntent = targetSnapshot?.intentAction ?? draft.intentAction`
   —— 目标快照优先，其次草稿级；
3. `isModifyIntent`：显式 `query` **永远赢**（任何范围确认都不能推翻）；
   否则有显式意图取显式、无显式则看「有无目标快照」或「是否已确认整片」；
4. **三者都没有时 → 普通对话**（`isModifyIntent = false`），走会话回复流，不改工程。

**所以「无目标」绝不等于「按整片提交」**。无目标且无意图时是普通对话；
只有 `whole_confirmed`（用户显式点过「确认整片修改」）才是整片修改。
盘点初稿把它写成「按整片提交」是错的，已更正。

跨页草稿的风险点也在这里：用户在对话区写普通对话草稿，切到工作台后
**不能**因为「工作台默认显示全局工程」就自动附加画面或把意图改成修改。
当前代码在这条路径上是对的（意图只由 `intentAction` / `targetSnapshot` 决定），
但界面上没有把「现在会走哪条路」说出来 —— 这正是要补的可见性。

#### 建议的改动优先级（已按用户意见重排）

1. **统一会话身份**（先做）：同一会话共用标题取值规则；侧栏清楚标明当前项目；
   时间统一语义（相对/绝对可因空间不同，但不能让同一时间产生歧义）。
2. **核实并补齐发送意图可见性**（与第 1 项同等优先）：针对普通对话、
   显式目标、整片续改、跨页面草稿四种情况，展示**与真实发送路径一致**的意图与范围。
   不新增语义，只把已有判定结果显示出来。
3. **真实过程与结果摘要**（后做）：侧栏只展示**有真实且属于本轮**的过程数据
   （`executedTools` 存在才显示可展开摘要，不按消息长度或状态猜步骤数）；
   两处都能查到未改动、保存失败、结果等关键事实，布局各自适配。

不改动：不把 `awaitingInfo` 这种项目级临时值直接当作历史消息结论。

**本轮只盘点与核对，未改代码。** 第 1、2 项需先出设计再实施。

#### 六、第 1 项设计：统一会话身份

**实测证据（同一批会话，两处显示）**

对话区左栏：

```
用 bash 执行 sleep 30，然后回答   21分钟前
未命名对话                        3小时前
未命名对话                        3小时前
```

侧栏下拉（`ConsoleChrome`）：

```
用 bash 执行 sleep 30，然后回答 (22:42)
未命名对话 (19:46)
未命名对话 (19:44)
未命名对话 (17:29)   ← 实际是 2026-11-06，六天前
```

三处不一致，按严重程度：

| # | 问题 | 证据 | 后果 |
| --- | --- | --- | --- |
| A | **跨天时间没有日期** | `f5d415a4` 实际 `2026-11-06 09:29Z`（本地 17:29），下拉显示「(17:29)」 | 与今天 17:29 无法区分，**同一时间产生歧义** |
| B | **同一会话名字不同** | 对话区「未命名对话」，侧栏取首句前 14 字 | 用户以为是两条不同会话 |
| C | 侧栏不显示项目名 | 下拉只列当前项目会话 | 多项目用户不知这些属于哪个项目 |

**设计（只改显示，不改数据）**

1. **标题规则唯一化**：两处都调 `sessionTitle()` 的同一套规则 ——
   有服务端标题用它；没有则取首条用户消息（现有 `useSessions.ts:95` 的实现），
   都没有才显示「未命名对话」。**侧栏不再自己拼首句**，直接读 `session.title`。
2. **时间语义统一**：两处都用「相对时间 + 绝对时间可查」。
   - 对话区左栏：`fmtAgo`（3小时前）—— 已有，保留；
   - 侧栏下拉：空间窄，用 `fmtAgo` 的短形态（`3小时前`），
     **跨天必须能区分**（`3天前` / `11月6日`），不再只给时分。
   - 悬停给完整时间（`title` 属性），这是「格式可不同、语义不能歧义」的落点。
3. **侧栏标明当前项目**：下拉旁或选项内显示项目名；
   当前项目只有一个时也要能看出「这些会话属于这个项目」。

**不做**：不合并两处的会话列表（对话区是跨项目分组，侧栏是当前项目上下文，
职责本就不同）；不改后端标题生成逻辑。

**验收口径**：同一会话在两处显示**同一个名字**；任意时间点都能判断出
「是今天还是六天前」；从侧栏能看出会话属于当前项目。

#### 七、第 2 项设计：发送意图可见性

**目标**：让用户在看到输入框时就知道「这句话发出去会走哪条路」，
显示内容必须与 `Conversation.tsx:1762-1784` 的真实判定一致。

四种情况，各自的真实行为与建议显示：

| 场景 | 真实判定 | 现状显示 | 建议显示 |
| --- | --- | --- | --- |
| 普通对话（无目标、无意图、未确认整片） | `isModifyIntent = false` → 会话回复流 | 无任何提示 | 「仅对话，不会修改工程」 |
| 显式目标 + 意图为修改 | `isModifyIntent = true` → `workflow_modify` | Pill 显示目标 | 保留 Pill，补「将修改工程」 |
| 显式目标 + 意图为提问 | 显式 `query` 优先 → `workflow_query` | Pill 显示目标，但意图靠按钮高亮 | 明确「仅提问，不修改」 |
| 已确认整片续改 | `whole_confirmed` → 整片 `workflow_modify` | Pill 或琥珀提示 | 「将修改整片工程」 |
| `target_required` 且无目标 | **直接拦截报错** | 琥珀提示 + 两个按钮 | 保留（已是明确拦截） |

**关键约束（按用户复审）**：

- **不能因为「没有目标」就写「按整片提交」** —— 那是错的，无目标无意图是普通对话。
- **跨页草稿不得改变意图**：对话区写普通对话 → 切到工作台 →
  不能因为工作台默认显示「全局工程」就自动附加画面或把意图改成修改。
  当前代码在这条路径上是对的，但界面必须把「现在会走哪条路」说出来，
  否则用户看到「全局工程」会以为要改工程。
- 显示的是**判定结果**，不是新增一套并行语义；文案直接从 `isModifyIntent` +
  `targetSnapshot` + `continuationScopeMode` 推出，不另存状态。

**实现位置**：对话区已用 `TargetSummaryPill`（支持 `draftIntent` 兜底），
现在只在 `targetSnapshot` 存在时渲染 —— 改为**总是渲染**，
无目标时由 Pill 自己按 `draftIntent`/默认值给出「仅对话」或「全局工程」摘要。
工作台侧已常驻，只需核对文案与判定一致。

**验收口径**：四种场景下，界面文字与实际发出的 `action`
（`workflow_modify` / `workflow_query` / 无 action）一一对应；
跨页草稿切换后意图不被静默改写。

#### 八、第 2 项已实施（2026-11-12）

**先统一判定，再改显示** —— 按用户要求，没有直接把胶囊改成"总是渲染"。

新增 `src/features/chat/model/sendPlan.ts`，`resolveSendPlan()` 是**唯一**判定实现，
发送（对话区 `sendToServer`、工作台 `submit`）与显示（`TargetSummaryPill`）
全部调它。判定顺序：

1. `target_required` 且无目标 → **拦截**（不是普通对话，也不是整片修改）；
2. 意图 = 目标快照优先，其次草稿级；
3. 显式 `query` **永远赢**（范围确认不能推翻）；
4. 显式 `modify` → 修改（**没有目标快照也算修改**）；
5. 无显式意图：有目标快照或已确认整片 → 修改；
6. 三者都没有 → **普通对话**。

**修掉的两处真实误导**（都是组件默认值造成的）：

| 问题 | 修法 |
| --- | --- |
| `effectiveIntent = ... ?? 'modify'`，把无目标无意图的普通对话显示成"修改全局工程" | 改为取 `resolveSendPlan` 的结果，无意图不再兜底成 modify |
| 普通对话时 scope 默认 `'project'`，摘要显示"全局工程" | 普通对话不显示工程范围，摘要显示「普通对话」 |

**展开面板也修了一处自相矛盾**：普通对话时"发送预期动作"已写「不会修改工程」，
但下面"目标范围与时间"仍写「全片修改（作用于整个项目工程）」。
现按判定结果分支：非修改时改为「引用范围 / 不涉及修改范围」，模式行改「仅提问」。

**顺带修掉一个视觉缺陷**：`.cv3-seat` 只有一条 `linear-gradient` 做背景，
整块区域底色其实是渐变的，消息区滚到下面会**透出来**——
实测出现「消息里的圆形图标压在目标详情框上」，看着像层级错乱。
改为渐变层 + 实色层叠加，下缘完全不透明。

**安装态实测**（项目「制作能力验证」）：

| 操作 | 胶囊摘要 | 展开面板 |
| --- | --- | --- |
| 初始（无目标无意图） | 普通对话 | 发送预期动作：普通对话 —— 只回答问题，不会修改工程 / 引用范围：不涉及修改范围 / 当前模式：仅提问 |
| 点「修改此目标」 | 全局工程 · 尚无版本 | 修改整片工程 —— 将修改整个项目工程，并生成新版本 / 全片宏观 |

#### 十三、侧栏过程摘要：从「历史摘要」补成「实时过程」（2026-11-12）

复审指出上一版**只证明了历史记录可展示，没证明执行过程已接通**。两处都成立，已修。

**1. 侧栏流回调没有接收工具事件**

原先侧栏 `chat.stream()` 只处理了 `onReasoning` / `onDelta` / `onTodo`，
`onCompleted` 里传的工具列表还是 `undefined` —— 执行过程中看不到任何步骤，
只有完成后重读历史才有。用户在最关心「AI 到底改了什么」的地方反而看不到过程。

修法：新增 `useChat.recordToolCall()`，侧栏补 `onStatus`，规则与对话区一致：

- 带 `arguments` → 开始帧，追加条目（**不写 `done`**，与后端落库一致）；
- 带 `callId` 无 `arguments` → 结果帧，回填 `done: true` 与 `isError`，
  **不清空 name/arguments**（后端结果帧不带 name，整个覆盖会让名字消失）。

**2. `done` 缺失被当成「完成」**

后端 `ChatStreamService.onToolCall` 在工具开始时只写 `callId`/`name`/`arguments`，
收到结果才回填 `done`。原实现只在 `done === false` 时显示「进行中」，
于是缺失 `done` 一律落到「完成」—— 把「不知道结果」谎报成成功。

修法：`toolStepState(t, roundRunning)` 四态：

| 条件 | 状态 |
| --- | --- |
| `isError` | 失败 |
| `done === true` | 完成 |
| `done === false` | 进行中 |
| 缺 `done` + 本轮仍在跑 | 进行中 |
| 缺 `done` + 本轮已结束 | **状态未知** |

`roundRunning` 是必需的：实时开始帧本来就没有 `done`，而这一轮明显在跑，
说「状态未知」也不准确；反过来本轮已结束却仍缺 `done`，那才是真的不知道。

**安装态实测（完整链路）**

| 阶段 | 观测 |
| --- | --- |
| 执行中（sleep 25） | 摘要「**正在执行** · 执行命令 1 次」，`data-running` 为真；展开步骤 `data-state="running"`「进行中」 |
| 执行完成 | 摘要「**执行了 1 步** · 执行命令 1 次」；步骤 `data-state="done"`「完成」 |

即：**同一轮里状态会从「进行中」翻到「完成」，不再是一开始就写死完成**。

测试 22 覆盖四态判定（含 `done` 缺失的两种情形）、实时记录的开始/结果帧规则、
结果帧不清空 name/参数、无 `callId` 结果帧不误伤其他条目。

`tsc = 0`、`build = 0`、22/22 通过，已部署。

#### 十四、真实调用点回归测试（2026-11-12）

按用户要求补的是**从界面操作发送、观察真实网络请求**的测试，
不再模拟分流逻辑。脚本：`frontend/test_ui_callpoints.py`。

**它抓到了三个此前所有单测都抓不到的真实缺陷。**

**缺陷 1：输入框可能整块不可见、不可点（P1）**

真机现象：点击输入框毫无反应、键盘无法聚焦，`textarea` 存在但
`visibility: hidden`，点击落到外层 `.lbx-compose-box`。

根因：`LeiBoxComposer` 挂载时「先隐藏 → 替换官方舞台 → 再显示」，
但 `flatten()` 依赖官方组件把 `stage`/`composer` 渲染出来 —— 那是异步的，
rAF 一帧未必够。一旦失败，代码路径**没有恢复 `visibility`**，
宿主就永久隐藏。手动执行同样的替换逻辑立刻成功，证明是时序问题。

修法：改为多帧 + 定时重试（约 2 秒），并用 `setTimeout` 兜底强制恢复可见
—— 宁可露出官方原样舞台，也不能让输入框永久不可见。

**缺陷 2：整片工程修改会额外误起一条普通对话（P1）**

真机现象：一次「修改此目标」提交后，除了创作任务，还冒出一条 AI 思考回复。

根因：`isModifyIntent` 为真但没有 `targetSnapshot`、也没点过「确认整片」时
（即「全局工程 + 修改」），代码**不推任何 `workflow_modify` 引用**；
而自动续流守卫正是按 `action === 'workflow_modify'` 判断「这是创作任务，别再起回复」。
标记缺失 → 守卫失效 → 多起一条普通回复流。

修法：`isModifyIntent` 且无局部目标时，推一条 `role:'target'`、
`action:'workflow_modify'`、`label:'整片工程修改'` 的引用。

**缺陷 3：改一个字再发，报「幂等键已用于不同请求」**

根因：幂等键在失败分支没有清空，且**没有与内容绑定**；
用户修改措辞后复用旧键，后端判定为「同一键不同内容」直接拒绝。

修法：给键绑定正文（`idemTextRef`），内容一变就换新键。

#### 十五、重试身份修正（2026-11-12，用户复审后）

**背景：为什么必须带消息身份**

## 原始完整方案

以下保存用户提供的原方案正文，供新会话恢复上下文；其中“目前”等状态以原方案编写时为准，不代表本次已重新验收。

重新梳理后，我认为上一版的方向有一部分是对的，但把两边简单概括成“完整会话”和“精简会话”还不够准确，也遗漏了项目中最重要的一层：**对话区和工作台处于同一创作流程的不同阶段，面向的核心对象不同。**

- **对话区以“想法和会话”为中心**：帮助用户开始创作、探索需求、组织项目和会话，也能回顾完整创作交流。
- **工作台以“当前作品”为中心**：帮助用户看画面、指出问题、让 AI 修改、核对结果，并围绕具体版本继续创作。
- **工作台侧栏的对话是连接两者的桥**：它不仅是缩窄后的聊天记录，还必须知道用户正在看哪个版本、指的是哪段画面，以及这次修改产生了什么结果。

## 一、先理清项目要完成的事情

根据项目的 [产品定义](/home/lufering/ai-video-desktop/FengMotion-desktop/PRODUCT.md)，FengMotion 面向的是有视频想法、但不一定会编程或剪辑的个人创作者。核心流程是：

**描述想法 → AI 制作真实视频工程 → 渲染预览 → 指出具体问题 → AI 修改 → 对比和继续调整。**

所以，项目的中心不是聊天，也不是时间线，而是**让想法持续变成可检查、可修改的视频作品**。

两处对话都服务于这件事，但关注的问题不同：

| | 对话区 | 工作台侧栏 |
|---|---|---|
| 用户主要在想什么 | “我想做什么？怎么做？继续哪个项目？” | “这个画面哪里不对？这次改成什么？” |
| 主要上下文 | 项目、会话、想法、参考资料 | 当前项目、版本、画面、时间、内容目标 |
| 主要产出 | 清晰的要求、方案、创作请求、交流记录 | 具体修改请求、执行状态、结果与下一步 |
| 阅读方式 | 适合长篇讨论、查看历史、切换会话 | 适合边看边说、快速追问、核对修改 |
| 与画面的关系 | 可跳转作品、引用作品，但画面不是当前操作中心 | 与右侧画面和时间范围直接联动 |

这里还有一个重要边界：用户从对话区发出的内容不一定都是“讨论”，也可能是明确的创作要求；工作台里也不一定每句话都是“修改”，用户可能只是在问“这个圆点现在在哪里”。**页面位置不能成为判断用户意图的唯一依据。**

## 二、目前项目里的实际情况

### 1. 对话区已经承担项目和会话入口的作用

当前的对话页不只是聊天界面。代码中有项目、会话的组织与切换，首页需求也可以带入这里；从这里可以进入项目工作台。页面源码自身也将其描述为“先聊清楚，再开始制作”。见 [Conversation.tsx](/home/lufering/ai-video-desktop/FengMotion-desktop/frontend/src/features/chat/Conversation.tsx:51) 和 [App.tsx](/home/lufering/ai-video-desktop/FengMotion-desktop/frontend/src/app/App.tsx:256)。

因此，对话区要解决的不仅是“完整显示消息”，还包括：

- 用户从哪里开始一段创作；
- 当前讨论属于哪个项目和哪条会话；
- 用户如何找到以前的想法、要求和结果；
- 一段讨论如何进入实际制作。

### 2. 工作台承担的是作品创作与审阅

工作台围绕项目中的实际工程、画面、版本、时间和创作任务展开。侧栏中除了对话，还有创作要求、执行记录、版本和修改审阅等入口；右侧则承担画面与相关工作区。

目前工作台的真实修改路径会读取项目状态、确认基准版本，并根据情况把意见写入项目、调用创作流程。针对画面和时间范围，还会检查相关能力和版本。见 [Workbench.tsx](/home/lufering/ai-video-desktop/FengMotion-desktop/frontend/src/features/workbench/Workbench.tsx:1369)。

这意味着侧栏不能只当作聊天窗口：它还要能把**用户所指的具体对象**准确带到创作请求中。

### 3. 两处已有共享基础，但还不是统一的可靠链路

当前应用创建了一份 `useChat()` 状态并传给两个页面，见 [App.tsx](/home/lufering/ai-video-desktop/FengMotion-desktop/frontend/src/app/App.tsx:139)。这让两处有共享消息的基础，但还有几个重要限制：

- 对话页有明确的 `activeSessionId`，工作台目前没有直接接收它；进入工作台时，不能仅凭共享内存断定侧栏已经绑定了正确会话。
- 两处发送路径不同：对话页走会话消息和回复流程；工作台的实际修改走创作流程。
- 侧栏目前会接纳没有项目归属的消息，这在项目切换时存在归属不清的风险。
- 对话页卸载或切会话会关闭当前回复流；源码说明后端当前不支持流的断点续读，不能把“切换后实时无缝续接”当作已具备能力。
- 对话页输入组件的文字由组件内部持有，不能仅凭共享 `chat.draft` 判断草稿已经同步。
- 工作台当前 AI 回复既有 `agentReply` 局部状态，也有部分历史恢复时写入共享消息的逻辑。完整回写和跨页面恢复需要单独打通，不能假定现在已经成立。

这些结论来自源码检查；**目前没有做跨页面、刷新、断线和多会话的完整端到端验证**。

## 三、上一版回答需要修正的地方

### 1. “侧栏就是完整会话的精简视图”说得太窄

侧栏确实应该能呈现关联会话，但它还承担**作品上下文、目标引用、修改反馈和结果跳转**。只把长消息折叠，并不能解决工作台的核心问题。

更准确的说法是：

> 对话区组织和展开创作交流；工作台侧栏把相关交流放回具体作品的上下文中，并与右侧操作联动。

### 2. “始终共用同一条当前会话”缺少进入路径

这只适用于用户**从某条明确会话进入工作台**的情况。

用户也可能从项目入口直接打开工作台、从任务或版本记录进入，或者打开一个还没有会话的项目。这时如果默认拿全局当前会话，可能把不同项目的内容混在一起。

正确做法应该是：先明确会话归属，再决定绑定哪条会话，不能简单取最后显示的内存列表。

### 3. “两边全部显示同一内容”需要区分内容类型

我上一版强调消息不能被偷偷隐藏，这个原则仍然成立；但不代表侧栏要把所有历史信息、全部日志都直接铺出来。

应该区分：

- **用户交流和影响判断的结果**：属于会话事实，两边都要可找到。
- **任务执行细节**：属于任务事实，对话中只需合适的摘要和入口。
- **页面临时状态**：例如播放器当前暂停、面板是否展开，不是消息，不需要作为聊天内容同步。

共享的是事实和归属；每个界面可以用合适的方式呈现。

### 4. “模型和权限必须按会话同步”不能直接定为现有事实

上一版把它写得过于绝对。项目中引擎、模型、推理强度和权限分别有什么真实生效范围，还需要核实各自接口。

更稳妥的产品要求是：**用户在发送前必须看得到实际会生效的设置；两处若使用同一个设置来源，就显示一致；若创作链路不支持某项设置，就不能展示成已生效。** 是否长期按会话记忆，需要结合真实能力设计。

### 5. “统一发送路径”不等于把两种执行能力强行合并

普通对话和修改工程可以使用不同的后端执行通道。需要统一的是：

- 这次请求属于哪个项目和会话；
- 用户提交了什么；
- 执行的是哪一种操作；
- 结果、状态和错误如何回到同一条记录。

不能因为希望两处消息一致，就把真实创作流程降级成普通聊天接口。

# 四、完整优化方案

## 1. 明确两处的产品职责

### 对话区：创作沟通与项目会话入口

对话区负责让用户从想法进入创作，并保留完整沟通过程。

应该重点支持：

- 选择项目、创建或切换会话；
- 输入想法、提供素材和参考；
- 与 AI 讨论创作思路、回答追问；
- 发起真实支持的创作任务；
- 查看完整消息、较长说明和附件；
- 从结果进入对应工作台、版本或任务；
- 回顾以前的沟通与创作结果。

对话区不需要模拟完整编辑器，也不需要常驻一套缩小版时间线。

### 工作台侧栏：围绕作品进行创作反馈

侧栏负责让用户在看画面的同时，围绕明确目标继续创作。

应该重点支持：

- 查看关联的对话和最近创作交流；
- 将当前项目、版本、时间范围、画面区域或可信内容带入请求；
- 对选中的对象提问或提出修改；
- 查看任务正在做什么、是否需要补充信息；
- 查看本轮结果，并在右侧定位或对比；
- 打开完整对话，继续查看长内容和历史。

侧栏不是独立于项目的第二个聊天系统，也不应该承担项目管理页的全部功能。

---

## 2. 建立明确的项目、会话和任务关系

建议以以下关系作为数据和界面设计基础：

```text
项目
├── 会话 A
│   ├── 用户消息 / AI 回复
│   └── 关联的创作任务与结果
├── 会话 B
│   └── 用户消息 / AI 回复
└── 作品
    ├── 场景与版本
    └── 任务、修改记录和产物
```

其中：

- 一个项目可以有多条会话。
- 一条会话可以产生多次创作任务。
- 一次任务关联发起它的会话和请求，也关联它修改的项目与基准版本。
- 一个版本属于作品，不因为切换会话而消失。
- 一条会话里的消息不能因为打开另一个项目而被带过去。

### 不同入口如何决定侧栏显示什么

**从某条会话进入工作台**

- 侧栏绑定该会话。
- 返回对话区仍回到同一条会话。
- 当前会话的草稿和上下文按实际同步能力保留。

**从项目直接进入工作台**

- 优先恢复该项目上次明确使用的会话，但要确认它仍属于该项目且可用。
- 如果没有可恢复会话，显示项目内的空白对话入口；用户首次发送时创建项目会话。
- 不自动借用其他项目或未分组的活动会话。

**从任务、版本或历史结果进入**

- 如果记录关联了会话，提供返回该会话的入口。
- 如果历史记录没有可靠关联，展示任务或版本事实，但不猜测属于哪条会话。

**未分组对话进入项目**

- 不能静默修改原会话归属或假设已落盘。
- 用户选择项目后，清楚呈现接下来的关联方式，并保留原有对话；具体采用“迁入”还是“基于该对话创建项目会话”，应结合现有数据能力实现，避免丢失历史。

---

## 3. 对话内容如何划分

### 两边都要能看到的核心内容

| 内容 | 对话区 | 工作台侧栏 |
|---|---|---|
| 用户消息 | 完整显示 | 完整显示；很长时可展开 |
| AI 正式回复 | 完整显示 | 默认显示主要内容，可展开 |
| AI 追问与用户回答 | 完整显示 | 完整显示，支持直接回答 |
| 创作或修改请求 | 正文及完整关联信息 | 正文 + 紧凑目标引用 |
| 真实结果 | 结果卡及说明 | 精简结果卡 + 右侧定位入口 |
| 失败、中断、未完成 | 原因、后续操作 | 简明状态 + 重试或查看详情 |
| 附件、素材与参考 | 完整附件和引用信息 | 紧凑展示，可查看或移除未发送引用 |

这里的“AI 追问”必须来自真实结果或明确状态，不能仅根据“本轮没有新版本”就推断 AI 在追问。项目产品文档已经指出这两者不能混为一谈。

### 对话区重点展开的内容

- 较长的创意讨论、方案和解释；
- 多附件、多参考资料；
- 会话历史和项目下的其他会话；
- 本轮任务的详细记录入口；
- 较完整的交付物说明。

### 工作台重点展示的内容

- **本次作用对象**：项目、场景、版本、时间范围、画面区域等，仅展示真实存在且本次有效的内容；
- **当前工作进度**：等待、执行、需要处理、完成或失败；
- **结果与下一步**：查看结果、对比、继续修改；
- **与右侧的联动**：点击引用定位对应位置，点击结果打开对应版本。

### 不应默认放在消息流里的内容

- 逐条技术日志和底层调用参数；
- 被包装成“AI 思考过程”的虚构内容；
- 与用户当前决策无关的重复状态；
- 播放器每一次播放、暂停或拖动时间线等操作记录。

真实执行详情可以在执行记录中查看，聊天里只保留用户理解任务所需的摘要与入口。

---

## 4. 共享状态、界面状态和历史快照分开设计

这是整套方案中最容易出问题的地方。

| 状态 | 建议归属 | 两处行为 |
|---|---|---|
| 会话消息、附件、回复 | 会话事实 | 同会话两边一致，可恢复 |
| 任务状态和结果 | 任务事实 | 两边显示同一事实，布局可不同 |
| 消息当时引用的版本和目标 | 消息/任务快照 | 固定不变，历史可追溯 |
| 当前未发送草稿 | 项目 + 会话的草稿 | 同会话切换时延续，并标出目标 |
| 工作台当前查看版本 | 工作台状态 | 用于预览；不反向修改历史消息 |
| 当前时间点和选区 | 工作台临时状态 | 用户选择带入后成为草稿引用 |
| 面板展开、滚动位置 | 各界面状态 | 各自保留，无需跨界面相同 |
| 模型及权限 | 依据真实能力定义作用域 | 发送前展示实际值，不假装同步 |

### 草稿和目标需要特别处理

例如用户在工作台引用了 `v4 的 3–4 秒`，写了半句后切到对话区：

- 应保留正文和引用。
- 对话区仍应显示这条草稿带有 `v4 · 3–4 秒`。
- 用户可主动移除引用。
- 如果版本已失效或不再满足修改条件，发送前提示，不静默换成最新版本或扩大为整个项目。

反过来，在对话区写的普通草稿切到工作台时，**不应该自动附加当前选中的画面或时间范围**，避免用户没有意识到作用目标发生变化。

## 5. 明确“提问”和“执行修改”

目前工作台存在真实修改流程，所以产品上必须避免用户以为自己只是提问，实际却触发工程变更；也不能让用户提出明确修改后只收到普通回答。

建议每次请求都具备清楚的**操作意图**：

- **询问 / 讨论**：解释画面、讨论方案，不声称已经修改工程。
- **创作 / 修改**：对明确的项目和目标执行创作；展示任务状态和结果。
- **需要澄清**：目标不足或实际能力无法确认时，先追问或提示，而不是擅自扩大范围。

界面上不一定要放一个显眼的大模式切换器。可以先根据实际入口表达，例如：

- 从“对这个区域提意见”进入时，草稿明确带上区域目标。
- 用户在普通对话中提出问题时，不因为身处工作台就默认写工程。
- 若当前链路无法可靠区分提问和修改，应先在发送前提供清楚的选择，再逐步优化；不能只依赖模型猜测。

**这部分需要结合实际后端行为验证后实现**，尤其要检查当前工作台提交是否会对看似问答的内容进入修改流程。

## 6. 消息与右侧工作区的联动

用户之前提出“左侧切换时，右侧内容切到对应界面”，这个方向是合理的，但应避免任何左侧点击都强制打断用户正在看的画面。

建议规则：

| 左侧操作 | 右侧响应 |
|---|---|
| 打开普通对话 | 默认保留当前预览 |
| 点击消息里的画面或时间引用 | 定位到对应版本和时间；版本不可用时提示 |
| 点击创作要求 | 展示要求详情，或在右侧展示对应编辑区 |
| 点击执行记录 | 展示对应任务详情 |
| 点击版本或结果卡 | 切换到对应版本，可进入对比 |
| 点击修改审阅 | 展示该轮修改的目标、结果和对比入口 |
| 仅切换左侧页签 | 是否同步切换右侧，由页签明确指向的任务决定；不要无条件丢失当前预览状态 |

返回预览时，尽量恢复原来的版本、播放位置和选区。用户应始终知道右侧正在查看什么，以及它是否是最新版本。

## 7. 两处界面的布局建议

延续现有项目的浅色、简洁工具界面，以及你之前强调的“图标 + 悬浮说明”，但不能让重要状态完全依赖图标猜测。

### 对话区

建议保持宽敞的消息阅读体验：

```text
项目与会话列表  │  当前会话标题 / 操作
                │
                │  用户消息
                │  AI 回复与创作结果
                │  可展开的详情
                │
                │  附件 / 引用 / 输入框
```

- 项目和会话关系清楚，不在正文重复展示大量项目信息。
- 创作结果使用简洁结果卡，突出“查看作品”等实际可用操作。
- 复杂执行详情折叠，避免把聊天正文变成日志。
- 进入工作台的入口应保留当前项目与会话上下文。

### 工作台侧栏

```text
当前项目 / 当前会话
对话 · 创作要求 · 执行记录 · 版本 · 修改审阅

用户消息
AI 回复 / 追问
紧凑任务状态或结果卡

当前目标引用：v4 · 00:03–00:04  ×
输入框
附件、模型等操作
```

- 侧栏标题需要让用户知道正在看哪条会话，但不必占用过多垂直空间。
- 项目、版本和目标只在有实际意义时显示，避免反复堆标签。
- 用户消息、AI 消息与完整对话区保持同一设计语言。
- 常用操作用图标和悬浮注释；**当前目标、失败原因、等待状态等关键内容用可见文字**。
- 侧栏展开长消息时不能遮挡输入框；窄窗口优先保证可阅读和可操作。

## 8. 需要补齐的功能

### 必须优先补齐

1. **会话绑定与归属**
   - 工作台明确接收或解析项目内的会话身份。
   - 直接进入工作台时有可靠的恢复或创建规则。
   - 项目切换不带入无关消息。

2. **消息与创作任务关联**
   - 工作台发送的要求、真实 AI 回复、任务及结果能回到关联会话。
   - 普通对话和创作任务保留不同执行路径，但对外形成一致的记录。
   - 重试和恢复不产生重复消息或重复修改。

3. **任务与页面解耦**
   - 切换页面不把任务误标为完成。
   - 如果当前后端无法恢复流，至少保留真实状态，待任务结束后重新读取真实结果；不能显示伪造进度。
   - 断开、失败、取消分别表达。

4. **草稿与引用保护**
   - 同一会话切换页面时保留输入和附件。
   - 目标在发送前可见、可移除。
   - 版本失效时阻止错误提交或要求用户重新选择。

5. **历史与错误兼容**
   - 旧消息缺少项目、会话或版本关联时，如实标记；不猜测归属。
   - 已提交但执行结果不明确时，先查看真实任务状态，再提供重试，避免重复改工程。

### 完成基础后再补齐

6. **消息引用定位**：点击历史引用能回到对应版本和时间。
7. **任务结果联动**：从消息跳到版本、结果或审阅。
8. **完整对话跳转**：侧栏打开完整对话时，定位到同一会话，最好保留当前阅读位置或目标消息。
9. **搜索与历史发现**：优先放在完整对话区，侧栏提供入口即可。
10. **设置作用域梳理**：逐项核实模型、推理强度和权限是否被真实发送并生效，再决定跨界面如何同步。

### 暂不建议添加

- 给侧栏单独建立另一套会话系统；
- 自动把所有项目历史消息合并到一条工作台消息流；
- 因为屏幕有空间而增加与创作闭环无关的传统编辑器功能；
- 在没有真实执行数据时展示模拟进度、推理过程或版本结果；
- 在尚未明确时间线直接编辑边界前，强行把轨道操作接成真实剪辑。

## 9. 建议开发顺序与验收标准

| 阶段 | 解决的问题 | 验收重点 |
|---|---|---|
| **第一阶段：会话归属** | 项目、会话、侧栏之间的绑定 | 两个项目、多条会话来回切换，不串消息；直接进工作台有明确归属 |
| **第二阶段：消息闭环** | 两处消息和创作结果一致 | 任一处发送后，另一处能看到正确内容、真实状态和结果；刷新可恢复 |
| **第三阶段：草稿与目标** | 切换页面不丢输入、不改错目标 | 草稿、附件、版本、时间范围保留；失效目标有提示 |
| **第四阶段：工作台联动** | 从消息定位到作品和结果 | 引用、结果、任务和版本能正确跳转；不存在的历史目标不误导 |
| **第五阶段：界面整理** | 信息层次和阅读体验 | 窄侧栏长消息可读、关键状态清楚、无重复信息，符合项目视觉规范 |

还应覆盖四类异常场景：任务执行中切换界面、网络或本地服务中断、刷新后恢复、旧数据缺少关联。只有这些路径跑通，才能认定两处对话真正协同。

我的最终建议是：**保留对话区和工作台侧栏两种界面，但把项目、会话、任务、作品版本的关系作为底层主线重新梳理。** 先解决“这句话属于谁、作用于什么、产生了什么”，再优化消息样式和快捷入口，这样后续增加功能才不会继续产生两套互相矛盾的状态。
