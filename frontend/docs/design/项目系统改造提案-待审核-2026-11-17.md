# FengMotion 系统改造提案（待审核）

日期：2026-11-17。**用户已批准按顺序实施，本轮实现与验收见《系统改造交付与验收-2026-11-17.md》。以下保留原提案背景，不作为未实施状态。** 用户要求：本轮已同意的小范围工作收尾后，不再自行堆积零散美化；有价值的大改先说明问题、方案与影响，审核通过再执行。

## 判断

目前不需要再换一套全站视觉。最值得系统投入的是让现有「项目、会话、工作台、工作流、资源库」真正服务同一条持续创作过程。

现有基础值得保留：自然语言生成可运行Remotion工程、真实版本/渲染产物、画面范围引用、已接通的本机引擎、工作流React Flow画布、素材与参考/特效库的区分，以及用户已确认的界面。应在此之上逐段迁移，不重建全部应用。

本次判断基于当前源码与已有走查记录；未对所有模块执行真实任务。社区在导航中是占位，插件设置明确服务未接入，不能宣称它们已经具备可改造的完整业务。特效库另有开发者工作，涉及其源码/预览导入的改动需先核对归属。

## 方案一（推荐先做）：以项目为中心的持续创作空间

### 为什么值得大改

- 「我的创作」实际以会话列表和对话为主。用户找作品、判断哪个项目正在跑、最新可看哪版，需要进会话或切工作台后自行拼信息。
- 启动、发起任务、等结果、刷新恢复分散：`Conversation.tsx` 与 `Workbench.tsx` 各自组装并提交创作；`workflowService.ts` 又有另一条运行适配。虽有共享发送意图、草稿、轮次store，但执行控制仍重复。
- 核心创作任务已经在后端持久化（`CreationTaskStore`）；审阅意见、场景编辑文档/试片记录、工作流定义与运行则仍有浏览器存储。刷新/换浏览器/重装的保留边界不同，不适合让用户靠记忆分辨。

### 用户会看到什么

「我的创作」先帮助找到作品：真实封面、最近活动、正在执行/需要处理的事项、可继续动作。点项目后进入同一个创作空间，在对话和工作台之间切换，项目、会话、草稿、任务、结果保持同源。保留直接进入最近会话和工作台的快捷方式，不强迫每次走项目列表。

任务反馈只围绕用户关心的事实：在做什么、是否还在运行、失败在哪里、怎样继续、结果是哪一版。高级日志可展开，避免全屏说明或仪表盘。

### 内部需要改什么

1. 冻结通用创作请求/结果身份：项目、会话、用户消息、请求、目标版本、可选工作流定义版本；扩充已有持久任务体系，不先另造平行任务表。
2. 提取统一任务提交/订阅/恢复层：对话和工作台只收集输入、呈现结果；现有Prompt-first执行器作为适配保留。普通聊天继续独立，不能假装聊天停止能取消制作任务。
3. 为审阅、编辑文档/试片、工作流定义/运行设计本机项目级持久化。这里的「持久化」是本机数据库/项目文件，**不要求上云**。草稿和UI偏好可先保留浏览器缓存，但要明确可恢复范围。
4. 再改项目入口与任务反馈UI。数据与请求身份先稳定，避免只换列表外观又出现错版/错会话。

### 范围和迁移

规模：大；建议分批交付。先统一当前两处创作提交，再迁移一类持久记录，再做项目入口。每批可单独回归。

浏览器旧数据迁移需要记录来源和schema版本，导入成功后才标完成；冲突不覆盖；没有历史身份的记录明确旧记录，不补猜。保留回读/导出与回滚路径。先只读列出真实历史记录，不能把空后端列表当成没有用户数据。

### 必须验收

- 同一需求从对话或工作台提交，目标、引用、约束、引擎和幂等语义一致。
- 长任务中切页、刷新、进程重启后能回到原任务；结果未知时查原请求，不盲目重发。
- 消息、结论、产物只归属该项目该轮；保存/补存失败可见并能恢复。
- 用两项目两会话测试交错执行、响应乱序、版本更新、失败重试、历史回看。
- 已有版本和项目文件可继续打开，旧数据迁移可核对数量与内容。

## 方案二：让工作流成为真正可执行、可复用的工作方式

### 问题证据

React Flow编辑能力已完整保留，但实际执行器仍是混合适配：Prompt-first制作节点可调真实Agent/渲染，其他节点多为快照；Structured主要做产物/Gate评估。任意图可编辑不代表任意图已可执行。旧契约有定义/版本/运行/nodeIO方案，标记仍为「待评审」，不能直接当冻结规范上线。

### 改造目标

画布始终是核心。节点声明输入、输出、所需能力、真实执行器；连线决定数据传递；运行前指出不可执行节点或缺输入；执行中定位到节点，保留实际输入输出与错误。不同步骤的两条真实工作流均可复用同一工作台。

定义、版本、项目应用和单次运行要独立：编辑只影响后续运行；旧运行能回看当时定义；演示、状态评估和真实制作明确分开。不能把所有项目绑定固定三个节点或强制Gate。

### 建议起点与验收

规模：大；优先依赖方案一的任务基础。先支持少量当前真实节点并允许组合，拿一条确实不同的第二流程验证；扩展节点/插件SDK另案。必须验证单节点失败/重试、取消、缺输入、历史版本、执行中编辑及真实产物；不以纯前端模拟运行通过代替。

## 方案三：把资源库变成可追溯的创作输入

### 问题证据

素材、参考片、特效已有浏览与待发送路径，后端也有资源上下文构造和检索记录。但「加入待发送」「随请求送达」「Agent实际使用」「进入成片」是不同事实；资源库到任务/产物的使用证据尚不能笼统宣称齐全。待发送本地存储失败还存在反馈缺口。

### 用户会看到什么

三个库各保留自己的特点，分享统一的「用于画面/借鉴风格/声音/信息」语义；在输入框能看到实际带入内容；任务结果显示有证据的使用情况及来源。工作流节点可选择资源，项目资料能回到对应来源。

原始代码预览、仓库来源、依赖/许可与运行环境需要绑定版本；不以二次包装效果冒充原始预览，不为每张卡常驻高开销实时实例。此项与另一个AI的特效库工作有交集，实施前先核对其产物和范围。

规模：中到大；先统一引用模型和任务证据，再做跨库体验。验收需真实请求与工程/产物核对：同名文件、移动/删除源文件、只换素材重发、引用版本更新、预览失败、无匹配候选都要覆盖。

## 不建议现在优先做的事

- 全站再换主题或卡片体系：当前用户已确认很多局部，先保持一致。
- 同时做社区、插件市场、任意节点执行器：都是独立产品与技术范围，当前证据不足，也会稀释核心制作体验。
- 把所有资源库合成一个列表：它们分别承担真实文件、参考依据和实现方法，统一入口不应抹掉区别。
- 继续盲追单次故障测试：在方案一建立稳定隔离环境/可控传输测试后再补，不触碰用户正在使用的服务。

## 推荐审批方式

建议先审核**方案一的方向**。通过后先交付第一个实施批次：通用任务身份与双入口执行/恢复收拢，附接口、迁移、回归清单及界面草图；待范围确认再改核心代码。方案二、三先留后续，不一次性承诺全部重做。

需要用户决策的核心：是否认可「项目为持续创作主体、对话与工作台是同项目的两个视图、任务和产物有统一持久身份」这个方向，以及是否允许为此调整「我的创作」入口层级。保留已有快捷进入，不引入强制向导。
