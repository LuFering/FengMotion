# 特效技法库重新规划

2026-11-16。上一轮在卡片中直接运行原始场景及后台批量渲染的方案停止使用。代码工作区以 v0.1.1 标签为基线；本文件是新的规划，不代表新功能已实现或验收。

## 目标与现状

用户可以按仓库找到技法，卡片优先展示该技法的真实画面，点击后查看来源、代码与使用条件。v0.1.1 已有卡片、图片或视频预览及 GitHub 识别界面；导入界面的写入尚未接通。不能将识别结果当作已导入，也不能把示意动画标为原始效果。

## 新方案

1. **先盘点，再导入**：先对本地三个现有资源库做只读清单，记录仓库、版本、路径、技术栈、许可证及原仓库已有的图片/视频/可运行示例。先验证真实条目，再设计 GitHub 导入；不承诺所有仓库都能自动识别和运行。
2. **卡片默认轻量**：列表优先显示仓库原有的图片或已提供的视频封面；不在每张卡片加载 React、Three.js 或 Remotion 场景。卡片只展示效果、名称、来源与必要状态，保留清楚的筛选和仓库分组。没有真实预览则明确显示「暂无原始预览」，不绘制替代效果冒充原作。
3. **按需播放**：仅在用户主动悬停或聚焦后播放有现成视频的卡片，离开或移出视口即暂停；同时播放数量设上限，后台标签页暂停。触屏和键盘有明确播放入口。海报与视频加载、解码失败需可见反馈；不得影响列表滚动。
4. **原始代码预览独立验证**：点击详情后才允许进入隔离预览。先核实仓库自身的示例、资源与运行依赖；原始效果无法运行时说明缺少什么，不自行补造画面。外部仓库代码不能直接在主应用或后端进程执行；须先制定权限、网络、文件访问、资源配额和超时隔离，并审查许可证。独立进程本身不等同于安全沙箱。
5. **导入有明确边界**：粘贴 GitHub 仓库地址后先展示仓库身份、固定提交版本、识别到的候选、许可及无法识别的原因，由用户选择导入。持久化来源和代码路径，重复导入可识别，失败可重试，不覆盖其他仓库。先支持通过实测的仓库结构，其余如实标记不支持。

## 开发顺序与验收

- 第一批只优化现有卡片和列表资源消耗，用已有真实素材验证，不运行外部代码；记录卡片数量、CPU、内存、滚动与播放并发，比较修改前后。
- 第二批分别验证三个本地资源库的识别与原始预览覆盖率，列出能用、缺素材和需运行环境的条目；不因单个示例成功宣称整个仓库可用。
- 第三批完成按仓库导入、去重及错误恢复，用隔离测试数据验证，不改用户现有库。
- 最后才讨论可信隔离中的按需运行、生成缓存和更新策略；先测单个真实示例的画面正确性、耗时与资源峰值，再决定是否扩大。

验收应覆盖：真实画面与来源一致、无预览时如实提示、卡片多时仍可顺畅滚动、切页后资源释放、窄窗口、失败和重复导入。明确记录测试机器、卡片数量及实际数据；在没有测量前不承诺具体性能改善。
