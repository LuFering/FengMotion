# 执行隔离实测报告

> 探测日期：2026-11-04｜机器：Arch Linux，内核 7.2.9-arch1-1，systemd 262
> 方法：**只读探测**，未安装软件、未改系统配置。
> 原则：**「命令存在」不等于「隔离生效」** —— 每一项都用对照实验验证实际效果。

---

## 1. 结论先说

| 需求 | 实测结果 |
|---|---|
| 限制文件读写 | **bwrap 可用并生效**（只读根，写 /home 被拒） |
| 禁止联网 | **bwrap `--unshare-net` 生效**（隔离内 DNS 失败，宿主成功） |
| 进程隔离 / 杀树 | **bwrap `--unshare-pid` 生效**（PID 从 2 起） |
| 限制资源（内存） | **未生效**：`systemd-run -p MemoryMax=256M` 写进了 cgroup（`memory.max=268435456`），但进程仍成功占用 512MB |
| 隔离内跑 Remotion | **可以出片**（网络隔离 + 只读根下渲染成功，30 帧 640x360） |

**推荐方案：bwrap 作为第一版隔离手段**，它在本机同时满足文件、网络、进程三项且不干扰渲染。
资源限制这一项**当前不可靠**，需要单独解决或明确接受缺口。

## 2. 候选逐项实测

### 2.1 bubblewrap（bwrap 0.13.0，`/usr/bin/bwrap`）

Arch 上随 `bubblewrap` 包提供，Flatpak 也用同一套机制，属桌面 Linux 常见组件。

| 测试 | 命令要点 | 结果 |
|---|---|---|
| 基本执行 | `--ro-bind / / --dev /dev -- /bin/echo` | ✅ 输出 `bwrap-ok` |
| 文件只读 | `--ro-bind / /` 下 `touch /home/lufering/...` | ✅ `只读文件系统` 被拒 |
| 项目外可见 | 同上，`ls /home/lufering/ai-video-desktop` | ⚠️ **可读**（只读但可见） |
| 网络隔离 | `--unshare-net` 下 `getent hosts github.com` | ✅ 隔离内 exit=2，宿主 exit=0 |
| PID 隔离 | `--unshare-pid` 下 `echo $$` / `ps` | ✅ PID=2，进程数 5 |
| 私有 /tmp | `--tmpfs /tmp` | ✅ 真实 /tmp 被遮蔽（原文件读不到） |
| 渲染可用性 | 只读根 + `--bind` 工作目录 + `--unshare-net` + `TMPDIR` 可写 | ✅ **成功出片** |

**渲染成功的前置条件（实测得出）**：
- `TMPDIR` 必须指向可写目录（渲染脚本用 `os.tmpdir()` 建临时工作目录，否则 ENOENT）
- `HOME` 也需要可写（Remotion 缓存）
- 依赖目录与浏览器路径要能读到（只读挂载即可）

### 2.2 firejail

**未安装**。Arch 提供该包，但需 setuid root，属额外系统改动，不在第一版考虑范围。

### 2.3 Docker（29.9.0，守护进程可用）

本机有守护进程且在跑。但：
- 需要用户在机器上装并运行 Docker 守护进程 —— **不能作为所有用户机器的依赖**
- 镜像要额外分发（Remotion + 浏览器 + Node，数百 MB）
- 容器内跑 Chromium 还需额外参数

**结论：不作为默认方案**，可作为「愿意自己部署」的进阶选项。

### 2.4 systemd-run（systemd 262）

`--user --scope` 可启动，`-p MemoryMax` 会写入 cgroup，但**内存限制未真正生效**：
申请并真实写入 512MB 成功（限额 256MB）。可能与本机 cgroup 委派配置有关，未深查。

**结论：不能依赖它做资源限制。**

- `unshare` 存在（util-linux 2.42.4），但需手工拼 namespace，能力弱于 bwrap
- `nsjail` **未安装**
- `podman` **未安装**

## 3. 两个执行点

**只隔离渲染器 ≠ 整个 agent 闭环已隔离。** 两者必须分别处理。

### 3.1 创作 agent 调用工具、改文件、跑命令

这是**风险更高**的一环：agent 会读写任意文件、执行 shell。

**已实测的部分**：

| 测试 | 结果 |
|---|---|
| dsh 在 bwrap 内启动 | ✅ 输出版本号 `0.2.1-rc.2` |
| dsh 需要写 `~/.dsh` | ⚠️ **硬依赖**：只读挂载下报 `EROFS: read-only file system, open '<HOME>/.dsh/profiles/sdk/cordis.yml'` |
| `~/.dsh` 挂载可写副本 | ✅ 可启动（`--bind <副本> <HOME>/.dsh`） |
| 改 `HOME` 到别处 | ❌ 失败：dsh 仍按真实 HOME 找 `~/.dsh`，不能用重定向 HOME 的方式隔离配置 |

**关键约束（实测得出）**：dsh 必须能写 `~/.dsh`，所以隔离不能把整个 HOME 设成只读，
只能把 `~/.dsh` 单独挂成可写的**副本**（保护用户真实配置不被 agent 改坏）。

**未完成的部分（必须如实标出）**：
- **禁网下 dsh 能否完成一次真实模型调用 —— 未验证**。dsh 要访问模型 API，
  `--unshare-net` 下大概率不可用，但本轮没有拿到可信结论：
  手工发 `initialize` 报 `no adapter registered for provider "undefined"`，
  **而不加 bwrap 的对照也报同样错误**（说明是我手工调用缺参数，不是隔离导致）。
  要用真实后端链路才能判定，下一轮先做这件事。
- 把整个后端放进 bwrap 的尝试失败，原因是我的挂载组合有误
  （`--tmpfs /tmp` 遮蔽数据目录、Tomcat 需要可写临时目录），
  **不是隔离不可行**。结论：隔离内必须显式给后端与渲染准备可写的 TMPDIR，
  且不能让 tmpfs 遮蔽已 bind 的路径。

### 3.2 渲染时执行项目代码与浏览器

已实测可行（见 2.1 渲染一行），但要注意：
- agent 写的源码在渲染时**被执行**（Remotion 打包 → Chromium 运行），本质是跑不受信代码
- 隔离内渲染成功说明这条路可行
- 仍需可写的 TMPDIR/HOME

## 4. 需要如实说明的缺口

1. **资源限制不可靠**：内存无法有效限制，agent 或渲染写出死循环会拖垮机器。当前只有超时（杀进程树）兜底。
2. **文件「只读可见」**：`--ro-bind / /` 让代码能**读到**整个文件系统（含 SSH 密钥、其他项目）。第一版若要收紧，需改为只挂载必需路径（`/usr`、`/lib`、依赖目录、项目目录）。
3. **bwrap 不是全员可用**：需要系统装有 `bubblewrap` 且允许非特权 user namespace。本机 `unprivileged_userns_clone=1`，但不是所有发行版默认如此。
4. **本机找不到隔离手段时**：应用应如何提示 —— 需在实现时定义降级策略（见 §5）。

---

## 5. 建议的实现顺序

1. **先验证 dsh 能否在 bwrap 内工作**（含读写 ~/.dsh、起子进程）—— 不成立则 §3.1 方案作废，须先换思路
2. 收紧文件可见范围（只挂必需路径，而不是 `--ro-bind / /`）
3. 渲染与 agent 两条路径分别接 bwrap，并各自验证「隔离生效」而非「命令跑通」
4. 探测不到 bwrap 时：**明确降级并告知用户**（界面显示「当前无沙箱，agent 代码以你的用户权限运行」），而不是静默照跑或直接拒绝
5. 资源限制单独解决；在此之前，如实写「仅超时兜底，无内存上限」

## 6. 附：需要修正的既有验收结论

上一轮报告称安装态「不依赖系统 Node」。**这个结论不成立，已确认**：

- AppImage **不自带 Node**（`resources/` 下只有 `jre`、`backend`、`remotion`、`workflow-v5`）
- `dsh` 的 shebang 是 `#!/usr/bin/env node`，依赖系统 `node`
- 渲染同样用 `fengmotion.remotion.node`（默认裸命令 `node`）

所以上一轮只证明了「在本机 `/usr/bin/node` 存在的前提下跑通」。
**不能据此说跨机器可用**，也没证明跨机器安装、第二轮修改、视觉质量或安全隔离已完成。

真正验证需要二者之一：
- 在**没有系统 Node** 的隔离环境/干净机器里跑一遍
- 或随包提供 Node 并实测（Electron 自带 Node 运行时，但它是打包进 asar 的，
  能否直接当作 `node` 给 dsh 与渲染脚本用，需实验确认）
