## 1. 对话与会话（当前重点）

### 1.1 项目下的会话列表 ✅

```
GET /api/projects/{projectId}/chat-sessions?limit=50&cursor=
```

响应 `200`：

```json
{
  "items": [
    {
      "id": "c1",
      "projectId": "p1",
      "title": "未命名对话",
      "createdAt": "2026-11-01T14:22:31.000Z",
      "updatedAt": "2026-11-01T14:25:10.000Z",
      "messageCount": 4
    }
  ],
  "nextCursor": null
}
```

- 按最近更新倒序。`limit` 默认 50，范围 1~200。
- `nextCursor` 为 `null` 表示没有更多。

### 1.2 创建会话 ✅

```
POST /api/projects/{projectId}/chat-sessions
Content-Type: application/json

{ "projectId": "p1", "title": "可选，缺省生成「未命名对话」" }
```

响应 `201` + `ChatSession` 本体（**不套信封**）。

- `projectId` 必须与路径一致，否则 `400 validation_error`。

### 1.3 会话详情 ✅

```
GET /api/chat-sessions/{sessionId}
```

响应 `200` + `ChatSession`。不存在 `404 not_found`。

### 1.4 删除会话 ✅

```
DELETE /api/chat-sessions/{sessionId}
```

响应 `204`，无响应体。消息软删除，保留审计记录。

### 1.5 消息历史 ✅

```
GET /api/chat-sessions/{sessionId}/messages?limit=50&cursor=
```

响应 `200`：

```json
{
  "items": [
    {
      "id": "m1",
      "sessionId": "c1",
      "role": "user",
      "text": "把这段视频调亮一点",
      "taskId": "t1",                      // 仅当触发任务时出现
      "references": [...],                 // 无内容时不出现
      "attachments": [...],                // 无内容时不出现
      "createdAt": "2026-11-01T14:22:31.000Z"
    }
  ],
  "nextCursor": null
}
```

- 按时间**正序**返回。
- `system` 角色消息在服务层已过滤，不下发展示。
- `taskId` / `references` / `attachments` 缺省时不出现（不是 `null`）。

### 1.6 发送消息 ✅

```
POST /api/chat-sessions/{sessionId}/messages
Idempotency-Key: <可选，重试时带同一个值>
Content-Type: application/json

{
  "text": "把这段视频调亮一点",
  "references": [...],       // 可选
  "attachments": [...]       // 可选
}
```

响应 `202`（注意是 **202 不是 201**）：

```json
{ "message": { ...ChatMessage... }, "taskId": "t1" }
```

- `202` 表示「消息已保存，助手回复稍后由流产生」，**不是**回合结束。
- `taskId` 目前总是缺席（任务域未接入），字段保留。
- 带 `Idempotency-Key` 时重复请求返回同一条消息，不会写两条。

### 1.7 回复流（SSE） ✅

```
GET /api/chat-sessions/{sessionId}/stream
Accept: text/event-stream
Last-Event-ID: <可选；当前只校验格式，不做断点续读>
?prompt=<可选；不传则取该会话最后一条用户消息>
```

**请求参数说明**：常规流程是「先 `POST` 消息，再订阅流」——此时不用传 `prompt`，
服务端会取该会话最后一条用户消息，避免正文在两条请求间不一致。

**状态：已接入 DSH，实测可用。** 引擎不可用时仍返回 `503 agent_unavailable`（含原因）。

接入后前端会收到这些帧（**这是关键差异，请务必看**）：

```
event: heartbeat
data: {"type":"heartbeat"}

event: status
data: {"type":"status","phase":"thinking"}

event: status
data: {"type":"status","phase":"tool","name":"bash","label":"echo hi"}

event: completed
data: {"type":"completed","message":{"id":"m2","sessionId":"c1","role":"assistant","text":"好的，我来执行…","createdAt":"..."}}

event: end
data: {"type":"end"}

event: error
data: {"error":{"code":"agent_unavailable","message":"…","requestId":"req_…"}}
```

**✅ 已有 `delta` 帧（2026-11-03 接入）。** 通过随包的 `dsh-plugin` 订阅 DSH 内部的
`agent/assistant-stream`，把 token 级增量经 stderr 转发、再映射成 SSE `delta`。

帧序列现在是这样：

```
event: status    {"phase":"thinking"}
event: status    {"phase":"done"}
event: delta     {"messageId":"pending-xxx","delta":"你"}      ← 逐 token 到达
event: delta     {"messageId":"pending-xxx","delta":"好"}      ← 同一条消息，按序拼接
event: completed {"message":{...真实 id 与全文...}}
event: end
```

**前端要点**：

- `delta` 的 `messageId` 是**流内占位 ID**（`pending-<uuid>`），不是最终消息 ID。
- 拼接规则不变：同一 `messageId` 的 delta 按到达顺序拼接。
- **仍以 `completed` 为准**：它携带真实消息 ID 与全文，到达后覆盖已拼接文本。
- 实测 delta 分批到达（一次 5~15 帧，跨度约 0.6~0.9 秒），不是均匀逐字。

状态阶段值：

| phase | 含义 |
|---|---|
| `thinking` | Agent 正在推理/生成 |
| `tool` | 正在调用工具（附 `name`、`label`） |
| `done` | 本回合完成 |

**前端兼容性说明（已查验源码）**：现有 `src/services/api/streams.ts` 按 `payload.type` 分派，未知类型走 `default: return 'continue'` 静默跳过。所以新增 `status` / `heartbeat` 帧**不会破坏现有逻辑**，但要显示阶段进度需要主动加 `case 'status'` 分支。

现有分支已支持：`delta`、`completed`、`task`、`end`、`error`。其中 `completed` 分支独立处理，缺 `delta` 也不影响状态机——所以 delta 通道故障时后端可以退回只发 `completed`，不会把界面打坏。

## 5. DSH 能提供但暂不开放的数据（供你判断优先级）

以下数据 SDK 实测**能拿到**，但当前没有对应的对外接口。列出来是为了让你决定要不要加。

| 数据 | SDK 来源 | 建议接口 | 价值 |
|---|---|---|---|
| **工具调用详情** | `tool/call` 事件：`{callId, name, arguments}` | 并入 SSE 的 `status` 帧 | 高——用户能看到 Agent 在干什么 |
| **工具返回结果** | `tool/result` 事件：`{content, isError}` | 并入 SSE 的 `status` 帧 | 高 |
| **任务/作业状态** | `job/registered` / `job/settled`：`{jobId, kind, label, status, detail}` | `GET /api/chat-sessions/{id}/jobs` | 中——长命令进度 |
| **推理内容** | `assistant/message.data.message.content[type=reasoning]` | 并入 `completed` 帧的 `reasoning` 字段 | 中——可折叠展示「思考过程」 |
| **token 用量** | `assistant/message.data.usage`：`{inputTokens, outputTokens, totalTokens}` | 并入 `completed` 帧 | 中——显示消耗 |
| **会话标题自动生成** | `session/title` 事件：`{title, source}` | 自动更新 `ChatSession.title` | 高——会话列表更可读 |
| **模型/上下文信息** | `request/context`：`{provider, model, contextWindow}` | `GET /api/harnesses/{id}/models` | 低 |
| **子 Agent 生命周期** | `subagent.started` / `subagent.finished` | 暂不需要 | 低 |
| **token 级分片（事后）** | `assistant/message.data.stream.text-chunks` + `dt` | 不建议做 | 见 §6 |

## 6. 做不了的（必须如实标注）

### 6.1 ✅ token 级 `delta` 帧（已推翻旧结论，2026-11-03 重新判定）

> **原结论作废。** 本节原先写「DSH 内部 token 级流只走 Web 客户端的 Remote 通道，SDK/headless/ACP 都拿不到」，据此判定做不了。这个判定**只对「官方对外通道」成立，对「插件」不成立**。
>
> 现在的做法：随包一个自写 DSH 插件 `dsh-plugin/`，订阅 DSH 官方公开事件 `agent/assistant-stream`，把每帧下发到 stderr，后端读出来映射成 SSE `delta`。不改 DSH、不直连提供商、不额外开端口。
>
> 实测：一次回复 31 个 delta 帧，跨度 0.89 秒，前端按「只追加文本」直接拼接即可。细节见 `docs/harness集成与接口清单.md §11`。
>
> **注意**：`delta` 的 `messageId` 是流内占位值 `pending-<uuid>`，最终 ID 以 `completed` 为准。

### 6.2 ⚠️ 伪流式回放（不建议）

DSH 把 token 分片持久化在会话日志里（`text-chunks` + `dt` 时间间隔数组），SDK 会带过来。理论上可让前端按 `dt` 节奏重放，制造打字机效果。

**不建议**：这是伪流式，用户仍要等整段生成完，只会把等待拉得更长。若产品坚持要，需明确标注为「回放」。

### 6.3 ❌ 优雅取消

SDK 协议**没有** cancel 方法。官方原文：「abandon a turn by closing the runtime process」。所以取消 = 杀子进程。`capabilities.cancel` 标为 `process`。

### 6.4 ❌ 任务域相关接口

`task` 领域仍是包占位。以下都做不了：

- `GET /api/projects/{id}/tasks`（任务列表）
- `GET /api/tasks/{id}`（任务详情）
- `GET /api/tasks/{id}/events`（任务事件流）
- `POST /api/tasks/{id}/cancel` / `retry`

`SendChatMessageResponse.taskId` 字段保留但总是缺席。

### 6.5 ✅ 附件上传（2026-11-03 新增）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/uploads` | multipart，字段名 `file`；返回 `{fileId, name, size, kind, mimeType, sha256}` |

**为什么现在做**：前端 `src/services/api/assets.ts` 早就有完整的上传编排，但后端一直没有对应端点 —— 契约要求附件「先上传为 Asset、再以 fileId 引用」，没有这个端点时前端只能不带附件发消息。

**约束（已实测）**：

- 单文件 **64 MiB**，超限返回 413 `file_too_large`
- MIME 白名单：`image/*`、`video/*`、`audio/*`、`text/*`、`application/pdf`；其余返回 415 `unsupported_media_type`
- 空文件返回 400 `validation_error`
- **响应不含落盘路径**：只有 `fileId`，调用方凭它引用。路径一旦外泄，等于把文件系统形状交给调用方
- 落盘名为随机 UUID + 由 MIME 推导的扩展名；**原始文件名只做展示**，不参与路径拼接（防目录穿越）
- 落盘目录 `~/.fengmotion/uploads`（配置项 `fengmotion.upload-root`），与项目工作区分开

`kind` 取值：`image` / `video` / `audio` / `file`。

### 6.6 ❌ 素材、渲染、检查、工作流、特效库、参考片库

对应领域全是包占位，没有任何接口。前端这些页面只能继续用本地 Mock 或禁用。

## 7. 通用约定

### 错误信封

```json
{
  "error": {
    "code": "validation_error",
    "message": "…",
    "requestId": "req_xxx"
  }
}
```

已用的错误码（后端源码实测全集）：

| code | HTTP | 含义 |
|---|---|---|
| `validation_error` | 400 / 405 | 请求格式或参数无效 |
| `not_found` | 404 | 资源不存在 |
| `internal_error` | 500 | 服务内部错误 |
| `precondition_failed` | 409 | `If-Match` 版本不匹配 |
| `idempotency_conflict` | 409 | 幂等键冲突 |
| `capability_unavailable` | 422 | 能力未接入（如 `purge=true`） |
| `agent_unavailable` | 503 | Agent 未接入（SSE 现状） |

**前端应按 `code` 分支，不要按 `message` 匹配**（契约 README §2.4：错误码只增不改义）。

### 分页

`{items, nextCursor}`。`nextCursor` 为 `null` 表示结束；游标对客户端不透明，原样回传。

### 并发控制

`PATCH /api/projects/{id}` 需要 `If-Match: <etag>`，不匹配返回 `409`。

### CORS

白名单当前只有 `http://localhost:5173`、`http://localhost:4173`。**Electron 壳的 `fengmotion://app` 不在名单里**，会 403——需要后端加这一项。

## 8. 建议的前端改动顺序

1. **对话流**（1.7）——把「等回复」的 UI 改成消费 SSE：显示 `status` 阶段（思考中/调用工具），收到 `completed` 再显示正文，**不要做打字机动画**。
2. **引擎选择器**（4.1/4.2）——首页读 `/api/harnesses`，不要硬编码引擎名；按 `capabilities.streaming` 决定不显示打字机。
3. **会话标题**——若后端接入 `session/title`，会话列表标题会自己变好，前端无需改动，只需信任 `title` 字段。
4. **其余页面**——继续用 Mock，等对应领域落地。
