# 会话消息持久化

> ⚠️ **本文记录的是当时的规划与决策，其中「未实现」「包占位」「尚未接入」等说法已过期。**
> 现状请看 [`当前实现状态.md`](./当前实现状态.md)。本文保留原样以便追溯当时的取舍，
> 请勿据本文判断当前能力，也不要照本文重做已完成的模块。

本文说明 chat 模块的存储设计，以及它与参考实现 `dsh-session-persistence`（DeepSeek Harness 的会话持久化包）的取舍。它不是契约文档；对外字段与端点见 `../FengMotion-desktop/docs/contracts/agent.md`。

## 1. 需求

- 会话属于项目，消息属于会话；对话历史是项目数据，跨项目不可见。
- 一条消息要么完整落库，要么什么都不留下；失败不产生半截文本。
- 历史按时间正序分页；翻页过程中新消息不断追加，不能读到重复或漏读。
- 同一次发送的重试不能写出两条一样的消息。
- 删除会话不物理删除消息（契约要求保留审计记录）。

## 2. 采用的结构

```text
chat_sessions(id, project_id, title, created_at, updated_at, deleted_at)
chat_messages(id, session_id, seq, role, text, task_id,
              references_json, attachments_json, created_at)
chat_message_idempotency(key, request_hash, session_id, message_id, created_at)
```

三条关键决定：

**只追加 + 会话内单调序号。** `seq` 从 1 开始，按会话递增，是消息顺序的唯一依据。消息正文写入后不再修改；修改意图应该产生一条新消息，而不是覆盖旧记录。

**序号由写锁下的「读最大值 + 1」分配。** 读取最大序号和插入必须放在同一个事务里，并且先发一条空更新取得 SQLite 写锁（与会话创建时的做法相同，见 [事务与 SQLite 写锁](事务与SQLite写锁.md)）。`UNIQUE(session_id, seq)` 是最后一道保护：即使并发绕过了写锁，后写者也会失败而不是产生重复序号。

**结构化字段整列存 JSON。** `references` 与 `attachments` 的形状由契约定义（多态引用、附件元信息），服务端不解释其中字段，也不按它们做查询。整列存 JSON 比为一个暂不需要查询的多态结构建表更简单；将来要按引用反查时再拆表。

## 3. 与 dsh 的对照

`dsh-session-persistence` 把每个会话存成一份只追加的 JSONL 日志（默认带校验和的 Zstandard 帧），并暴露 `SessionPersistence` 这层与后端无关的接缝。可以直接借用的约定：

| dsh 的约定 | 本项目落地 | 说明 |
|---|---|---|
| 连续、单调的 `seq` | `chat_messages.seq` + 唯一约束 | 顺序与游标的唯一依据 |
| 只追加，已提交事件绝不重写 | 没有更新消息正文的 SQL | 修正用新消息表达 |
| flush 是持久性屏障 | 一次事务提交一条完整消息 | 失败即回滚，不产生半截消息 |
| 崩溃后不暴露撕裂尾部 | SQLite 事务保证 | 文件日志需要截断撕裂尾部，数据库不需要 |
| 单写者持有会话 | SQLite 单写事务 | 不同进程也互斥；未做压力测试 |
| 会话日志作为可读产物 | 暂不需要 | 若将来需要导出对话，可从表导出 JSONL |

没有照搬的部分：dsh 的流式增量落盘（一次回复按 delta 逐段持久化）在本项目暂不需要，因为 Agent 尚未接入；接入后若要支持「断线后恢复半截回复」，应新增增量表而不是修改现有消息行，避免破坏「消息不可变」的前提。

## 4. 翻页

游标是「本页最后一条消息的序号」的 URL 安全 Base64，客户端不解析。查询用 `seq > :afterSeq ORDER BY seq ASC LIMIT n+1`：

- 不用 `OFFSET`：消息持续追加时偏移量会漂移，翻页可能重复或漏读。
- 多取一条判断是否还有下一页，避免额外 `COUNT`。
- `system` 消息不下发展示，查询时直接过滤；它们仍占用序号，所以客户端看到的序号可能不连续，但顺序与游标不受影响。

## 5. 幂等

发送消息接受 `Idempotency-Key`，规则与项目创建一致：24 小时内同键同内容返回首次写入的那条消息；同键不同内容返回 `409 idempotency_conflict`。请求摘要绑定会话 ID，同一把键换到别的会话重放同样视为冲突。

幂等记录与消息插入在同一个事务里提交，因此不会出现「消息写入了但幂等键没记住」导致的重试重复。

## 6. 软删除

`DELETE /api/chat-sessions/{sessionId}` 只写 `chat_sessions.deleted_at`：详情、历史、发送都按 404 处理，会话不再出现在项目列表里，消息行与幂等记录保留。契约（agent.md §5）要求删除会话不取消任务、保留审计记录，这正对应软删除。

## 7. 当前限制

- **没有消息编辑与撤回**：只追加的设计决定；如需撤回，应记录一条撤回事件而不是删除行。
- **幂等记录不清理**：与项目创建相同，目前只在同键重试且过期时删除单条。数据量增大后需要定期清理任务。
- **并发未压测**：写锁 + 唯一约束的组合理论上正确，但没有用并发测试验证 SQLite 的等待与超时行为。
- **回复流未实现**：`GET /api/chat-sessions/{id}/stream` 当前返回 `503 agent_unavailable`，不发空流。接入 Agent 后按 `delta → completed → end` 推送，`Last-Event-ID` 用序号续读。
- **消息数用子查询派生**：会话列表每行做一次 `COUNT`，在单机 SQLite 与当前数据量下可以接受；数据量上来后应改为维护计数列或缓存。
