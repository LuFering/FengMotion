# 任务请求契约与修改执行流程

本文定下「用户提修改要求 → 任务系统 → 产出新视频」这条链路的分层边界。
先定接口与职责，再动代码；第一版支持范围有限，但范围必须明确写在下面。

## 1. 为什么要分两层

前端有两套任务数据表达：

| 契约 | 定义位置 | 表达的是 | 现状 |
|---|---|---|---|
| `TaskRequest` | `desktop/src/services/api/types` / `contracts.ts` | **用户修改意图**：改哪里、参考什么、保留什么 | 代码完整（含约 300 行 `validate.ts` 校验），但 `api/tasks.ts:create()` **无调用方** |
| `film.scenes` | `desktop/src/services/api/taskClient.ts` | **确定的渲染输入**：Remotion props | 已接通，已验收（见 `任务系统.md`） |

两者不是同一个东西，也不该合并：

- `film.scenes` 能表达「渲染这个片子」，能表达「把第 2 幕的字改成红色」，
  但**表达不了**「保留选区外的内容」「以这张参考图为目标」「只改第 3–5 秒」。
- `TaskRequest` 能表达意图，但**它不是视频数据**：
  `scope=selection` + `references=[preview/bbox]` 描述的是一次修改请求，
  里面没有一个像素、一句话幕文本。

**关键边界（本设计的核心约束）：**

> `TaskRequest` **不能**通过字段转换变成修改后的 `film.scenes`。
> 中间必须有一个执行器：读当前项目与场景 → 调用 AI 生成修改方案 →
> 校验方案 → 得到新的 `film.scenes` → 才交给渲染器。

把 `TaskRequest` 直接映射成 `film` 是错的，因为它缺失被修改对象的内容。
任何声称「加一层字段转换就能支持 AI 修改」的实现都应被拒绝。

## 2. 分层结构

```
POST /api/projects/{projectId}/tasks
        │
        ├── 请求体带 film.scenes ──────────────┐
        │      （无 kind 或 kind=render）      │
        │                                      ▼
        │                              RenderTaskRunner ──→ Remotion ──→ mp4
        │
        └── 请求体带 TaskRequest（kind≠render）─┐
                                               ▼
                                       ModifyTaskRunner
                                               │
                          ① 解析 scope / references / constraints
                          ② 读当前项目与目标场景（场景来源见 §5）
                          ③ 调 AI 生成修改方案（结构化 diff）
                          ④ 校验方案（字段白名单、越界、约束保持）
                          ⑤ 得到新的 film.scenes，落盘
                                               │
                                               ▼
                                  RenderTaskRunner（复用，不再新写一条渲染链路）
```

分流点就是 `TaskService.TaskRunner` 接口 —— 已存在，不需要新抽象。
`TaskController.create()` 目前只有一个 `render` 分支，改为按请求形状 + `kind` 分派。

## 3. 后端接收与报错的规则

**不允许静默丢弃任何字段或任务类型。** 具体规则：

### 3.1 任务类型支持矩阵

| kind | 第一版 | 行为 |
|---|---|---|
| `render` | 支持 | 走渲染 |
| `modify` | **部分支持**（见 §6） | 走修改执行流程 |
| `check` | 不支持 | `400 unsupported_task_kind` |
| `analyze` | 不支持 | `400 unsupported_task_kind` |
| `restore` | 不支持 | `400 unsupported_task_kind` |
| 未知 kind | 不支持 | `400 unsupported_task_kind` |

不支持的类型必须在**创建阶段**就报错，不能先入队再失败 ——
否则用户会看到一条「已接受」然后无意义地等。

### 3.2 字段支持矩阵

`TaskRequest` 的字段分三档：**解释**（真正实现语义）、**记录**（存下来但不解释）、
**拒绝**（无法保证语义正确就不接收）。

| 字段 | 档位 | 说明 |
|---|---|---|
| `kind` | 解释 | 决定分流 |
| `prompt` | 解释 | 用户原话，进修改执行流程的输入 |
| `scope` | 解释 | `project` 全片 / `scene` 指定场景 / `selection` 选区 |
| `sceneIds` | 解释 | `scope=scene` 时必填 |
| `references` | 解释 | 按 `role`/`kind` 解析目标与参考 |
| `constraints` | 部分解释 | 见 §3.3 |
| `attachments` | 记录 | 只存元信息，第一版不喂给模型 |
| `feedbackId` / `creativeBrief` / `workflowId` / `workflowRevision` | 记录 | 评审信封，随任务落库留痕，不参与执行 |

### 3.3 `constraints` 逐项说明

前端 `ModificationConstraints` 里有若干开关。第一版只有能真正保证语义的才标为「解释」：

| 约束 | 档位 | 第一版行为 |
|---|---|---|
| `limitToSelection` | 解释 | `true` 时把可改场景集限制在 `references` 指向的范围 |
| `preserveOutsideSelection` | 解释 | `true` 时校验结果只动了选区内场景，越过即失败 |
| `preserveCamera` / `preserveCaptions` / `reuseExistingComponents` | **记录** | 第一版 `film.scenes` 没有相机/字幕轨/组件概念，无法保证语义正确；接收入库但**在执行事件里显式声明未生效** |

**「记录但不生效」必须在任务事件里说明**，不能静默：
创建时追加一条 `warning` 类事件，正文写明哪几条约束本版未实现。
理由：用户勾了「保持镜头」而系统其实没管，比不接收这个字段更糟。

### 3.4 错误码

| 错误码 | HTTP | 触发 |
|---|---|---|
| `unsupported_task_kind` | 400 | kind 不在支持矩阵 |
| `unsupported_field` | 400 | 出现无法解释且不允许记录的字段 |
| `validation_error` | 400 | 结构不合法（沿用现有） |
| `scene_not_found` | 400 | `sceneIds` 指向的场景不存在 |
| `constraint_unsatisfied` | 422 | 修改结果违反 `preserveOutsideSelection` |
| `modify_plan_invalid` | 422 | AI 产出方案未通过校验 |

## 4. 修改执行流程的四个阶段

`ModifyTaskRunner` 内部严格分阶段，每个阶段都检查取消、都发进度事件：

### ① 解析（report 5%）
把 `scope` + `references` + `constraints` 解析成**可执行的修改范围**：
哪些场景可以改、哪些必须原样保留。解析不出明确范围就
`validation_error` 失败，而不是「猜一下用户的意图」。

### ② 读取（report 15%）
读项目当前场景数据。第一版场景来源见 §5。
读不到就是 `scene_not_found`。

### ③ 生成（report 20–70%）
把「当前场景 + 用户原话 + 修改范围」交给模型，要求产出**结构化修改方案**，
不是直接产出整份 `film.scenes`：

```json
{
  "edits": [
    { "sceneId": "s2", "field": "text", "from": "旧字幕", "to": "新字幕" }
  ]
}
```

理由：方案是**可校验、可展示、可拒绝**的中间产物。
直接让模型改整份 scenes，出错时无法判断它多改了哪里，也就无法保证
`preserveOutsideSelection`。

### ④ 校验 + 落盘（report 70–90%）
逐条检查 `edits`：

- `sceneId` 必须在允许修改的集合里；
- `field` 必须在白名单里（第一版见 §6）；
- `from` 必须与当前值一致（防止模型基于过时认知改错地方）；
- 应用后重新检查 `preserveOutsideSelection`。

任一不通过 → `modify_plan_invalid`，**原片不动**。
全部通过才写回项目场景，随后转交 `RenderTaskRunner` 渲染。

## 5. 第一版场景来源（必须先说清）

修改流程要「读当前场景」，但项目场景目前**没有权威来源**：
真实渲染路径的 `film.scenes` 是前端在请求里带来的，项目目录里没有 scenes 文件。

第一版采取的方式：**以前端携带的 `film` 为基线**。

即在 `TaskRequest` 之外，`modify` 请求**额外带一份当前 `film`** 作为基线，
修改流程在它之上应用 `edits`。

这不是理想方案 —— 理想是项目里有唯一权威场景文档，由后端读写。
但先有权威来源需要先定「场景存哪、谁写」，是独立一步。
**把这件事写在这里而不是藏起来**，是为了不让第一版看起来比实际完整。

明确的已知缺口：前端带来的基线与项目真实内容可能不一致，
第一版不做基线版本校验。

## 6. 第一版支持范围（必须遵守）

**能改的字段**（`edits.field` 白名单）：

| 字段 | 说明 |
|---|---|
| `scenes[].text` | 字幕/正文 |
| `scenes[].subtitle` | 副标题 |
| `scenes[].color` | 文字颜色 |
| `scenes[].backgroundColor` | 背景色 |
| `scenes[].durationSeconds` | 单幕时长 |

**不能改的**（第一版）：`width`/`height`/`fps`、增删场景、改 `backgroundImage`、
改动画与转场类型、任何相机/字幕轨/组件概念。

**`scope` 支持**：`project`、`scene` 支持；`selection` 第一版**降级为
`unsupported_field` 报错**（选区需要坐标到场景的映射，尚不存在）。
降级为报错而非静默按 `project` 处理 —— 后者会让用户以为只改了选区，其实改了全片。

## 7. 界面诚实性要求

这条是硬要求，不是体验优化：

- 请求被接收 ≠ 视频已改好。任务 `queued`/`running` 时界面必须显示进行中，
  不能出现「已完成」「已修改」字样。
- 首版未生效的约束、降级的 scope，必须能在任务详情里看到说明。
- 修改流程失败时原片**必须保持可用**，界面不能出现「视频已损坏」。

对应到实现的约束：`ModifyTaskRunner` 在校验通过前**不写回项目场景**。

## 10. 第 2 步实施结果

已完成并实测（后端运行在 18080，真实 HTTP 请求）：

| 场景 | 期望 | 实测 |
|---|---|---|
| `kind=check`/`analyze`/`restore`/未知 | 400 `unsupported_task_kind` | ✅ 一致 |
| `scope=selection` | 400 `unsupported_field` | ✅ 一致 |
| `modify` 缺 `film` 基线 | 400 `validation_error` | ✅ 一致 |
| `modify` + 未生效约束 | 受理，且 warning 事件排在 accepted 之后、执行之前 | ✅ 事件序 `accepted → warning → progress → error` |
| `modify` 执行 | 明确失败 `modify_not_implemented`，不假装成功 | ✅ 一致 |
| 旧渲染路径（无 kind + film.scenes） | 不受影响，仍能出片 | ✅ 6 秒 completed，产物 102730 字节，HTTP 200 |

事件种类新增 `warning`（`TaskEvent.KIND_WARNING`）。前端可据此把它显示成需要留意的提示。

### 实施中修掉的两个真实缺陷

**1. 合仓导致的渲染路径回归（阻断性）**

`backend/remotion/render.mjs` 里 `node_modules` 默认路径写死为
`<repo>/FengMotion-desktop/node_modules`，合仓后实际位置变成 `<repo>/desktop/node_modules`，
拼接结果成了 `FengMotion-desktop/FengMotion-desktop/node_modules`。

改为按 `desktop/node_modules` → `node_modules` 顺序探测存在性，都找不到时报出已尝试的路径。
写死一条路径的代价是「目录改名后得到一句 Cannot find module，而不是说清方向的错误」。

**2. 渲染子进程 stdout/stderr 串行读取死锁（阻断性）**

原实现先 `readAllBytes(stdout)` 再读 stderr。Remotion 把 Chromium 日志写进 stderr，
管道缓冲区（约 64KB）写满后子进程阻塞，stdout 永不关闭，父进程一直等 —— 互等到超时。

实测表现：**渲染实际已完成（progress 100%），但后端拿到空 stdout 并报「输出无法解析」**，
方向被指错。改为两个流并发读取。

顺带修正错误文案：空 stdout 现在报「渲染脚本没有输出结果」并带出 stderr，
而不是笼统的「无法解析」。
