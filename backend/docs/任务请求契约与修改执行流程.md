# 任务请求契约与修改执行流程

本文定下「用户提修改要求 → 任务系统 → 产出新视频」这条链路的分层边界。
先定接口与职责，再动代码；第一版支持范围有限，但范围必须明确写在下面。

## 1. 为什么要分两层

前端有两套任务数据表达：

| 契约 | 定义位置 | 表达的是 | 现状 |
|---|---|---|---|
| `TaskRequest` | `desktop/src/services/api/types` / `contracts.ts` | **用户修改意图**：改哪里、参考什么、保留什么 | 代码完整（含约 300 行 `validate.ts` 校验），但 `api/tasks.ts:create()` **无调用方** |
| `film.scenes` | `desktop/src/services/api/taskClient.ts` | **确定的渲染输入**：Remotion props | 已接通，已验收（见 `任务系统.md`） |

两者不是同一个东西，也不该合并：

- `film.scenes` 能表达「渲染这个片子」，能表达「把第 2 幕的字改成红色」，
  但**表达不了**「保留选区外的内容」「以这张参考图为目标」「只改第 3–5 秒」。
- `TaskRequest` 能表达意图，但**它不是视频数据**：
  `scope=selection` + `references=[preview/bbox]` 描述的是一次修改请求，
  里面没有一个像素、一句话幕文本。

**关键边界（本设计的核心约束）：**

> `TaskRequest` **不能**通过字段转换变成修改后的 `film.scenes`。
> 中间必须有一个执行器：读当前项目与场景 → 调用 AI 生成修改方案 →
> 校验方案 → 得到新的 `film.scenes` → 才交给渲染器。

把 `TaskRequest` 直接映射成 `film` 是错的，因为它缺失被修改对象的内容。
任何声称「加一层字段转换就能支持 AI 修改」的实现都应被拒绝。

## 2. 分层结构

```
POST /api/projects/{projectId}/tasks
        │
        ├── 请求体带 film.scenes ──────────────┐
        │      （无 kind 或 kind=render）      │
        │                                      ▼
        │                              RenderTaskRunner ──→ Remotion ──→ mp4
        │
        └── 请求体带 TaskRequest（kind≠render）─┐
                                               ▼
                                       ModifyTaskRunner
                                               │
                          ① 解析 scope / references / constraints
                          ② 读当前项目与目标场景（场景来源见 §5）
                          ③ 调 AI 生成修改方案（结构化 diff）
                          ④ 校验方案（字段白名单、越界、约束保持）
                          ⑤ 得到新的 film.scenes，落盘
                                               │
                                               ▼
                                  RenderTaskRunner（复用，不再新写一条渲染链路）
```

分流点就是 `TaskService.TaskRunner` 接口 —— 已存在，不需要新抽象。
`TaskController.create()` 目前只有一个 `render` 分支，改为按请求形状 + `kind` 分派。

## 3. 后端接收与报错的规则

**不允许静默丢弃任何字段或任务类型。** 具体规则：

### 3.1 任务类型支持矩阵

| kind | 第一版 | 行为 |
|---|---|---|
| `render` | 支持 | 走渲染 |
| `modify` | **部分支持**（见 §6） | 走修改执行流程 |
| `check` | 不支持 | `400 unsupported_task_kind` |
| `analyze` | 不支持 | `400 unsupported_task_kind` |
| `restore` | 不支持 | `400 unsupported_task_kind` |
| 未知 kind | 不支持 | `400 unsupported_task_kind` |

不支持的类型必须在**创建阶段**就报错，不能先入队再失败 ——
否则用户会看到一条「已接受」然后无意义地等。

### 3.2 字段支持矩阵

`TaskRequest` 的字段分三档：**解释**（真正实现语义）、**记录**（存下来但不解释）、
**拒绝**（无法保证语义正确就不接收）。

| 字段 | 档位 | 说明 |
|---|---|---|
| `kind` | 解释 | 决定分流 |
| `prompt` | 解释 | 用户原话，进修改执行流程的输入 |
| `scope` | 解释 | `project` 全片 / `scene` 指定场景 / `selection` 选区 |
| `sceneIds` | 解释 | `scope=scene` 时必填 |
| `references` | 解释 | 按 `role`/`kind` 解析目标与参考 |
| `constraints` | 部分解释 | 见 §3.3 |
| `attachments` | 记录 | 只存元信息，第一版不喂给模型 |
| `feedbackId` / `creativeBrief` / `workflowId` / `workflowRevision` | 记录 | 评审信封，随任务落库留痕，不参与执行 |

### 3.3 `constraints` 逐项说明

前端 `ModificationConstraints` 里有若干开关。第一版只有能真正保证语义的才标为「解释」：

| 约束 | 档位 | 第一版行为 |
|---|---|---|
| `limitToSelection` | 解释 | `true` 时把可改场景集限制在 `references` 指向的范围 |
| `preserveOutsideSelection` | 解释 | `true` 时校验结果只动了选区内场景，越过即失败 |
| `preserveCamera` / `preserveCaptions` / `reuseExistingComponents` | **记录** | 第一版 `film.scenes` 没有相机/字幕轨/组件概念，无法保证语义正确；接收入库但**在执行事件里显式声明未生效** |

**「记录但不生效」必须在任务事件里说明**，不能静默：
创建时追加一条 `warning` 类事件，正文写明哪几条约束本版未实现。
理由：用户勾了「保持镜头」而系统其实没管，比不接收这个字段更糟。

### 3.4 错误码

| 错误码 | HTTP | 触发 |
|---|---|---|
| `unsupported_task_kind` | 400 | kind 不在支持矩阵 |
| `unsupported_field` | 400 | 出现无法解释且不允许记录的字段 |
| `validation_error` | 400 | 结构不合法（沿用现有） |
| `scene_not_found` | 400 | `sceneIds` 指向的场景不存在 |
| `constraint_unsatisfied` | 422 | 修改结果违反 `preserveOutsideSelection` |
| `modify_plan_invalid` | 422 | AI 产出方案未通过校验 |

## 4. 修改执行流程的四个阶段

`ModifyTaskRunner` 内部严格分阶段，每个阶段都检查取消、都发进度事件：

### ① 解析（report 5%）
把 `scope` + `references` + `constraints` 解析成**可执行的修改范围**：
哪些场景可以改、哪些必须原样保留。解析不出明确范围就
`validation_error` 失败，而不是「猜一下用户的意图」。

### ② 读取（report 15%）
读项目当前场景数据。第一版场景来源见 §5。
读不到就是 `scene_not_found`。

### ③ 生成（report 20–70%）
把「当前场景 + 用户原话 + 修改范围」交给模型，要求产出**结构化修改方案**，
不是直接产出整份 `film.scenes`：

```json
{
  "edits": [
    { "sceneId": "s2", "field": "text", "from": "旧字幕", "to": "新字幕" }
  ]
}
```

理由：方案是**可校验、可展示、可拒绝**的中间产物。
直接让模型改整份 scenes，出错时无法判断它多改了哪里，也就无法保证
`preserveOutsideSelection`。

### ④ 校验 + 落盘（report 70–90%）
逐条检查 `edits`：

- `sceneId` 必须在允许修改的集合里；
- `field` 必须在白名单里（第一版见 §6）；
- `from` 必须与当前值一致（防止模型基于过时认知改错地方）；
- 应用后重新检查 `preserveOutsideSelection`。

任一不通过 → `modify_plan_invalid`，**原片不动**。
全部通过才写回项目场景，随后转交 `RenderTaskRunner` 渲染。

## 5. 场景来源：已改为服务端权威（第 4 步落地）

~~第一版以前端携带的 `film` 为基线~~ —— 该缺口已补上。

现在项目当前场景存在 `project_scenes` 表（单行一项目 + `version` 版本号），
修改任务一律**读服务端最新版本**作为基线。

`film` 字段退化为「初次导入的起点」：只有项目还没有任何场景时才需要，
一旦提交过就一律以库为准。这消除了一整类问题：
连续修改时第二次不会拿到第一次之前的旧快照，也就不会把第一次的改动抹掉。

## 6. 第一版支持范围（必须遵守）

**能改的字段**（`edits.field` 白名单）：

| 字段 | 说明 |
|---|---|
| `scenes[].text` | 字幕/正文 |
| `scenes[].subtitle` | 副标题 |
| `scenes[].color` | 文字颜色 |
| `scenes[].backgroundColor` | 背景色 |
| `scenes[].durationSeconds` | 单幕时长 |

**不能改的**（第一版）：`width`/`height`/`fps`、增删场景、改 `backgroundImage`、
改动画与转场类型、任何相机/字幕轨/组件概念。

**`scope` 支持**：`project`、`scene` 支持；`selection` 第一版**降级为
`unsupported_field` 报错**（选区需要坐标到场景的映射，尚不存在）。
降级为报错而非静默按 `project` 处理 —— 后者会让用户以为只改了选区，其实改了全片。

## 7. 界面诚实性要求

这条是硬要求，不是体验优化：

- 请求被接收 ≠ 视频已改好。任务 `queued`/`running` 时界面必须显示进行中，
  不能出现「已完成」「已修改」字样。
- 首版未生效的约束、降级的 scope，必须能在任务详情里看到说明。
- 修改流程失败时原片**必须保持可用**，界面不能出现「视频已损坏」。

对应到实现的约束：`ModifyTaskRunner` 在校验通过前**不写回项目场景**。

## 10. 第 2 步实施结果

已完成并实测（后端运行在 18080，真实 HTTP 请求）：

| 场景 | 期望 | 实测 |
|---|---|---|
| `kind=check`/`analyze`/`restore`/未知 | 400 `unsupported_task_kind` | ✅ 一致 |
| `scope=selection` | 400 `unsupported_field` | ✅ 一致 |
| `modify` 缺 `film` 基线 | 400 `validation_error` | ✅ 一致 |
| `modify` + 未生效约束 | 受理，且 warning 事件排在 accepted 之后、执行之前 | ✅ 事件序 `accepted → warning → progress → error` |
| `modify` 执行 | 明确失败 `modify_not_implemented`，不假装成功 | ✅ 一致 |
| 旧渲染路径（无 kind + film.scenes） | 不受影响，仍能出片 | ✅ 6 秒 completed，产物 102730 字节，HTTP 200 |

事件种类新增 `warning`（`TaskEvent.KIND_WARNING`）。前端可据此把它显示成需要留意的提示。

### 实施中修掉的两个真实缺陷

**1. 合仓导致的渲染路径回归（阻断性）**

`backend/remotion/render.mjs` 里 `node_modules` 默认路径写死为
`<repo>/FengMotion-desktop/node_modules`，合仓后实际位置变成 `<repo>/desktop/node_modules`，
拼接结果成了 `FengMotion-desktop/FengMotion-desktop/node_modules`。

改为按 `desktop/node_modules` → `node_modules` 顺序探测存在性，都找不到时报出已尝试的路径。
写死一条路径的代价是「目录改名后得到一句 Cannot find module，而不是说清方向的错误」。

**2. 渲染子进程 stdout/stderr 串行读取死锁（阻断性）**

原实现先 `readAllBytes(stdout)` 再读 stderr。Remotion 把 Chromium 日志写进 stderr，
管道缓冲区（约 64KB）写满后子进程阻塞，stdout 永不关闭，父进程一直等 —— 互等到超时。

实测表现：**渲染实际已完成（progress 100%），但后端拿到空 stdout 并报「输出无法解析」**，
方向被指错。改为两个流并发读取。

顺带修正错误文案：空 stdout 现在报「渲染脚本没有输出结果」并带出 stderr，
而不是笼统的「无法解析」。

### 尚未验证

- 未在打包后的桌面应用里复验渲染（本次只跑了独立后端进程）。
- 前端尚未接入 `modify` 结果展示；界面仍按演示标识处理。

## 11. 第 3 步实施结果

修改链路已端到端跑通并实测。

### 组成

| 类 | 职责 |
|---|---|
| `ModifyTaskRunner` | 四阶段编排：解析范围 → 读基线 → 生成方案 → 校验应用 → 渲染 |
| `MockModifyExecutor` | ③ 生成方案。第一版用确定性规则代替模型 |
| `ModifyPlanApplier` | ④ 校验并应用。模型说了不算，这里说了算 |

### 实测记录（后端 18080，真实 HTTP + 真实渲染）

一次成功的修改任务，事件序列：

```
accepted  queued    | 已接受，等待开始
progress  running   | 开始执行
progress  building  | 正在解析修改范围
progress  building  | 正在读取当前场景
progress  building  | 正在生成修改方案
progress  building  | 已生成 1 条修改
progress  building  | 正在校验修改方案
progress  building  | 校验通过，开始渲染
progress  building  | 渲染完成，正在登记产物
complete  completed | 已完成
```

产物 `renders/modify-1793726255968.mp4`，100317 字节，HTTP 200 可下载。

**内容正确性已核对**：抽帧比对，基线片首帧显示「原始文本」，
修改后首帧显示「已修改」，md5 不同。

失败路径：

| 场景 | 结果 |
|---|---|
| 要求解析不出目标值 | `failed` / `modify_plan_invalid`，**无产物**，原片未动 |
| `sceneIds` 不在基线里 | 400 `scene_not_found`（创建阶段） |
| `scope=selection` | 400 `unsupported_field`（创建阶段） |

### ④ 的四条校验

1. 场景必须在可改集合内
2. 字段必须在白名单内
3. `from` 必须与当前值一致 —— 防止模型基于过时认知改错地方
4. 应用后必须满足 `preserveOutsideSelection`

**任一不通过整份拒绝**，不做「跳过坏的、应用好的」：
那样用户会拿到半改的片子，且不知道哪条没生效。

### 实施中发现并修掉的问题

**1. `scene_not_found` 报得太晚（已修）**

初版只在执行器里校验 `sceneIds`，用户会先看到「已接受」再在后台失败。
已前移到 `TaskRequestGuard`，创建阶段直接 400。

**2. `ModifyPlanApplier` 漏了 `@Component`（已修）**

导致 Spring 上下文加载失败、`ProjectApiTest` 7 个用例全挂。
这是 `mvn -o test` 抓到的，不是靠肉眼。

### 第一版的真实边界

`MockModifyExecutor` **不是模型**，它只认两类说法：
「把文字改成 X」「文字/背景颜色改成 X」。其余一律报
`modify_plan_invalid` 而不是瞎猜。

换成真实模型时只需替换该类的 `generate` 实现，`ModifyTaskRunner`
与校验层不用改 —— 这正是先接确定性规则的目的。

### 尚未验证 / 未做

- 未接真实模型
- 未在打包后的桌面应用里复验
- 前端未接入，工作台仍走演示路径
- 基线仍由请求携带，不做版本校验（文档 §5 的缺口依旧存在）

## 12. 第 4 步：场景持久化与版本校验

### 为什么必须先做这一步

只靠前端传基线，第二次修改仍会拿第一次之前的旧场景，
把第一次的结果覆盖掉。这不是理论风险 —— 是「改文字 → 改背景色」这种最常见的
连续操作就会触发。

### 结构

`project_scenes` 表（单行一项目）：

| 列 | 用途 |
|---|---|
| `project_id` | 主键 |
| `version` | 版本号，只在条件更新成功时 +1 |
| `film_json` | 场景整份 JSON |
| `task_id` | 产生该版本的任务（可追溯） |
| `updated_at` | 写入时间 |

`tasks` 表加两列：`base_version`（基于哪一版）、`result_version`（提交成了哪一版）。
两者都为空表示与场景版本无关（如纯渲染）。

### 三条硬约束

**1. 条件更新必须是单条 SQL**

`UPDATE ... WHERE project_id = ? AND version = ?`。
先查版本再写会分成两条语句，两个并发任务可能都读到 version=2 然后都写成功，
后写的静默覆盖前者。首次写入用 `INSERT OR IGNORE`（主键冲突即表示已存在），
同样是原子判定。

**2. 渲染与提交分开**

渲染可能失败、可能被取消。只有渲染成功后才提交新场景。
否则用户会看到「场景已更新」但产物根本不存在。

**3. 冲突时不覆盖，但保留产物**

版本已变 → 抛 `scene_version_conflict`，`result_version` 保持为空，
消息里说明「视频文件保留在 renders/... 但未成为当前场景」。
产物留着（用户可能要），但绝不冒充已应用。

### 实测记录（后端 18080，真实渲染）

**连续两次修改**

| 任务 | 内容 | base→result | 结果 |
|---|---|---|---|
| 1 | 把文字改成「第一次改动」 | 0→1 | completed |
| 2 | 背景颜色改成 #4a0000（**不带 film**） | 1→2 | completed |

第二次产物的抽帧核对：画面文字仍是「第一次改动」，背景已变深红。
**两次改动都保留了** —— 这是本步的核心验收点。

**并发冲突**

同时提交 A、B，都基于版本 2：

| 任务 | 状态 | base→result |
|---|---|---|
| A | `failed` / `scene_version_conflict` | 2→null |
| B | `completed` | 2→3 |

库中版本从 2 只推进到 3，A 未覆盖任何东西。

**取消与失败**

| 场景 | 版本变化 | 当前版本归属 |
|---|---|---|
| 取消 | 3 → 3（不变） | 仍是 B |
| 失败（`modify_plan_invalid`） | 3 → 3（不变） | 仍是 B |

### 尚未做

- 没有版本列表、diff、回滚界面（本步只要版本号、条件更新、任务关联）
- `project_scenes` 目前没有对外接口，前端还读不到「当前场景」
- 执行器仍是确定性规则，**不是通用 AI 修改能力**

## 13. 第 5 步：场景读接口与 baseVersion 预检

### 读接口

```
GET /api/projects/{projectId}/scene
```

| 情况 | HTTP | 响应要点 |
|---|---|---|
| 项目不存在 | 404 | `not_found` |
| 项目存在但还没场景 | 200 | `initialized=false`、`version=0`、**`film=null`** |
| 有当前场景 | 200 | `initialized=true`、`version`、`film`、`taskId`、`updatedAt` |

```json
{
  "projectId": "...",
  "initialized": true,
  "version": 6,
  "film": { "width": 640, "height": 360, "fps": 30, "scenes": [...] },
  "taskId": "510cb61e-...",
  "updatedAt": "2026-11-03T17:40:52.853Z"
}
```

**「尚未初始化」必须是明确状态。** 返回一份空片子冒充已有内容，
会让用户以为项目里已经有片子，后续修改也会基于这个凭空产生的基线。
因此 `film` 明确为 `null`，而不是 `{}` 或默认场景。

### baseVersion 预检

修改请求可带 `baseVersion`（前端读取当前场景时拿到的版本号）。
与库中版本不一致 → 创建阶段直接 `409 scene_version_conflict`，不建任务。

**这是提前拦截，不是唯一防线**：预检通过后、提交前仍可能有别人提交，
那种情况由执行器的条件更新拦截。两层都必要 —— 预检省掉白跑的渲染，
条件更新才是真正保证不覆盖的那道。

不带 `baseVersion` 时跳过预检，行为与之前一致。

### 实测

| 场景 | 结果 |
|---|---|
| 读已有场景 | `version=6`，内容与 `taskId` 对应 |
| 项目不存在 | 404 `not_found` |
| 新建项目 | `initialized=false`、`film=null` |
| `baseVersion=1`（当前 3） | 409，**未创建任务** |
| `baseVersion=3`（当前 3） | 受理，完成后版本推进到 4 |

### 顺带修掉的一个缺陷

**冲突任务的产物路径丢失**

版本冲突时任务会 `failed`，但视频**已经渲染出来了**。
原实现把 `artifactPath` 留空，前端拿不到路径，用户会以为白跑了一场。

已改为：执行器在抛冲突前先 `registerArtifact(...)`，失败落库时一并写入，
并在 error 事件里带 `artifactApplied=false` 表明「有文件但未应用」。
实测冲突任务 `artifactPath=renders/modify-1793727651886.mp4`，HTTP 200、101553 字节可下载，
而当前场景仍归属成功的那次任务（`version=6`）。

这个修复不只服务冲突场景：任何「已产出文件后才失败」的任务都不再丢路径。

### 前端接入要点（下一步）

1. 打开工作台 → `GET .../scene`；`initialized=false` 时明确显示「还没有场景」，不要造一份
2. 提交修改 → 带上读到的 `version` 作为 `baseVersion`
3. 修改成功 → 重新读取场景
4. 收到 409 或 `scene_version_conflict` → 提示刷新，不要自动重试
5. 展示冲突任务的产物时要标注**「未应用到当前场景」**
