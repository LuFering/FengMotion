## 4. 修改能力的真实边界

### 4.1 可改字段（白名单，`ModifyPlanValidator.ALLOWED_FIELDS`）

`text`、`subtitle`、`color`、`backgroundColor`、`durationSeconds`

### 4.2 不支持（明确报错，不静默忽略）

图片替换、动画、转场、场景增删、选区（`scope=selection` → `unsupported_field`）。

**任一编辑项落在白名单外，整份方案拒绝**（错误码 `unsupported_field`），不做部分执行。
取消需求时输出空 `edits` 也视为失败（`modify_plan_invalid`），不会被当作「已完成」。

### 4.3 记录但不生效的约束

`preserveCamera`、`preserveCaptions`、`reuseExistingComponents` 只写入 `warning` 事件，
**不参与校验**。界面上对应开关已置灰，任务详情写「本次未提交保留约束」。
审阅区的需求与纠正只保存在本地，不自动传入真实修改；保留要求非空或带参考上下文时，真实修改会阻止提交并说明原因。成功受理的真实意见会记录在本地审阅区。已在隔离项目通过浏览器验证保留要求拦截、真实修改受理及意见记录；该次任务完成并把场景文字更新到版本 2。

### 4.4 版本历史与回退

| 能力 | 说明 |
|---|---|
| 快照 | 每次成功提交都在同一事务内写入该版本的完整 `film`，失败提交不留快照 |
| 列表 | `GET /api/projects/{id}/scene/versions`，新版本在前，含 prompt、变更摘要、产物路径 |
| 单版 | `GET /api/projects/{id}/scene/versions/{version}` |
| 回退 | `POST /api/projects/{id}/scene/versions/{version}/restore`，可带 `expectedVersion` |

**回退语义（重要）**：回退<strong>不是把版本号改回去</strong>，而是提交一个内容等于目标版本的新版本
（`source=restore`、`fromVersion=目标版本`）。因为 `version` 是条件更新的比较依据，
把它改小会让基于旧版本号的在途任务意外匹配成功并覆盖回退结果 —— 版本号必须单调递增。

因此：历史只增不减、回退本身可以被回退、回退后继续修改的基线是回退后的内容。

错误码：`noop_restore`（400，回退到当前版本）、`scene_version_conflict`（409，`expectedVersion` 已过期）、
`not_found`（404，版本或项目不存在）、`snapshot_corrupt`（422，快照数据不可用）。

**前端**：工作台输入框上方的「场景版本 vN」即入口，点击打开历史面板 ——
列出每版摘要与视频、标记当前版本与回退来源，回退需二次确认，
失败按 conflict / noop / corrupt / unreachable 分类给出下一步。
回退成功后自动重读当前场景并滚回列表顶部。

**尚未做**：回退不重新渲染视频，只还原场景数据；快照不清理（会一直增长）；
从旧库升级的项目没有历史快照，列表为空属正常。

## 5. 尚未启动的关键缺口

1. **工作流节点仍是演示**：创作上下文、项目工程渲染、agent 改工程都是真实的，
   但 `workflowService` 里的节点推进与产物快照仍是界面演示。
   真实出片走「agent 创作 / 渲染项目工程」这条独立入口，不走节点图。
2. **执行边界没有进程/网络隔离**：agent 写的代码以当前用户权限运行、可以联网。
   目前只有目录约束（入口不越界）、输出重定向、超时杀进程树。
   在真正的隔离手段到位之前，不能声称已隔离。
3. **版本历史清理策略**：快照只增不删，长期需要归档或上限策略。
3. **运行恢复的剩余边界**：新任务记录执行进程身份；启动时仅对同一 Linux 主机、启动周期、PID 命名空间和用户下，能够确认执行进程已退出的任务标记中断并追加事件。已有场景快照的版本与产物路径会保留。旧任务无身份、跨启动周期或身份无法确认时不会自动收尾；强杀后遗留的渲染子进程也不会自动清理。
5. **干净环境安装验证**：当前依赖系统 Node、Chrome、`dsh`，并带本机模型配置路径，
   第三方机器可安装性未验证。
6. **启动耗时**：AppImage 下后端启动实测约 30–100 秒，启动反馈与耗时需优化。

## 7. 项目工程渲染（已实测）

agent 把 Remotion 源码写进项目目录，后端构建并渲染：

```
项目/
  prompt.original.md       用户原文
  corrections.md           后续纠正
  lookdev-brief.md         视觉方向（按需）
  film.config.json         { entry, compositionId, width, height, fps }
  src/index.tsx            工程入口（Composition 注册）
  src/*.tsx                画面组件
  renders/                 产物
```

接口：`GET /workflow/film` 读工程状态，`POST /workflow/render` 渲染并提交版本。

- **共享运行时**：项目不装依赖，实测 `import 'react'` / `'remotion'` 可直接打包。
- **入口与 composition 从配置读**，缺失/越界/文件不存在都明确拒绝，不猜默认值。
- **版本记录源码指纹**：源文件清单 + 大小 + 修改时间、配置、依赖版本、渲染规格，
  与「修改」共用同一条版本链。
- **超时是配置**（`fengmotion.remotion.project-timeout-seconds`，默认 900 秒），
  超时杀整棵进程树并区分 `render_timeout` 与 `render_failed`。

**实测（开发态）**：真实需求 → 按 workflow-v5 写工程 → 渲染 31 秒出片 →
抽帧确认画面（球滚入、压扁、片名淡入）→ 提出修改（加呼吸 + 改名）→ 重渲得 v2，
抽帧确认两处都生效；失败路径返回 422 并带 esbuild 的行号级原因；
超时返回 504 且无残留子进程；入口越界被拒绝。

**实测（安装态 AppImage，0.1.0）**：同一链路在打包应用里跑通 ——
workflow-v5 可定位（`toolAvailable=true`）、工程渲染成功、抽帧确认画面正确。
首次渲染 140 秒（含 Remotion 自动下载 chrome-headless-shell），
第二次 33 秒（缓存复用）。**不依赖系统 Java / Chrome / Node。**

安装态踩到并修掉四个只在打包后出现的问题（开发态因为文件就在仓库里测不出来）：
渲染脚本漏打包、浏览器路径指向开发机、试图用 Electron 自身当浏览器会
重跑主进程抢端口而超时、以及 dsh 依赖 PATH 导致从桌面图标启动时找不到。

**agent 闭环的安装态实测**：以不含 `~/.local/bin` 的 PATH 启动（模拟桌面图标），
`harnesses` 返回 `available`，agent 自主建工程并出片（2 分 54 秒），抽帧确认画面正确。

## 8. 用户级安装（已实测）

```bash
cd desktop
npm run build && node scripts/build-electron.mjs && node scripts/prepare-backend-resources.mjs
node scripts/install-desktop.mjs     # 装到 ~/.local，无需 sudo
fengmotion                            # 或应用菜单搜索 FengMotion
```

装出的布局：`~/.local/opt/fengmotion-desktop/{electron,app/{main.cjs,dist,resources/{jre,backend,remotion}}}`。
主进程按 `main.cjs` 同级的 `resources/` 查找运行时（`main.ts` 的 `resourcesRoot` 三个分支）。

**实测结果**：自带 JRE 启动后端 4.48 秒就绪；渲染成功出片，抽帧确认内容正确。
不依赖系统 Java / Node / Chromium。

**边界**：Agent（DSH）仍用本机已配置的引擎，未随包分发。
