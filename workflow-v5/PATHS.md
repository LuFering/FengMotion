# v5 的两条创作路径（Prompt-first / Structured）

> 先明确：**v5 目前没有证明比高级提示词更好。**
> 它只证明了职责分层和工程校验更清楚；是否提升成片质量，必须用真实渲染做对照实验。
> 在对照结果出来之前，**Prompt-first 是默认路径**，Structured 只在任务确实受益时启用。

## 路径 A · Prompt-first（默认）

入口与项目模板见 `prompt-first/README.md`。

面向创意性强、视觉方向明确、需要高质量表达的短片。

```
原始创作提示词 + 素材/参考 + 用户确认的创作指令
        ↓
读原文：找视觉命题/视觉母题/关键画面
        ↓
核心视觉事件 + 输入事件覆盖 + 注意力路径 + 视觉机制
        ↓
设计系统：tokens + 视觉原语 + 视觉机制/镜头行为
        ↓
frame score：帧级时间编码（起止帧/时长/曲线/焦点/可见窗口）
        ↓
lookdev：2–3 个方向 + 媒介能力试片（只验证不可计算项）
        ↓
多镜头：film-plan（视觉弧 + 注意力/可见变化/动作/时间/镜头）
        ↓
实现：tokens + 原语组件 + 代码级不变量
        ↓
假设驱动验证（先写 2–4 个视觉假设，再选帧）→ 定位镜头/时间段 → 只改一个 → 重渲同段
        ↓
连续预览只用于运动/节奏/切点；技术 QA + 设计编码复查
```

- 高质量提示词是创作核心；原始输入、参考图、确认后的创作指令**持续可读**。
- 先做便宜的测试帧/风格帧，再写完整动画；如果测试帧仍像默认占位符，换方向/媒介，而不是继续堆代码。
- 多镜头写 `film-plan.md`：视觉弧 + 关键画面 + 关键动作/时间/镜头设计；不要求镜头 JSON。
- 字幕/旁白不是画面的解释器；如果去掉字幕看不懂事件，优先改画面/镜头。
- `shot-plan.json` / `animatic-review.json` 是复杂项目的可选工具，不是 Prompt-first 默认门禁。
- v5 的结构化数据在后台记录约束、资源、版本和问题，**不要求主创模型先填完所有中间文件**。
- 适用：氛围短片、风格短片、单一视觉概念、用户已给出明确方向。

## 路径 B · Structured（按需）

面向复杂、多场景、多人协作、品牌一致性要求高、需要严格复现的任务。

```
意图编译 → 导演方向 → 参考/关键画面
        ↓
动画蓝图 → 组件合同 → 执行规格
        ↓
原型验证（Prototype/Proof）→ 全片制作 → 技术检查 + 视觉判断
```

- 只有当任务确实需要可追溯交接、版本确认、组件复用和自动验收时，才走完整流程。
- 两条路径共用同一套执行工具、素材管理、渲染引擎和验收系统；不是两套制作后端。

## 哪些是硬约束，哪些只是建议

| 硬约束（防止错误/虚假完成） | 创作建议（启发，不是门禁） |
|---|---|
| 用户明确要求原文逐字保留 | 每条字幕一定对应一个独立场景 |
| 不得伪造参考、素材、组件、验收结果 | 每次必须提供三个视觉方向 |
| 真实文件、组件接口、Schema 正确 | 每场必须有规定数量的事件阶段 |
| 最终输出参数与已确认规格一致 | 所有场景必须采用特定运动机制/节奏曲线 |
| 预览与正式渲染使用一致输入/逻辑 | 所有视频都必须经过同样数量的评审节点 |
| 交付前完成必要技术检查与视觉判断 | 只有某种固定叙事结构才算合格 |

具体片型（UI 演示、品牌片等）可以有更具体的节奏/字体/布局规范，但应由片型和用户目标决定，不应用到所有作品。

## 关键画面：结构示意 ≠ Look-dev

Gate A 的样稿必须分两类：

- **结构示意**：SVG/色块/占位形状，只验证构图、空间关系、焦点。
- **Look-dev 样稿**：真实参考帧、摄影素材、生成图像或高质量拼贴，验证材质、光线、色彩、焦点和视觉识别度。

写实方向（naturalistic / 依赖 video-footage、真实材质、自然光）**不能只靠结构示意通过 Gate A**；
必须至少有一张 Look-dev 样稿，证明高质量素材路线可行。结构示意可以讨论布局，但不能证明最终写实质感。

## Prototype / Proof 通路

当前候选组件/资产在正式 preflight 被阻塞，但验证它们又需要实际渲染。为此分两级：

- **sketch 模式**：允许自由探索和渲染，明确非交付；不要求 Gate/完整依赖。
- **prototype 模式**：允许 candidate 组件/资产、零外部资产、只验证选中场景；不要求 Gate A/B、正式批准或全片资产；要求文件真实存在、规格合法、build manifest。
- **production 模式**：要求 Gate A/B/C 通过、组件/资产 available、证明与当前 spec/config 哈希一致，才允许全片预览与正式成片。

原型通过后，组件/资产才从 candidate 转为 available；不能为了过门提前改状态。

## 保留原始创作上下文

结构化数据是约束账本，不是创意的唯一载体。每次迭代必须允许主创模型重新阅读：

- 原始用户输入与高级提示词；
- 用户提供的参考图/素材；
- 已确认的视觉方向与关键画面；
- 最近一次真实渲染结果。

`intent-brief.json` 负责事实、原文、未决事项；`visual-direction.json` 稳定已确认的视觉语言；
动画蓝图/scene.spec 负责实现与验收。它们不能替代原始上下文。

## 什么时候用哪条路径

- 默认：Prompt-first。
- 仅在以下情况启用 Structured：多场景/多人协作、品牌一致性、需要复用组件、需要严格复现、需要自动验收与版本追溯。
- 是否把 Structured 变成默认，取决于 `EVALUATION.md` 的对照实验结果；没有稳定超过 Prompt-first，就不改默认。
