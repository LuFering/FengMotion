# Prompt-first（默认创作路径）

> 用完整提示词、参考和素材直接创作 Remotion；默认流程不做「先填完整结构化文件再开工」。
> 目标是让模型先看见画面，再写代码；不是让模型通过门禁。
> 只有在多人协作、客户交付、严格复现、素材/授权风险高时，才升级 Structured 路径（见 `../PATHS.md`）。

## 项目目录

```text
<project-dir>/
  prompt.original.md     # 用户原始输入，逐字保存，不摘要、不改写
  corrections.md         # 用户后续纠正，追加，不覆盖原文
  decisions.md           # 关键决定，可 supersede
  lookdev-brief.md       # 视觉转译工作稿：视觉命题/参考/方向/色版/光/材质/镜头/运动
  quality-bar.md         # 看片问题：用来定位「哪里 generic、下一轮改什么」
  film-plan.md           # 多镜头可选：一页导演处理，不是审批表
  references/            # 参考图/视频/链接清单
  qa/
    passes/NN/           # 每轮渲染、抽帧、观察记录
  project.json
```

`shot-plan.json`、`animatic-review.json`、`scene.spec` 等仍可用于复杂/Structured 项目，但**不是默认 Prompt-first 的前置条件**。

## 开始

```bash
cd workflow-v5/prompt-first
node tools/init-project.mjs <project-dir> --film-id <id> --prompt-file <原始提示词.md>
```

- `prompt.original.md` 逐字复制，不做摘要；已存在时默认不覆盖。
- 之后把用户纠正追加到 `corrections.md`，关键决定写入 `decisions.md`。
- 先写 `lookdev-brief.md`：视觉命题、参考、2–3 个方向、色版/光/材质/镜头/运动。
- 做 1–3 张便宜测试帧，并排比较方向；如果还是默认占位符，换方向/媒介。
- 多镜头写 `film-plan.md`（一页导演处理），不需要先写镜头 JSON。
- 没有必须通过的 animatic/静帧门；测试帧和 animatic 是判断工具，不是审批门。

## 上下文优先级

1. 用户最新明确纠正/新要求。
2. 用户明确标记的硬要求（原文/参考/必须保留内容）。
3. 用户已确认的决定。
4. 当前有效的模型决定（`decisions.md` 中 `active`）。
5. 模型推断与临时假设。

原文不能被摘要替代。上下文变长时，完整原文留在项目文件中，创作阶段注入相关原句、纠正、硬约束与最近决定。

## 创作闭环（画面先行）

```text
原文/参考/素材
  → 读原文，找视觉命题/视觉母题
  → 核心视觉事件 + 输入事件覆盖 + 注意力路径 + 视觉机制
  → 设计系统：tokens + 视觉原语 + 视觉机制/镜头行为
  → frame score：帧级时间编码（起止帧/时长/曲线/焦点/可见窗口）
  → lookdev：1 个主方向（不确定才 2–3 个）+ 媒介能力试片
  → 多镜头：film-plan（视觉弧 + 视觉机制/镜头差异/可见变化/帧表）
  → 实现：tokens + 原语组件 + 代码级不变量
  → 假设驱动验证 → 定位镜头/时间段 → 只改一个 → 重渲同段
  → Finishing Pass：首版整体看镜头差异/视觉密度/时间表现/节奏收束
  → 只修最影响成片的一个问题 → 局部重渲 → 最终整体回看
  → 没有播放条件：2–3 秒短运动预览 + 密集时间序列 + 人审，记录未完整审片
  → 可选：能力检索（风格/镜头卡/原语）→ 只取 1–2 个候选，不套皮肤
  → 技术 QA + 设计编码复查（不是通过/失败门禁）
```

### 视觉转译（这是重点）

模型默认会写「暗背景 + 渐变光 + 几何图形」，因为没有先决定画面。Prompt-first 要做的是：

1. **原文 → 视觉命题**：这段文字里，什么是只有画面能表达的？
2. **参考 → 视觉系统**：借什么构图/光/色/材质/镜头/运动，不借什么。
3. **方向**：方向明确时只做一个主方向；只有真正不确定时才并排看 2–3 个。
4. **测试帧**：只验证不可计算项（材质/光/合成/落位）；不做大批量抽帧，不用截图代替设计推理。
5. **选定方向**：写清为什么、放弃了什么、风险是什么。
6. **再实现**：先建立色板/光/材质/镜头规则，再写镜头；不要每镜临时画几何。

### 用代码推理画面

主路径不是“渲一堆帧找感觉”，而是先把画面写成代码可推理的结构：

- **tokens**：颜色角色、字号/行宽、网格/边距、时长、缓动、相机、光；
- **视觉原语**：Stage / Light / Subject / Camera / Liquid / Text 等组件，接受 tokens，不写死魔数；
- **frame score**：每个关键动作/相机/焦点写成起止帧、时长、曲线、可见窗口；有 BPM 先算 beat→frame；
- **视觉机制**：一句话说明什么可见的东西贯穿全片，镜头如何跟随/服务它；
- **代码级不变量**：主体/文字在安全区、状态连续、时间边界在帧内；
- **渲染只验证不可计算项**：材质、光、合成、遮挡、文字实际落位；先写 2–4 个视觉假设，再选帧，不固定数量。
- 代码骨架见 `templates/visual-encoding.ts`：tokens、Keyframe、`at()`、`checkShot()`，复制到项目后按需扩展。

如果设计只能写成形容词，不能写成 token/帧/参数/关系，先不要写代码，也不要靠大批量抽帧去“找感觉”。

### 从视觉命题到注意力

视觉命题不是一句氛围文案；它要落到**核心视觉事件**和**注意力路径**：

- 观众真正看到“发生变化”的是什么？
- 第一眼 → 发现/靠近 → 变化/接触 → 高潮 → 余像，分别是什么？
- 每个镜头让观众“从看 A 变成看 B”，还是只是换了一个物体？
- 哪个瞬间是视觉高潮？最后留下什么画面？
- 原文/用户要求的输入事件是否都被覆盖？删掉/背景化的事件由什么承担？
- 哪些元素服务这个事件，哪些只是氛围/装饰；保留装饰要有理由。
- 这个事件在画面上具体改变了什么？不能只写“光渐变/液体动画/粒子飘动”。

如果核心事件说不清，先不要选风格；否则容易做成有质感的静物展示。

### 从风格到动作

Lookdev 只解决“长什么样”，不能证明“怎么动”。继续往下写：

- 关键动作的起始 → 中间 → 结束；
- 路径、速度、停顿、先发生/后发生；
- 相机为什么动、跟谁、何时停；
- 光/阴影/液体/粒子/材质如何响应动作；
- 下一镜继承什么状态；
- 选 1–3 个最难动作，先做 3–5 秒局部预览，再扩到全片；
- 如果纸片/几何无法表达液体/机械/形变，换表现方式或媒介，不要硬做成图标；
- 先做 3–5 秒“媒介能力试片”，再决定要不要写完整片。

### 字幕/旁白

- 字幕/旁白不是画面的解释器；它们应该补充画面不能说的，而不是复述画面。
- 如果去掉字幕就看不懂事件，优先改画面/镜头，而不是加更多字幕。
- 多镜头可以让字幕跨镜头；不需要为了字幕换行新建镜头。

### 成片优先

- 文档写到足够开始写代码为止，不为补全流程牺牲实现/渲染。
- 复杂片至少 2–3 轮整片渲染 + targeted 修复。
- 工作流是能力包，不是审批链；与成片冲突时优先成片。

## 最小充分产物

设计只做到“足够写代码”：

- 视觉命题 + 视觉机制；
- 1 个主方向 + 关键参考；
- 镜头差异/视觉节拍；
- tokens/原语/frame score；
- 高风险动作试片；
- 最终问题清单。

复杂任务才展开完整模板；方向明确时不为了比较而比较。文档不是进度，渲染/审片/打磨才是。

## 可选能力检索

如果本地接入了 `workflow-v5/capabilities/index.json`：

- 有明确风格需求 → lemo-opuscar 取 1 个 `STYLE.md`+`DIRECTOR.md` 作参考；
- 有具体镜头运动需求 → video-shotcraft 取 1–3 张卡 + demo 源码；
- 需要具体原语 → remotion-scenes 复制 1–2 个组件并重新蒙皮。

只借结构/运动/参数，不照抄整套皮肤；不匹配就不用，不为了用资产而用。记录来源/license 到 decisions。

## 创作习惯

这些是习惯，不是硬门禁：

1. 先做便宜的图，再写贵的代码。
2. 先解决最难的动作，再做容易的镜头。
3. 一次只改一个最大的视觉问题。
4. 计划服务于画面；如果文档开始替代画面判断，删掉文档。
5. 参考是借结构/光/材质/构图，不是照抄表皮。
6. 复用已经成立的视觉系统，不要每轮重新决定风格。
7. 允许实验；实验失败就换方向，不要用更多装饰救场。
8. 安静/留白可以保留，但必须是有意的节奏。

### 技术/真实性底线

这些必须过：

- 不伪造参考、素材、组件、渲染、用户批准或审片结果；
- 不把占位渲染当最终交付；`sketch`/`prototype` 明确标记非交付；
- 用户要求逐字保留的内容不能遗漏/改写；
- 技术错误（JSON、帧窗口、fps/宽高/帧数、资源、输出损坏）必须修；
- 没有实际渲染证据，不声称「效果已改善」；只看静帧/接触表时，记录「未做连续播放审片」。

## 高级工具（可选，不是默认门禁）

复杂/Structured 项目可以按需使用：

- `shot-plan.json` + `validate-shot-plan.mjs`：机器可读镜头/事件/字幕/状态交接；
- `animatic-review.json` + `validate-animatic-review.mjs`：记录 animatic 完整播放/无字幕测试/返工状态；
- `cut-evidence.mjs`：切点前后帧 + freeze/black 定位；
- `animation/`、`execution/` 下的蓝图、scene.spec、组件合同。

这些工具用于**复杂项目的协作和追溯**，不是 Prompt-first 的创作前提，也不应用来替代画面判断。

## 什么时候升级 Structured

- 多人/多 agent 并行，需要稳定接口。
- 客户/品牌/法律要求，需要显式审批与追溯。
- 长片、多场景、复杂素材合成，前期规划能显著降低返工。
- 高风险素材、真实人物、写实合成、授权/外部依赖。
- 需要复现、回滚、审计。

升级不是默认；阈值只是建议，最终由任务判断/用户选择。
