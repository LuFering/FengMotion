# 协作分工与文档体系

日期：2026-10-22 · 状态：已采纳

## 背景与问题

- 仓库缺少成体系的开发文档：无开发规范、无进度与更新日志、无前后端协议文档，目录职责靠口头约定，新参与者（含 AI）无从对齐。
- 维护者不擅长前端，此前需不断就前端实现细节与 AI 沟通，精力消耗过大。
- 协作方 token 资源不对称：本地 AI 充足，远程协作者有限。

## 决定

1. **分工 v2**：维护者主责后端与 Agent 集成、方向裁决、验收与合并；协作者（muse-lufering）负责前端的设计、文档、测试与审核，产出可直接施工的规格与验收结论；本地 AI 作为执行主力，按规格实现前端与后端代码，提交走 PR 并接受审核。一行级小修协作者可直接在 PR 分支修正。
2. **文档体系**：根目录设 ARCHITECTURE.md（代码地图）与 CONTRIBUTING.md（参与要点）；开发文档集中于 `docs/dev/`（规范、进度、更新日志、前后端协议、决策记录）；`.github/` 设 PR 与 Issue 模板。参照开源项目 Yuxi（xerrors/Yuxi）的文档组织方式（根目录三件套 + docs 分区 + 决策记录 + 验证状态词），按本仓库规模裁剪，不照搬其复杂治理机制。
3. **流程**：功能分支 + PR 合入 main，不直推；中文 Conventional Commits；验证结论使用状态词（已通过/已查验/未执行/推断），未验证不写成通过。

## 替代项与取舍

- 协作者全量实现前端：判断密度低、出量大，不符合 token 经济性，弃。
- 文档继续散落在 `docs/design/` 与口头约定：新参与者对齐成本高、易漂移，弃。
- 照搬 Yuxi 的完整治理（证据矩阵、决策归档分级等）：对当前单人维护规模过重，只取其骨架（目录组织、模板、状态词、决策留痕），弃繁就简。

## 后果

- 前端问题收敛为「规格 → 实现 PR → 审核+实测 → 合并」闭环，不外溢占用维护者精力。
- 文档成为事实来源之一：目录、进度、契约变化必须同步更新文档（已写入开发规范第 7 节）。
- 协作者的产出以文档与结论为主，实现产能依赖本地 AI 的排期。

## 验证

- 本记录与文档体系以 PR 形式提交，维护者合并即视为采纳生效。
- 首个完整闭环（01 期规格 → 实现 → 审核 → 合并）跑通后，在开发进度中复盘本分工是否需要调整。
