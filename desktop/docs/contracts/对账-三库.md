### 1.2 A. 审核状态：保留五值（已裁决）

`reviewStatus` 扩为 **`none | pending | needs_review | approved | rejected`**。

**必须同时写清语义与转换，不能只加枚举：**

| 值 | 含义 | 初始值 | 允许的下一状态 |
|---|---|---|---|
| `none` | 从未提审 | **新导入素材的初始值** | → `pending` |
| `pending` | 已提审，未出结论 | — | → `approved` / `rejected` / `needs_review` |
| `needs_review` | 审过，结论是「需要修改后再提」 | — | → `pending`（修订后重新提审） / `rejected` |
| `approved` | 审核通过 | — | → `needs_review`（发现问题回溯） |
| `rejected` | 审核不通过，不再采用 | — | → `pending`（修订后重提） |

- `needs_review` 与 `pending` 的区别：**`pending` 是「还没审」，`needs_review` 是「审了、要求改」**。二者不可互相压平。
- `rejected` 与 `needs_review` 的区别：`rejected` 是终局否定，`needs_review` 是待修订。
- **授权状态 `licenseStatus` 继续完全独立**，任何审核转换都不改授权。
- 非法转换（如 `none` → `approved`）必须 4xx 或后端拒绝，与 `README.md §4.5` 的非法组合规则一致。

### 1.3 B. 内置 vs 演示是两个维度（已裁决）

**不能用「文件是否真实存在」判断是不是演示数据。** 拆成两个正交维度：

| 维度 | 字段 | 取值 | 说明 |
|---|---|---|---|
| 文件来源 | `sourceType` | `builtin` / `imported` / `generated` / `sample` | 文件从哪来 |
| 是否演示 | `demo?: true` | 有 / 无 | 该条是否演示用途 |

- 随应用分发的**真实文件** → `sourceType=builtin`；若同时是演示用途，**可以**再标 `demo: true`。
- `sourceType=sample` 只留给**内容本身是编造/占位**的条目。
- **红线：演示条目的 `refs` 不得被包装成真实用户项目关系。** 演示引用只能指向演示项目，且需在响应中可区分。

### 1.4 C. 文件导入：第一版复制入库（已裁决）

- 第一版**默认复制入库**：用户通过文件选择器或拖入导入，文件复制进应用管理目录，DB 只存索引与相对路径。
- **「通过路径选择后复制入库」与「长期引用原文件路径」是两件不同的事。** 前者是复制的一种触发方式，后者才是持续引用。不做后者，不等于前者永远不做。
- 若第一版不提供「路径字符串直传」接口（`asset.md §3.3`），必须**明确返回不可用**（`422 capability_unavailable`），**同时保证文件选择与拖拽导入可用**。
- 删除/备份行为：复制入库的文件随素材记录删除；引用原文件模式若将来启用，必须在 UI 标明「移动或删除原文件会失效」。

### 1.5 迁移（IndexedDB → 后端）

**必须保留**：文件本体（`blob`）、缩略图（`thumbBlob`）、`id` 对照、文件夹、标签、授权、审核、收藏状态、`builtin` 种子标记、`demo` 标记。

#### 1.5.1 流程

1. **导出基线**：迁移前导出 IndexedDB 全量清单（含每条 blob 的 SHA-256、字节数、`updatedAt`）。
2. **逐条上传**：成功后写回 `oldId → newId` 映射；失败记录原因，**不中断其余条目**。
3. **校验**：逐条比对服务端 `sizeBytes` 与内容哈希；不一致即该条失败。
4. **切换**：只有当「全部成功」或「用户确认跳过失败项」时才切换页面数据源。
5. **回退**：任一阶段可回退，回退后页面立即恢复读 IndexedDB。

#### 1.5.2 切换期间写入策略（关键，不能只有「全成功才切」）

「只要有一条失败就一直用旧库」是可行的保守起点，但**光有它不够**：迁移期间用户若继续改 IndexedDB，后端副本会立刻过时，切过去就丢改动。

采用**「迁移期间单写 + 变更补传」**：

| 阶段 | 读 | 写 | 说明 |
|---|---|---|---|
| `idle` | IndexedDB | IndexedDB | 未开始迁移 |
| `migrating` | IndexedDB | **IndexedDB（唯一写入方）** | 后端只接收补传，不接受页面直写 |
| `verifying` | IndexedDB | IndexedDB | 校验中，仍单写旧库 |
| `switching` | **短暂双禁写** | 禁写 | 只在此窗口切换，避免两边不一致 |
| `migrated` | 后端 | 后端 | 旧库保留只读，不删除 |

- **`migrating` 期间页面照常可用**，用户的改名/加标签/移动文件夹仍写 IndexedDB。
- 迁移器维护一份**变更日志**（`oldId + updatedAt` 快照），在进入 `verifying` 前对 `updatedAt` 变化的条目**补传一次**；补传后再校验。
- 切换窗口（`switching`）尽量短，UI 显示「正在切换数据源」。窗口内到达的写操作**排队**，切换完成后按新数据源执行，不丢弃。
- **不静默丢改动**：任何被跳过/失败的条目必须在界面逐条列出，用户可选择重试或明确放弃。
- **可恢复**：迁移状态机持久化（写后端 meta 表），应用重启后能从中断处继续，不要求用户从头再来。

### 3.2 E. 分析维度（已裁决）

**界面默认保持现有六项**：`cameraMove`（运镜）/ `rhythm`（节奏）/ `lighting`（光线）/ `composition`（构图）/ `transition`（转场）/ `reusable`（可借鉴点）。

后端设计约束：

1. **后端允许保存有依据的其他分析信息**，数据结构可扩展（如 `scale`/`subjectMove`/`color`/`narrative`/`shotType`），但：
   - **不强制模型填满**；
   - **不强制界面全部展示**；
   - **不把这些技术维度作为工作流门槛**。
2. **不编造置信度和证据，不等于不要证据。**
   - 有真实可追溯的**帧、时间段、人工标注** → 保存并展示。
   - 没有 → 标为「未知」或 `pending`，**不留空白让人觉得是没做**，也不填默认值冒充结果。
3. **分析来源必须三分**：`measured`（实测：切点/时长/亮度等可计算量）/ `model`（模型判断）/ `user`（用户填写）。界面上必须可区分。

### 3.3 F. `reusable` 与 `suggestion` 分开（已裁决）

| 字段 | 回答的问题 |
|---|---|
| `reusable`（可借鉴点） | **可以借鉴什么，以及它的限制条件** |
| `suggestion`（建议） | **对当前这条创作的具体用法建议** |

- 两者语义不同，**暂不合并**。
- **缺少依据就留空或 `pending`**，不允许两处生成同义内容。
- 若将来发现二者在真实数据上高重合，再议合并；当前以「不重复生成」为约束。

## 4. 三库共用基础设施

| 项 | 设计 |
|---|---|
| 文件存储 | 应用管理目录，按 `contentHash` 分桶；DB 只存索引与相对路径 |
| 去重 | 内容 SHA-256 识别同一文件本体；**不合并**同一文件的名称/标签/授权等用户记录 |
| 引用 | `ResourceRef{kind: project\|workflow\|task\|scene, id, label}`；删除前由后端检查引用并 409 列出引用方 |
| 任务 | 复用现有 `tasks` 基础设施，参考片解析用 `kind=analyze` |
| 状态机 | 素材五维（`README.md §4.5`）统一实现，禁止压成单一 `ready` |

### 4.1 检索：第一阶段范围（不是三库终点）

**第一阶段（本分支交付）**：
- 结构化筛选（类型/来源/文件夹/标签/审核/授权/可用性/引用/项目）
- 中文文本搜索：SQLite `LIKE` 子串匹配，覆盖名称、别名、标签、描述、技法用途、片段观察与分析文本
- 分类计数（facets）
- **不上 FTS5**：中文分词与默认全文索引的效果必须用真实数据压测后再决定，不假设可用

**后续阶段（仍在三库目标内，本分支不完成）**：
- 语义检索：待 embedding 模型与运行方式确定后，对可检索文本分段建索引
- 向量索引视为**可重建派生数据**，不取代原始记录
- 混合召回：关键词 + 语义 + 硬约束，用户指定的项目/类型/授权先作为约束，再排序
- 索引更新：新增/编辑/删除/模型版本变更时更新或重建；失败可重试，页面显示「未索引/索引中/失败」
- 结果必须带**可用证据**：资源 ID、来源、版本、文件可用性；参考片返回时间段与分析来源；特效返回适用条件、限制与本机执行状态
- 多模态：按「画面相似/动作相似」检索需要可用的图像/视频模型与验证过的索引方案，**不能只给文件名做文本向量就称为理解视频**

**不得把第一阶段描述成「已完成语义检索」。**

## 5. 与分析链路的关系（可失败原则）

参考片解析为异步任务（`kind=analyze`），必须满足：

- 自动分析失败时，**人工标记的片段、播放、收藏、集合全部照常可用**，视频状态停在 `pending` 而不是伪造 `partial`。
- 模型不可用 → 保持待分析，不报「已解析」。
- 重复解析写入新版本，不覆盖旧分析，保留历史。

## 6. 与创作工作流的衔接

本分支**不重做现有工作流创作链**。只约定资源引用最小契约：

一次创作请求可携带：
- 素材 ID、用途、文件访问方式
- 特效 ID、版本、参数、以及是「借鉴」还是「执行」
- 参考视频/片段 ID、时间范围、希望借鉴或避免的内容

后端负责解析并检查资源存在性，向 agent 提供它实际能读取的文件与信息。

**四种状态必须分别记录**：`选中资源` → `传给 agent` → `agent 实际读取` → `产物中引用`。三库完成后先提供可调用查询接口；**真实创作链未验证前，不宣称「已用于生成」**。

### 9.10 缩略图与元数据

`ThumbnailService`：视频 `ffmpeg -ss 1` 抽帧 → 480 宽 WebP；图片缩放（只缩不放）；
`ffprobe` 读宽高与时长。

失败语义分两类，**不混在一起**：

| 失败 | 结果 | 界面 |
|---|---|---|
| 元数据读不到 | 字段留空 | 显示「未知」 |
| 缩略图生成不了 | `thumbnailUrl=null` | 回退类型图标 |

两者都不让导入失败；**绝不画假图冒充缩略图**。处理状态据此判定：真解析过才标 `ready`。

验证：

```
6 个真实素材     → 全部有缩略图与元数据，界面占位图标数=0
图片             → dur=None（ffprobe 报的 0.04s 是单帧时长，已过滤）
无 ffmpeg        → 导入照常成功、状态停在 pending（NoFfmpegFallbackTest）
随包 ffmpeg      → env -i 仅用随包 lib 抽帧成功（7162B）
```

打包环节踩到的真实坑（值得记下）：

- 系统 `libavcodec.so.63` 是**符号链接**，`cpSync` 会把绝对路径链接拷进去，
  安装包里只剩一条指向 `/usr/lib/...` 的死链 —— **等于没带库，但打包脚本显示成功**。
- `cpSync` 加 `dereference` 也不行：它把符号链接目标当目录处理，报 `EISDIR`。
- 改用 `copyFileSync` 跟随链接，并加校验拦截空文件/死链。产物 34MB。

### 9.12 特效库

### 9.14 参考片库（基础能力）

后端新增 `reference` 域。视频**复用素材**（`assetId`），同一文件不在素材库与参考片库各存一份；
按素材反查去重，拖两次同一视频不产生两条参考片。

守住的三条分析口径：

| 约束 | 为什么 |
|---|---|
| `observation` 与 `inference` 分列 | 合并后界面没法分区块，用户会把推断当事实 |
| `pending=true` 时 value 必须为空 | 填「无」会让界面分不清「解析过、结论是无」和「还没解析」 |
| 已解析必须有 value 且必须标 `source` | 模型判断不能显示成实测事实 |

`inference` 不在可编辑字段里 —— 允许手改推断等于把人的猜测伪装成模型结论。
自动分析如实返回 `422 capability_unavailable`，不伪造 `partial`。

验证（18082 + 浏览器）：

```
导入真实 mp4    → duration=10000ms 实测、复用素材、重复导入 deduped
切两段          → 六维全 pending、value=''、source=null
自动分析        → HTTP 422 capability_unavailable
收藏/集合/搜索  → 均正确；「沙漠」命中 1 条
视频 Range      → 206 + Content-Range
页面            → 真实视频播放、片段 2/2、六维「待分析」、无 JS 错误
```

前端改造中修掉两个真实缺陷：

- 模块级 `SEGMENT_BY_ID`/`VIDEO_ORDER` 绑定演示常量，数据改服务端后在到达前就固定成空表；
- 后端返回相对路径 `/api/assets/...`，而 `<video src>` 需要完整 URL，
  否则会打到前端 dev server —— 表现为「视频永远播不出来」（缩略图此前踩过同一个坑）。

### 9.18 安装态真机验证（发现了安装级阻塞）

构建 AppImage（285MB）后在**全新 HOME** 下实测 —— 这是开发态永远暴露不了的一层。

**发现的阻塞**：后端在全新安装时**根本起不来**。

```
java.sql.SQLException: path to '/home/.../data/fengmotion.db':
                      '/home/.../data' does not exist
```

SQLite 不会创建缺少的父目录，而它以「Failed to execute database script」的形式抛出，
看起来像 schema 有问题，实际原因是目录不存在。开发机的
`~/.config/FengMotion/data` 早就有了，三库开发期间一直没踩到。

**修法**：在 `main` 里、`SpringApplication.run` 之前创建目录。
做成 `@Component` + `@Value` 实测来不及 —— 数据源初始化比 bean 注入更早。

**安装态实测结果**（全新 HOME、零依赖）：

| 项 | 结果 |
|---|---|
| 后端健康检查 | 通过，`fengmotion.db` 建出 |
| 特效目录 | 16 条自动导入 |
| 素材导入 | 640×360 / 10000ms 实测值，缩略图 4820B WebP |
| 随包 ffmpeg | **安装态真实生效**（缩略图由它生成） |
| 参考片导入 | 复用素材、可播放 |
| workflow-v5 | `toolAvailable=true` |
| 四个视图 | 渲染无 JS 错误；特效库 16 条带真实预览图 |

**过程中值得记的一点**：首次探活失败一度被误判为「后端没起来」，
实际是**启动要 35 秒**（AppImage 挂载点首次读取慢），探活太早。
日志为空也是同一原因 —— 不是没输出，是还没到输出的时候。

新增 `StartupDirectoriesTest` 3 项锁住该回归。
