# 前后端协议

本协议约定前端与（未来）Agent 后端之间的数据与状态契约。由协作者出前端稿、维护者确认后端可实现性与字段口径后冻结；冻结后的变更走第 6 节流程。

状态：v0.2（2026-10-23 起，字段与端点以 `docs/contracts/` 全量契约 + `src/types/contracts.ts` 为准，本文件只保留总原则与变更流程）。当前后端未接入，契约是双方对齐目标，前端先以演示适配器实现。

## 1. 总原则

- **唯一数据入口**：前端视图只经 `src/services/` 的 studioApi 层取数与执行动作，禁止视图内散落请求与数据拼装。
- **适配器可替换**：演示适配器与真实后端实现同一接口；切换实现不改视图代码。
- **契约先行**：新能力先在本文件补契约（字段、状态、错误），再写实现。
- **诚实标注**：凡经演示适配器返回的数据，UI 必须显式标注 Demo（见第 4 节）；禁止以演示结果冒充真实执行。

## 2. 通用约定

- ID：所有实体使用稳定字符串 ID；跨实体引用只用 ID，不嵌套整对象。
- 时间：统一毫秒时间戳（`startedAt` 等）或 ISO 8601 字符串，同一契约内不混用；时长用毫秒（`timecodeMs`、时长字段）并在字段名注明单位。
- 状态枚举：小写蛇形（`not_run`、`running`、`completed`、`failed`、`cancelled` …），枚举值只增不改义；废弃值保留并标注，不复用。
- 可空性：字段缺失用「不返回该字段」表达，不用空字符串或 0 冒充；未知状态必须有明确的未执行/无数据表达，不得默认成成功。

## 3. 核心对象（前端所需口径）

- **Project / Task**：项目与创作任务。任务状态是全站执行状态的唯一驱动源（工作台顶部摘要、任务页签、我的创作卡片状态都读同一状态，不各存一份）。
- **Artifact（产物）**：版本化产物（渲染结果、关键帧、方案等），带版本号与来源任务；产物浏览器当前为只读演示。
- **AgentReference**：Agent 对场景/帧/时间范围/区域/产物的结构化引用，分 target 与 context 两种角色（已在 studioApi 落地）。

## 4. Demo 标注规范

- 演示适配器返回的数据对象须带可识别的 demo 标记（现有 fixture 约定 `demo: true`）。
- UI 呈现：演示数据在页面上有可见的「演示」标识；由演示数据驱动的操作（恢复、检查通过等）必须禁用或明确标注为演示行为。
- 汇报与文档同样适用：演示链路跑通只能表述为「交互连通」，不得表述为「真实能力完成」。

## 5. 全量 API 契约（`docs/contracts/`）

自 2026-10-23 起，字段、状态、端点、错误码以 `docs/contracts/` 为准，类型唯一来源为 `src/types/contracts.ts`。本文件不再重复字段定义，避免两处口径打架。

## 6. 契约变更流程

1. 提出方在本文件以 PR 形式修改契约，并写明变更原因与影响面。
2. 另一方确认可实现性（后端）或可呈现性（前端）后合并，视为新版冻结。
3. 已冻结字段不直接改义：需要新语义时新增字段或枚举值，旧值标注废弃并给出迁移期。
4. 实现跟不上契约时，先改演示适配器顶住并保持 Demo 标注，不私自改契约迁就实现。

## 工作台本地审阅扩展说明（2026-10-29，未冻结为服务端契约）

现有本地演示 `TaskRequest` 新增可选的 `feedbackId`、`creativeBrief`，后者保存原始需求、带 ISO 时间的后续纠正、特别保留要求；`preview` 引用新增可选 `endTimeSeconds`，与 `timeSeconds` 表达同一真实媒体的选段，结束须大于开始且不超过实际时长。此处属于本地前端快照扩展，无新增 HTTP 端点，未宣称服务端已经接收或执行；后续真实适配器需按冻结契约完成字段映射与评审。

审阅意见以项目为边界存入浏览器 localStorage。`open` / `resolved` 是用户自己的待处理/已处理标记，与任务完成、Agent 执行、检查通过独立。每次发送保存不可变请求和需求快照；后续纠正不会回改旧请求。存储失败时显示仅页面有效并允许导出 JSON。播放位置、区域和版本定位只依赖实际文件与运行产物，缺文件不替换成旧片。同路径的文件不能被当作两版比较。

`ModificationConstraints` 另加可选 `preserveOutsideSelection`：表示框选区域之外保持不动，对应说明文档第 7 节原话「背景不要动」。同一段要求的另外两处补充：默认目标引用现在会带上当前停留的时间位置（用户不点「引用此帧」直接发送，时间位置也不再丢失）；切换预览画面时，上一个画面的区域/时间引用会撤下并降为上下文，避免「看着 A、改的是 B」。以上均为本地扩展，服务端契约尚未冻结这些字段。演示适配器会把收到的目标对象、时间位置、框选区域、保留条件、需求快照逐项回执，供用户核对「用户指的对象与执行对象是否一致」。


### 本机场景编辑文档与渲染（2026-10-29）

该链路为本机真实能力，不调用演示 studioApi 生成视频。`src/editor/types.ts` 定义 `SceneDocument` schemaVersion=1：项目/文档身份、引擎、画布规格、图层、元素覆盖及源文件哈希。文档按项目保存在 `fengmotion:scene-documents:v1:<projectId>`；最后打开文档保存于 `fengmotion:editor-last:<projectId>`；媒体文件通过 assetService 存入 IndexedDB。换浏览器/清理本地数据前需要导出 ZIP 备份。

`fengmotion:editor-renders:<projectId>` 记录本机导出身份、场景身份、素材 ID、版本及时间，新记录包含当次文档快照。预览 `origin: editor`、`assetId` 可选字段区分本机真实文件与工作流产物；不填写虚构 workflowId，不把本机编码描述为云端任务完成。编辑入口按当前编辑器预览的场景身份定位可编辑文档，当前修改保存在同场景工作副本；历史导出文件保持原样。

JSON/ZIP 导入经过规格及图层校验；HTML 只接受清单中身份和哈希匹配的源工程，忽略导入包提供的可执行源码，实际运行内置受信任快照。ZIP 可恢复媒体文件和 MIME。当前不提供通用 Remotion TSX 项目编译 API，也不支持 HTML 视频编码。浏览器 MP4 编码能力由实际 WebCodecs 检测决定，失败时展示原因。

## 前端 API 传输层（2026-10-30，本地实现，服务端契约未冻结）

依据 `FengMotion-前后端迁移与视频生成方案/02-前后端API契约.md`（迁移草案 v0.3，**提案、未冻结**）在 `src/services/api/` 落地前端 API 层：`HttpClient` 是**唯一 fetch 出入口**，各域客户端（system/projects/tasks/chat/assets/renders/checks/workflows/library）只经它请求；视图仍按第 1 节「唯一数据入口」只经 `src/services/` 取数。以下为本地约定与已发现的契约缺口，需评审后回写 `docs/contracts/` 与 `src/types/contracts.ts`：

- **基址**：默认 `http://127.0.0.1:8080/api`，取值优先级 显式入参 > 环境变量（`VITE_FENGMOTION_API_BASE` 等）> 本机 localStorage `fengmotion:api-config:v1` > 默认值，来源记入 `ApiConfig.source` 供界面说明。前缀延续 `/api`（02 §1），不改写用户填写的路径，也不偷偷引入 `/api/v1`。**不做自动降级**：连不上即报错，不换成演示数据。`4173` 与 `5173` 是不同 Origin，联调仍需后端白名单或代理（03 §4）。
- **契约缺口：401 无对应错误码**。`docs/contracts/README.md` §2.2 要求 token 过期返回 `401` 并重新握手，但 `ApiErrorCode` 未收录该值。传输层暂以本地码 `unauthorized` 表达，建议评审时并入契约。
- **传输层本地错误码**：`network_error`（压根没连上）、`stream_disconnected`（已连上、流在中途断了：SSE 被掐断或空闲超时）、`timeout`（超时）、`aborted`（调用方取消）不属 `ApiErrorCode` —— 它们根本没到服务端，用 `internal_error` 冒充会把「连不上」或「连接断了」说成「服务端出错」，故单列。前两者还必须分开：对用户的下一步动作不同（前者要检查后端是否启动，后者等等即可）。以上均在 `src/services/api/types.ts` 登记。
- **事件流参数**（本地实现细节，可按部署调整，不是服务端契约）：`streamIdleTimeoutMs` 默认 45 秒（对齐 README §2.9）、`streamReconnectLimit` 默认 5 次、`streamStableMs` 默认 10 秒 —— 最后一项目的是区分「健康长连接偶发断线」（应清零重连计数）与「连上→发一帧→立刻断开」的抖动故障（不得清零，否则重连上限永不生效、界面会无声地永远显示「正在恢复」）。三者都可由环境变量（`VITE_FENGMOTION_STREAM_*`）或本机存储覆盖；若产品希望「有进展就永不放弃」，调小 `streamStableMs` 即可，但重连上限也就不再能收束抖动故障，该取舍需评审后写进契约。
- **本地扩展字段发送闸门**：`preview` 引用、`feedbackId`、`creativeBrief`、`preserveOutsideSelection` 属未冻结扩展（第 59–65 节）。`ApiConfig.allowLocalModifyExtensions` **默认 false**，开启前真实任务一律被 `validateTaskRequest` 拦下并说明原因，避免服务端忽略未知字段后静默丢目标（02 §1 P0 阻塞）。
- **发送前校验**：`src/services/api/validate.ts` 在发请求前核对 kind 必填块、至多一个 target、`scope=scene/selection` 的定位条件、preview 的项目归属与时间范围、bbox 归一化边界、区域外保留必须有区域、附件必须有已完成上传的 `fileId`，以及旧字段 `shotId` 混入。任一项无法确认即抛 `validation_error`（问题清单在 `details.problems`），不发送。
- **旧骨架兼容**：错误信封两种形状都解析（嵌套 v0.3 优先，其次旧扁平 `{code,message}`，并标记 `legacyShape`）；`shotId` 无到 `sceneId` 的真实映射时拒绝转换，不按名称猜；`demo:true`/`mock:true` 都识别为演示但**不改成 false**。
- **能力视图**：`buildCapabilityViews` 合并服务端 `/capabilities` 与本机能力，服务端 `unavailable` 不隐藏本机编辑器能力；`demo` **不**放行真实写操作。
- **事件流**：`GET /tasks/{id}/events` 与 `/chat-sessions/{id}/stream` 用 fetch 流自建（`EventSource` 不能带 `Last-Event-ID` 与鉴权头，token 也不放 URL）。按 `(taskId, seq)` 去重、缺口未补齐时状态为 `resyncing`（界面显示「正在恢复」），**断线、超时、202 均不得判为完成**；终态只认 `end` 帧或终态事件。对话流 `delta` 无 seq、重连可能重放，以 `completed` 的完整消息为准。
- **token**：只放内存，不进 localStorage、不进 URL；本机存储只保存基址与模式等偏好。

## 对话会话接入（2026-11-01，前端已接；后端 create/list/detail 待实现）

对话视图的「我的创作」左栏已从纯内存改为读服务端会话。依据 `docs/contracts/agent.md` §2，项目路径下的会话接口约定如下（前端按此实现，后端实现须与本表一致）：

| 操作 | 请求 | 成功响应 |
|---|---|---|
| 列表 | `GET /projects/{projectId}/chat-sessions?limit=&cursor=` | `200` + `Page<ChatSession>`（`{items, nextCursor}`；条目按最近更新倒序） |
| 创建 | `POST /projects/{projectId}/chat-sessions`，body `{projectId, title?}` | `201` + `ChatSession` 本体（不是信封）；`projectId` 必须与路径一致；`title` 缺省由服务端生成「未命名对话」 |
| 详情 | `GET /chat-sessions/{sessionId}` | `200` + `ChatSession` |

`ChatSession` 字段：`{id, projectId, title, createdAt, updatedAt, messageCount}`，时间 ISO 8601 字符串。错误沿用 `contracts/README.md` §2.4 信封；404 在本轮被前端同时解释为「项目不存在」与「会话端点尚未实现」，不硬指其中一种。

前端行为与边界：

- **有项目的会话**走真实 HTTP：进视图按项目拉列表（翻页到 `nextCursor` 为空），创建走 POST，进入服务端会话时补读一次详情（`GET /chat-sessions/{id}`）刷新标题/时间/消息计数。详情读取失败时保留列表已有信息并标出「不是最新」+ 重试，不把失败显示成空会话。
- **无项目的会话**服务端无对应端点（契约要求会话必须属于项目），只保留本页草稿，标「仅本页」，**不调用创建接口**。
- **创建失败**保留用户输入为未保存草稿（`origin: 'local'`，左栏可见「仅本页」与「重试保存到服务端」），不冒充创建成功；错误原因在左栏与对话区同时可见。
- **消息历史 / 发消息 / SSE 尚未接入**（后端未实现）：服务端会话的输入框停用并说明「输入已停用；现在输入的内容不会被发送或保存」，不展示演示回复、不写回会话对象、不调用 `POST /messages` 与 `/stream`。演示回复只存在于本页草稿，且消息上保留演示来源标注。
- **重命名 / 置顶 / 归档 / 删除 / 改归属**均无服务端端点：重命名对服务端会话禁用，删除只从本页视图移除（文案为「从列表移除」，不声称服务端已删除）。
- 创建请求会自动带 `Idempotency-Key`（传输层行为），但本轮后端**未承诺**幂等，前端也不依赖它去重。

### 核心事实：没有 token 级流

DSH 的 SDK 通道（`dsh --profile sdk`，stdio JSON-RPC）**只发持久事件**，文本在步骤提交点整段到达
（后端文档 §1.1 已实测：`step/start` 之后静默 7.5 秒，直到 `assistant/message` 才一次性给全文）。
token 级实时流只走 Web 客户端的 Remote 通道，进程外集成拿不到。

**因此前端不做打字机动画**——没有增量就不假装有增量。这是后端文档 §4.1 的明确要求
（「不要显示，会误导用户」）。已查验：现有对话界面本就没有逐字动画，只有「正在回复…」占位文字。

### SSE 帧：新增 `status` / `heartbeat`

契约（`docs/contracts/agent.md` §流式）原有帧是 `delta` / `completed` / `task` / `end` / `error`。
后端接入 SDK 后会新增两种帧，前端已支持：

| 帧 | 载荷 | 前端行为 |
|---|---|---|
| `status` | `{type:'status', phase:'thinking'\|'tool'\|'done', name?, label?}` | 显示阶段文案；**不携带正文** |
| `heartbeat` | `{type:'heartbeat'}` | 仅重置空闲计时，不改变任何状态 |

`ChatStreamStatus` / `ChatStreamHeartbeat` 已加入 `src/types/contracts.ts`，
`openChatSessionStream` 新增可选 `onStatus` 回调（`src/services/api/streams.ts`）。

**`status` 不是回复**：正文仍只由 `completed` 给，`completed` 为准。缺 `delta` 不影响状态机
（后端文档 §4.3 方案 B 的前提，已查验 `onDelta` 本就是可选参数）。

### 引擎探测：`/api/harnesses`

新增 `src/services/api/harnesses.ts`（`harnesses.list()` / `models(id)`）与
`src/shell/useHarnesses.ts`（hook）。首页引擎选择器的**可用性改由后端探测结果决定**，
本地 `data/harnesses.ts` 只保留名字/图标/颜色这些展示信息。

三种状态必须区分（后端该端点当前是 🔨「可做，未实现」）：

| `probe.status` | 含义 | 界面 |
|---|---|---|
| `ready` | 后端给出清单 | 按每项 `status` 显示「已接入 / 配置有误 / 未接入」 |

### 引擎可用性的判定（2026-11-02，按真实后端实测修正）

初版实现把「未接入」与「状态未知」混在一起，界面上三个引擎一律显示「状态未知」。**这是错的**：
「未接入」是确定的结论，「状态未知」是「读不到」。已按两层判据重做：

| 层 | 数据来源 | 作用 |
|---|---|---|
| 1. DSH 是否接入 | `GET /api/capabilities` 的 `agent.status` | 决定全部引擎的基调 |
| 2. 该引擎自身状态 | `GET /api/harnesses` 的对应条目 | 决定单个引擎 |

判定顺序（`src/shell/useHarnesses.ts` 的 `availabilityOf`）：

| 条件 | 结论 | 界面文案 |
|---|---|---|
| `agent.status === 'unavailable'` | 全部引擎未接入 | 未接入，仅展示 |
| `agent.status === 'demo'` | 全部引擎只有演示数据 | 未接入，仅展示 |
| 能力声明**读不到** | 无法判断 | 状态未知 |
| 后端清单里**没有**该引擎 | 该引擎未接入 | 未接入，仅展示 |
| 该引擎 `status === 'misconfigured'` | 配置有误 | 配置有误 |
| 该引擎 `status === 'available'` | 可用 | 已接入 |

「状态未知」只保留给真正无法判断的情形（能力声明读不到），不再兜住「未接入」。

### 实测发现：后端已实现，后端文档滞后

后端两份文档把 `/api/harnesses` 标为 🔨「可做，未实现」，但**实测（2026-11-02）该端点已存在并返回真实数据**：

```json
{"items":[{"id":"dsh-sdk","name":"DeepSeek","kind":"sdk","status":"available","version":"0.2.1-rc.2",
  "capabilities":{"streaming":"commit","cancel":"process","resume":true,"tools":true,"reasoning":true}}],
 "cachedAt":"2026-11-01T16:15:36.489312725Z"}
```

`/api/capabilities` 的 `agent` 也已是 `available`（后端 `SystemController.agentCapability()` 按真实探测结果声明）。
因此前端按「文档滞后于实现」处理：接口存在就用，不依赖文档里的 🔨 标记。

### 实测发现：引擎 id 两套命名

后端用 `dsh-sdk`（harness 维度），本地 `data/harnesses.ts` 用 `deepseek`（产品维度）。按 id 精确比较会一个都匹配不上，
把已接入的引擎误判成「状态未知」。前端加了 `matchHarness()`：先精确匹配 id / name，再做包含式匹配。

### 实测发现：模型字段名不一致

`/api/harnesses/{id}/models` 实测返回 `isDefault`，而后端文档 §4.2 写的是 `default`。前端两个都读，以文档为准、实测兜底。

### 桌面壳与前端的后端地址（接线修复）

桌面壳运行时才知道真实后端地址（可能是动态端口），而前端配置层只认**构建期**注入的 `VITE_FENGMOTION_API_BASE`。
原先两者**没有接上** —— 壳设置的地址完全不起作用，前端一直打默认 8080（已实测：设 `FENGMOTION_API_BASE` 无效）。

修复：`electron/preload.ts` 暴露 `runtimeConfig()` → `src/services/desktopBridge.ts` 读取 →
`src/services/api` 的 `initDesktopApiBase()` 把它作为 `explicit` 一档注入配置（压过 env 与本机存储）。
`App.tsx` 启动时调用；`useHarnesses` 在探测前等地址就绪。

### 模型目录也接后端（2026-11-02）

模型列表此前读的是本地 `data/harnesses.ts` 的 `h.models`，那三个名字（`deepseek-chat` /
`deepseek-reasoner` / `deepseek-v4.1-flash`）是**产品侧写的**，与 DSH 实际路由不符 ——
选到前两个必然失败。

后端 `GET /api/harnesses/{id}/models` **存在且可用**，实测返回：

```json
{"items":[{"id":"deepseek-v4.1-flash","label":"deepseek-v4.1-flash","isDefault":true,
  "contextWindow":null,"maxTokens":null}]}
```

注意后端当前只返回**配置里那一个模型**（`HarnessService.doProbe()` 里 `List.of(new ModelEntry(properties.getModel(), …))`），
不是 provider 的完整模型目录。配置见 `application.yml`：`provider: agent2api-ecs` / `model: deepseek-v4.1-flash`。
后端文档 §4.2 写「数据来自 DSH 的 provider 配置，不在后端硬编码」—— 与实现仍有差距，属后端待补。

前端处理：

- 模型列表以**后端目录**为准（`src/shell/useHarnesses.ts` 的 `modelsOf`），**不回退本地列表**
  （本地名字在 DSH 路由中不存在，回退等于让人选一个必然失败的模型）。
- 后端目录就绪后，当前选中的模型若不在目录里，用**派生值** `effectiveModel` 校正到后端默认模型
  （不用 effect + setState，避免级联渲染）。
- 拉模型失败按引擎记，不影响其他引擎。

| # | 缺口 | 前端现状 |
|---|---|---|
| 23 | `/models` 只返回配置的单模型，非 provider 完整目录 | 前端按实际返回展示；后端补齐目录后前端无需改动 |
| 24 | `contextWindow` / `maxTokens` 实测为 `null` | 前端视为「未知」，不显示具体数值 |
