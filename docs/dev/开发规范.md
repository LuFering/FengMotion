# 开发规范

本规范约束 FengMotion 仓库的日常开发协作。由协作者起草、维护者批准；修改本规范本身走 PR。

## 1. 分支

- `main` 是唯一主干，始终保持可构建。
- 所有开发从 main 切功能分支，命名：`feat/<范围>-<主题>`、`fix/<范围>-<主题>`、`docs/<主题>`、`chore/<主题>`，如 `feat/fe-workbench-gate-card`、`docs/repo-standards`。
- 前端分支范围前缀用 `fe`，后端/Agent 用 `be` / `agent`，便于按前缀识别归属。
- 分支小步快走：一个分支一个主题；勤同步 main（至少在提 PR 前 rebase 或 merge 一次），禁止长分支漂移数周。
- 不直推 main。紧急修复例外时，提交信息正文第一行写明「直推原因」。

## 2. 提交

- 中文 Conventional Commits：`<type>(<scope>): <说明>`。
  - type：`feat` / `fix` / `docs` / `refactor` / `style` / `test` / `chore` / `build`
  - scope 用模块名：`workbench`、`fx`、`assets`、`shell`、`workflow`、`docs` 等
  - 示例：`feat(workbench): 增加 Structured 路径的 Gate 确认卡`
- 一个提交只做一件事；提交前自查 `git diff`，不带入无关文件与调试残留。
- 提交身份须可辨认作者（真人或其 AI 协作者账号），禁止冒用他人身份。

## 3. Pull Request

- PR 标题与首个提交同义；正文按 `.github/PULL_REQUEST_TEMPLATE.md` 填写：变更说明、影响范围、验证情况、未验证范围。
- 一个 PR 一个主题；大改动先拆分或先对齐方案（必要时补决策记录）。
- 前端 PR 须附截图或预览（改动前/后对照更佳）；接口或契约变化须同步更新 [前后端协议](前后端协议.md)。

## 4. 审核

- 前端 PR 由协作者（muse-lufering）审核，维护者最终合并；后端/Agent PR 由维护者自审，涉及契约的部分协作者参与确认。
- 审核清单（前端）：① 与施工规格逐项一致；② 使用设计 token 与共享组件，无平行样式体系；③ 改动范围干净，无无关业务逻辑变更；④ 未接通能力明确标 Demo；⑤ 构建、类型、lint 通过；⑥ 交互真实可用，加载/空/错误状态齐全。
- 审核结论分级：**阻塞**（必须改）与**建议**（可跟进）。结论留痕在 PR 评论。
- 作者对意见有异议时在 PR 内讨论；涉及产品方向与审美的分歧，升级维护者裁决。

## 5. 证据规则（验证状态词）

完成与验证是两件事。汇报与 PR 中描述检查结果时，只使用以下状态词，且不得拔高：

| 状态词 | 含义 |
|---|---|
| 已通过 | 实际执行了该检查且结果为通过（附命令或截图） |
| 已查验 | 人工查看/对照过，但未跑自动化检查 |
| 未执行 | 没有跑这项检查（须写原因） |
| 推断 | 基于代码阅读的判断，未实际验证 |

- 构建/lint/类型检查的结论必须来自实际运行输出。
- 未在与使用者相同环境验证过的视觉结果，只能写「已查验」并注明环境差异。
- 演示数据与真实能力在 UI、文档、汇报中一律显式区分（见协议文档第 4 节）。

## 6. 测试

- 每期交付与每个前端 PR，至少执行：`npm run build`（含 `tsc -b`）、`npm run lint`。
- 交互改动按页面核心任务清单回归（清单随各期规格给出）；失败项在 PR 中如实记录。
- 当前仓库尚无自动化测试套件；引入测试框架须走决策记录。

## 7. 文档维护

- 目录与职责变化 → 更新 [ARCHITECTURE.md](../../ARCHITECTURE.md)。
- 流程与规范变化 → 更新本文件。
- 每期开始/结束 → 更新 [开发进度](开发进度.md)。
- 版本级变化（用户可感知）→ 更新 [更新日志](更新日志.md)。
- 契约变化 → 更新 [前后端协议](前后端协议.md)，并遵循其变更流程。
- 重要取舍 → 新增 [决策记录](决策记录/README.md)（一篇一事：背景、决定、替代项、后果、验证）。
- 文档与代码不一致时，以代码为事实来源并立即修文档；不留「以后再补」。

## 8. 目录约定

- 新文件先找归属：页面进 `src/views/`，组件进 `src/components/`，数据入口进 `src/services/`，设计规格进 `docs/design/`，开发文档进 `docs/dev/`，设计素材进 `design/`。
- 禁止在根目录新增无归属文件；`workflow-v*` 旧版本目录只读，不回改历史。
- `public/replica/` 为 iframe 过渡页：只允许修过渡层问题（视觉对齐、Demo 标识、滚动与错误态），禁止在其中新增产品功能。
