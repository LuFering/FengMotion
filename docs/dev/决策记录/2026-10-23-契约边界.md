# 契约边界：域模型 / 服务传输 / Agent 编排

日期：2026-10-23 · 状态：已采纳

## 背景与问题

- 01 期 Issue 6 要冻结 `src/types/workflow.ts`、`src/types/check.ts` 与两份契约文档（`docs/契约-工作流.md`、`docs/契约-检查.md`）。
- Codync 开发者群里 Claude Code 提议「第一个 PR 做 studioApi 的类型与接口契约文档」，并提出拆分：agent 编排与任务协议归 DeepSeek Harness，studioApi 服务层与数据层归它自己。
- 两处口径不对齐，会出现三份互相竞争的“契约”：Issue 6 的两份域契约、新的 studioApi 契约文档、以及既有的 `docs/dev/前后端协议.md`。谁都能写、谁都能改，等于没有契约。

## 决定

分三层，每层只有一个归属；文档只做说明与互链，不重复定义字段。

1. **域模型层（01 期 Issue 6，本期唯一新增）**
   - 文件：`src/types/workflow.ts`、`src/types/check.ts`、`docs/契约-工作流.md`、`docs/契约-检查.md`
   - 负责：本地 AI（可由外部 DSH bot 代笔）；审：Codex（与 main 一致性）+ Claude Code（后端可实现性）
   - 范围：字段、状态、关联、状态转换。不写 mock 实现，不写 UI。
2. **服务与传输层（studioApi）**
   - 文件：`src/services/studioApi.ts` 的类型 + `docs/dev/前后端协议.md` 第 3、5 节
   - 负责：Claude Code 提改动（文档与类型签名），本地 AI 落到 `src/services/` 并跑构建；审：Codex
   - **不新开第三份 API 文档**：所有传输契约写进 `docs/dev/前后端协议.md`。
3. **Agent 编排与任务协议**
   - 文件：`docs/dev/前后端协议.md` 第 3 节 Task 相关；未来如独立成 `src/types/task.ts` 再单独立项
   - 负责：DeepSeek Harness（外部 bot）出品；审：Claude Code
   - 本期**不冻结**，只记录现状；01 期不新增该层文件。

## 边界规则（防止各写一套）

- 同一字段只能在一处定义：域模型在 `src/types/`，传输在 `src/services/studioApi.ts`。文档不得复述字段，只能引用。
- 冻结后的改动走 `docs/dev/前后端协议.md` 第 6 节流程（PR + 双方确认）。
- 群内 bot 不直接改 `src/views/`、`src/components/`；前端实现由本地 AI 统一提交，避免多个 agent 并行写同一棵组件树。
- Issue 6 是 `前后端协议.md` 第 5 节的执行，不是第三份契约；两份文档完成后，第 5 节改为链接。

## 与群内分工 v2 的关系

群内 v2 的五个视角（Codex 契约一致性、Claude Code 后端正确性、DeepSeek Harness 规格符合性、Hermes 构建回归、Muse Bridge 矩阵汇总）用于**审**，不构成实现权：

- 实现权按 2026-10-22 决策：本地 AI 统一写 `src/`（可由外部 DSH bot 代笔），群内 bot 不直接改前端视图与组件。
- 群内 bot 的产出以三类形式进入：可复现的证据（命令 + 输出）、审阅结论（用状态词）、必要时一条建议补丁分支。
- 已存在的建议补丁由本地 AI 复核后落到实现分支，不直接合并——避免同一文件两套改法。
- 唯一例外：Claude Code 的 studioApi 类型签名 PR（只改 `docs/dev/前后端协议.md` 与 `src/services/studioApi.ts` 的类型），需要本地 AI 合并并跑构建。

## 替代项与取舍

- 让 Claude Code 新开 `docs/契约-API.md`：与既有 `前后端协议.md` 重复，同一件事两个事实源，弃。
- 把域模型也并进 studioApi 文档：域模型会被传输细节污染，UI 与后端无法各自演进，弃。
- Issue 6 与 studioApi PR 并行开工：两边都要动 `src/types/` 与 `src/services/`，冲突概率高；改为串行（先定域模型，再定传输）。

## 后果

- 群里的两个“待拍板”项在 main 上已有结论（见附录），不再阻塞契约 PR。
- Issue 6 可独立开工，不依赖 studioApi 契约；studioApi 的类型 PR 落在 `src/services/` 与协议文档，不与 Issue 6 抢文件。
- 串行意味着 studioApi 契约 PR 要等 Issue 6 合入后开，排在 chore（lockfile）之后。
