> **「已实测」只写真实跑出来并看到输出的**；**「设计」是尚未实现的主张**。
> 本文所有代码都是临时探针，**已删除，未进入仓库**。

## 0. 结论先行

1. **静态规则对 remotion-scenes 的覆盖率是 100%**（204/204 能提取组件名、注释、props）。
   这条数据很重要：它说明「发现候选」不需要模型，模型要做的是**翻译与补全**。
2. **注释信息密度太低，值得让模型补**：平均 15 个字符、41% ≤12 字符、
   199/204 是日文。`ボケ効果`（散景效果）这种标签不足以支撑创作决策。
3. **模型输出必须逐条校验，幻觉是稳定复现的，不是偶发**：
   两轮真实调用分别编出了 `__PLACEHOLDER__` 和 `DataBarChart2`（输入里只有 `DataBarChart`）。
4. **校验器能把幻觉全部拦住**：8 个真实组件 8 条通过、1 条幻觉被拒，覆盖率无遗漏。
5. 成本可控：8 个组件 7.5 秒，204 个约 25 批 ≈ 200 秒。

**建议**：按你提的架构实现，但**规则层承担的比例要比原设想更大** ——
不是「规则发现、模型理解」的简单分工，而是
**规则产出可校验的事实骨架，模型只填骨架上的语义空位**。

## 1. 实测记录

### 1.1 静态发现（无模型）

对 `capabilities/remotion-scenes/src/scenes` 下全部 204 个组件（已排除 13 个 `index.tsx` 导出清单）：

| 能力 | 结果 |
|---|---|
| 识别出 `export const Xxx = ({...})` | **204/204** |
| 提取到 props 名与默认值 | **204/204** |
| 提取到首块注释 | **204/204** |
| 注释里能解析出「组件名 - 描述」 | **204/204** |
| 顶层目录即分类 | 16 个分类 |

props 分布极不均衡：`startDelay` 出现在 200 个组件上，其余 props 各出现 1–10 次。
这说明**绝大多数组件没有可调参数** —— 对"能不能用"的判断很有价值（见 §3.3）。

### 1.2 注释的信息量

| 指标 | 数值 |
|---|---|
| 平均长度 | 15.2 字符 |
| 中位数 | 15 字符 |
| ≤12 字符 | 83 个（41%） |
| 含日文 | 199/204 |
| 含中文 | 146/204 |

最短样例：`ボケ効果`、`波形背景`、`ノワール風`、`回転ドラム`、`オーロラ効果`。

**判断**：这些是"视觉现象的名字"，不是"这个效果解决什么表达问题"。
用户选特效时真正要问的是后者。

### 1.3 模型补充（真实调用，deepseek-v4.1-flash）

输入 8 个组件（跨 8 个分类），输出耗时 **7.5 秒**。

对比示例：

| 组件 | 原注释 | 模型产出 |
|---|---|---|
| BackgroundAurora | `オーロラ効果` | 中文名「极光背景」；用途「多层柔性光带缓慢摆动，营造梦幻氛围背景，**适合开场或标题铺垫**」 |
| DataBarChart | `バーチャート - 棒グラフ` | 中文名「柱状图」；用途「数据柱依次弹起生长，**用于视频内展示对比数据**的说明场景」 |
| EffectChromaticAberration | `色収差 - クロマティックアベレーション` | 中文名「色差偏移」；用途「文字红蓝色边错位抖动，营造故障震感，**适合科技或故障风强调**」 |

模型补的正是注释缺的那一半：**用在什么场合**。

### 1.4 幻觉：稳定复现

| 轮次 | 输入 | 模型输出 | 幻觉内容 |
|---|---|---|---|
| 1 | 8 个组件 | 9 条 | `__PLACEHOLDER__`（占位符被当成了组件） |
| 2 | 8 个组件 | 9 条 | `DataBarChart2`（输入只有 `DataBarChart`） |

**两轮各编造一条**。这不是偶发，是这类任务的结构性风险：
模型倾向于"凑满"输出行数。

### 1.5 校验器有效性

用真实模型输出跑校验，规则是「`component` 必须在输入候选集合里 / 名称非空且 ≤12 字 /
用途 ≥8 字 / 分类必须在枚举内」：

```
输入候选: 8
模型输出: 9
校验通过: 8
被拒: 1  {"component":"DataBarChart2","reason":"unknown-component"}
未被描述的组件: （无）
```

**幻觉被拦下，真实组件零遗漏。**

## 2. 架构（对齐你的建议，并补充实测依据）

```
扫描来源
  → 按来源选择解析器（已有：CapabilitySource 四实现）
  → 规则发现候选、提取客观字段（覆盖 100%，见 §1.1）
  → 有需要时由模型补充语义（只补注释缺失的「用途/分类/标签」）
  → 校验、去重、记录来源        ← 幻觉唯一可靠的拦截点，见 §1.4
  → 预览并确认
  → 写入特效库
```

### 2.1 分工边界（比原设想更明确）

| 层 | 负责 | 不负责 |
|---|---|---|
| 规则 | 组件名、文件路径、props、依赖、API 用量、分类目录 | 语义理解 |
| 模型 | 中文名、一句话用途、中文标签 | 判断组件是否存在、可执行性、许可 |

**关键约束：模型不得新增条目。** 它只能对「规则已发现的组件」补字段。
任何 `component` 不在候选集合里的输出，一律丢弃（§1.5 已验证有效）。

### 2.2 排除规则按来源配置

你的判断正确：`references/` 只收 `shots/` 这条规则对 shotcraft 有效，
不能假定其他库同构。所以排除规则应该**从代码移到来源配置**：

```yaml
# 每个来源一份，与代码分离
- name: video-shotcraft
  root: video-shotcraft
  include: ["references/shots/**"]
  exclude: ["**/README*", "**/ATTRIBUTION*", "**/_template/**"]
  categoryFrom: parentDir

- name: remotion-scenes
  root: remotion-scenes
  include: ["src/scenes/**/*.tsx"]
  exclude: ["**/index.tsx"]
  categoryFrom: topDir
  needsModel: true      # 只有这个来源需要模型补语义
```

这样新增库时改配置而不是改代码，恰好解决 §1 之后反复"遇到一个补一个"的问题。

### 2.3 证据与版本

每条记录补充：

| 字段 | 作用 |
|---|---|
| `source_path` | 已有 |
| `content_hash` | 源文件 SHA-256，未变化则跳过（已用于三库，复用同一机制） |
| `parser_version` | 解析器版本号，规则变更后可定向重跑 |
| `model_generated` | 哪些字段来自模型（逐字段标记，不是整条打标） |
| `model_id` | 生成时用的模型，便于复查 |
| `unconfirmed` | 模型没能确定、留空的字段列表 |

**幂等**：同一文件同一规则的解析结果必须得到同一 ID（现有实现已满足）。

### 2.4 「能介绍」与「能使用」分开

| 状态 | 判据 | 界面措辞 |
|---|---|---|
| 能介绍 | 静态发现成功 | 可浏览、可搜索 |
| 能使用 | 有入口 + 依赖可解析 + 参数可填 + 环境验证通过 | 可插入创作流程 |

§1.1 的数据在这里有用：**200/204 个组件只有 `startDelay` 一个参数**，
这意味着"参数化调用"对绝大多数组件没有意义 —— 它们更像**视觉原子**，
应该被组合而不是被调参。

第一版一律 `execution_status = not-implemented`，不做运行验证。
理由：204 个组件逐个隔离编译验证成本高，且没有 `package.json`
（实测该目录下不存在），环境信息不完整。

### 2.5 先预览再导入

预览页应显示：新增 / 更新 / 跳过 / **待确认**，以及每条跳过原因。
§1 的教训是：一条过宽的规则会悄悄吞掉大量条目（实测从 507 修正到 175）。
预览是唯一能让人发现"规则写错了"的地方。

## 3. 建议的实施顺序

| 阶段 | 内容 | 验收 |
|---|---|---|
| 1 | 来源配置化（§2.2），把现有三个库的规则从代码搬进配置 | 175 条结果不变 |
| 2 | 源码候选发现器（纯规则，无模型） | 204/204 候选，0 条垃圾 |
| 3 | 模型补充 + 校验（§2.1、§1.5） | 幻觉 0 采纳、真实组件覆盖率 ≥95% |
| 4 | 预览与确认 | 能看到跳过原因 |
| 5 | 全量导入 remotion-scenes | 人工抽检 20 条 |

**建议一次性做 1–2，观察后再决定 3。**
理由：1–2 是纯确定性工作，风险低；3 的收益已在 §1.3 证明，但把模型接入
导入链路会引入不确定性与成本，值得等 1–2 稳定后再做。

## 4. 明确不做（本阶段）

- 不做组件渲染验证（§2.4）
- 不让模型判断「这个组件能不能运行」
- 不让模型生成不存在的组件
- 不把注释直接丢掉：原注释保留在 `source_text`，用于复查模型是否翻译错
