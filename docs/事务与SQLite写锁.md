# 事务与 SQLite 写锁

本文结合 `ProjectCreationCoordinator` 中的项目创建流程，解释事务、幂等和 SQLite 写锁各自负责什么。

## 1. 为什么创建项目需要事务

带幂等键的项目创建涉及两项数据库写入：

1. 在 `projects` 表中保存项目记录。
2. 在 `project_idempotency` 表中保存幂等键与项目的关联。

我们希望它们一起生效。如果只保存了项目，幂等记录却没有保存，前端重试时就无法通过幂等键找到此前创建的项目。

数据库事务把这些数据库操作组成一个整体：

```text
开始事务
  ├─ 保存项目记录
  ├─ 保存幂等记录
  └─ 提交 → 两项数据库改动一起生效

执行或提交失败 → 回滚 → 本次事务中的数据库改动不保留
```

**提交（commit）**确认数据库改动；**回滚（rollback）**撤销当前事务中尚未提交的改动。

## 2. Spring 怎么管理事务

项目中使用 `TransactionTemplate`：

```java
return transactions.execute(status -> {
    // 在事务中执行的数据库操作
    return project;
});
```

Spring 在事务中执行 Lambda 中的代码。正常执行后会尝试提交；遇到未处理的运行时异常时回滚并抛出异常。提交本身也可能失败。

`status` 是 Spring 提供的事务状态对象；当前回调没有使用它。回调里的 `return project` 返回给 `execute`，外层的 `return` 再把结果返回给调用方。

当前创建流程使用同一个 Spring 数据源：`service.create(request)` 内部保存项目的操作，以及协调器写入幂等记录的操作，会参与这个事务。这些读写由 MyBatis / MyBatis-Plus Mapper 执行，Mapper 与会话绑定到同一个 `DataSource` 和 `TransactionTemplate` 开启的事务，因此不会出现“部分操作不在事务内”的情况。

## 3. 幂等解决什么问题

假设前端请求创建项目，后端成功了，但响应在网络中丢失。前端不知道结果，于是重试。如果后端把重试当成新操作，就可能产生重复项目，或者因为目录已存在而报冲突。

前端可以为同一次创建生成一个 `Idempotency-Key`，重试时继续使用它：

| 情况 | 当前处理 |
|---|---|
| 没有提供键 | 正常创建，但不使用幂等记录保护重试 |
| 键以前没有使用过 | 创建项目并保存幂等记录 |
| 有效期内键和请求内容都相同 | 查询并返回已有项目 |
| 有效期内键相同、请求内容不同 | 返回 `409 idempotency_conflict` |
| 记录已过期 | 删除旧记录后，继续按新请求处理 |

当前有效期为 24 小时。请求内容通过 `fingerprint(request)` 计算 SHA-256 摘要，与保存的摘要进行比较。重试返回的是项目**当前数据**；项目被修改后，它不一定与第一次响应完全相同。

## 4. 锁和幂等有什么区别

| 机制 | 解决的问题 | 当前代码 |
|---|---|---|
| 事务 | 项目记录和幂等记录一起提交或回滚 | `transactions.execute(...)` |
| 锁 | 协调同时发生的操作 | `synchronized` 和 SQLite 写事务锁 |
| 幂等记录 | 识别之后到达的重复请求 | `project_idempotency` 表 |

例如，锁已经释放后，前端仍可能在几分钟后重试，所以锁不能代替幂等记录。同时，两个请求可能同时查询幂等记录，也需要考虑并发协调。

## 5. 锁不一定是锁住一个 Java 对象

不同系统可以用锁协调不同范围：

| 锁 | 由谁管理 | 协调范围 |
|---|---|---|
| Java `synchronized` | JVM | 同一 JVM 内使用同一个锁对象的线程 |
| SQLite 写锁 | SQLite | 访问同一个数据库的连接，包括不同进程中的连接 |
| Redis 锁 | 应用通过 Redis 操作 | 能访问同一个 Redis 并遵守相同约定的客户端 |

理解一把锁时可以问：**谁管理它、哪些执行者遵守它、它保护什么范围？**

当前方法上的：

```java
public synchronized Project create(...) {
    // ...
}
```

会让同一个协调器实例上的调用串行执行；不同幂等键的创建也会排队。不同 JVM 的对象锁互不共享。

## 6. 为什么空更新会请求 SQLite 写锁

当前事务中，幂等仓储的 `acquireWriteLock()` 负责发出这条空更新。迁移到 MyBatis 后，这条 SQL 由 Mapper 语句发出（Mapper 只承载 SQL，不负责事务边界）：

```sql
UPDATE projects SET id = id WHERE 0
```

访问方式的变化不影响锁语义：Mapper 与 `ProjectCreationCoordinator` 使用同一个 Spring 数据源，并在 `TransactionTemplate` 已经开启的事务中执行，所以 SQLite 收到的仍是一次写事务请求。Mapper 方法本身不能声明事务边界，调用方必须位于事务内；这一点与原先使用 `JdbcTemplate` 时相同。

拆开看：

```sql
UPDATE projects
SET id = id
WHERE 0
```

- `UPDATE` 是写类型 SQL。
- `id = id` 是一个不会改变字段值的赋值表达式。
- `WHERE 0` 不匹配任何行，因此不会实际更新项目记录。

**SQL 自己不是锁**。当前代码利用 SQLite 执行写语句时请求写事务的行为，在查询幂等记录之前，尝试提前获得数据库写入权限。SQLite 自己管理锁；它不是锁定 `id` 字段，也不是只锁某个项目或幂等键。

同一个 SQLite 数据库同一时刻只允许一个写事务。另一个写入者可能等待，也可能因等待超时等原因收到数据库忙错误。写事务的锁与事务相关，通常在提交或回滚时释放；读取是否受影响还取决于 SQLite 日志模式和事务阶段。

这条空更新是**SQLite 特定、比较隐晦的实现技巧**，不是所有数据库或 Spring 项目通用的加锁方式。它在当前部署和连接配置下的并发效果，应通过针对性的并发测试验证；不能只凭注释就认为所有场景都已验证。

## 7. 事务中的 SQL 执行顺序

一次带幂等键、没有命中有效旧记录的请求，主要经过：

```text
进入数据库事务
  │
  ├─ UPDATE projects SET id = id WHERE 0
  │    提前请求 SQLite 写事务，不匹配项目行
  │
  ├─ SELECT ... FROM project_idempotency WHERE key = ?
  │    检查幂等键是否已有记录
  │
  ├─ INSERT INTO projects ...
  │    保存项目；由 ProjectService 调用 Repository 完成
  │
  └─ INSERT INTO project_idempotency ...
       保存幂等键、请求摘要、项目 ID 和创建时间
  │
提交事务
```

如果命中未过期且内容一致的记录，代码会查询并返回已有项目，不再执行后面的新建操作。旧幂等记录过期时，会在事务中删除旧记录，然后继续尝试创建；删除的是幂等记录，不是项目或项目目录。

## 8. 数据库回滚不会撤销目录创建

创建项目时还会在文件系统中创建目录。数据库事务不知道如何撤销这个文件夹：

```text
目录创建成功
    ↓
项目记录写入成功
    ↓
幂等记录写入失败
    ↓
数据库回滚；目录可能仍存在
```

因此，协调器在事务失败后会尝试删除本次创建的**空目录**。如果清理失败，会将清理异常附加到原始异常上，避免覆盖原始错误。

这是失败后的补偿操作，不是文件系统与数据库之间的原子事务。进程突然终止、目录变为非空或删除失败时，目录仍可能留下来，需要后续恢复机制或人工排查。

## 9. 发送消息时的同类用法

发送会话消息也用到同一把 SQLite 写锁，原因比项目创建更强：消息序号是「读当前最大值 + 1」的读-改-写，如果两个请求同时读到同一个最大值，就会写出重复序号。`chat_messages` 上的 `UNIQUE(session_id, seq)` 会在后写者插入时失败，但正确做法是让它先排队，而不是制造一次约束冲突。

因此 `ChatMessageService.send` 在事务中的第一条语句就是空更新 `UPDATE chat_sessions SET id = id WHERE 0`，之后才读幂等记录、读最大序号、插入消息、刷新会话时间。

**顺序很关键**：如果事务的第一条 SQL 是 `SELECT`，SQLite 会先开启读事务，之后升级为写事务时在并发下更容易直接失败，而不是按 busy timeout 等待。所以这条空更新必须排在所有读取之前，参数校验则放在事务外，避免无效请求也去抢锁。

具体代码与设计见 [会话消息持久化](会话消息持久化.md)。
