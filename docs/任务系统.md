# 任务系统（第一阶段）

制作任务：一次「提交要求 → 执行 → 产出视频」的完整记录。

## 为什么任务要落库

只在内存里放任务，服务重启后用户就看不到历史与失败原因了。所以任务状态与事件
全部写 SQLite，内存只保留「哪个任务在跑、怎么取消它」。

## 数据模型

```
tasks                                  task_events
├── id (PK)                            ├── id (PK)
├── project_id → projects(id)          ├── task_id → tasks(id)
├── kind          render / …           ├── seq        任务内递增，断线补发用
├── status        见下                 ├── kind       accepted/progress/build/complete/error/cancelled
├── prompt        用户要求（人可读）    ├── status     事件后的任务状态
├── request_json  完整请求体            ├── message    给人看的一句话
├── progress      0~100                └── data_json  机器可读附加信息
├── message       当前在做什么
├── artifact_path 产物相对路径
├── error_code    失败错误码
└── created/updated/finished_at
```

`request_json` 存整份请求而不逐字段建列：请求会持续演进，逐字段建列意味着每加
一个字段就要改表，而这里从不需要按子字段查询。

## 状态机

```
queued ──→ running ──→ building ──→ completed
   │           │            │
   └───────────┴────────────┴──→ failed
   └───────────┴────────────┴──→ cancelled
```

三条不变式：

1. **终态之后不再迁移**。取消一个已完成的任务会返回 409，把它改成「已取消」
   会让用户以为白做了。
2. **取消不可被覆盖**。SQL 层带 `status <> 'cancelled'` 条件：后台线程可能在
   取消之后才跑到状态更新，没有这个条件会把「已取消」写成「已完成」。
3. **状态变化必留事件**。事件是状态迁移的唯一可观察出口，两者在同一事务里写。

## 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/projects/{id}/tasks` | 创建任务，202 + 任务体 |
| GET | `/api/projects/{id}/tasks` | 项目任务列表，最新在前 |
| GET | `/api/tasks/{id}` | 任务详情 |
| POST | `/api/tasks/{id}/cancel` | 取消；已结束返回 409 |
| GET | `/api/tasks/{id}/events` | **SSE 事件流** |
| GET | `/api/tasks/{id}/events/snapshot` | 事件快照（测试/排查用） |

创建请求体：

```json
{ "prompt": "做一条 3 秒两幕的短片",
  "film": { "width":960, "height":540, "fps":30,
            "scenes":[{"text":"标题","durationSeconds":1.5,"textAnimation":"fade"}] } }
```

`film` 就是 Remotion 工程接受的 props，后端不重复定义一遍 schema。

## 事件流

前端订阅 `/api/tasks/{id}/events`，收到 `accepted → progress → … → complete`。

- 带 `Last-Event-ID` 可断线补发：事件有 seq，重连时从断点续
- 任务进入终态且事件发完后流自动关闭，不会挂一条永不结束的连接
- 轮询间隔 200ms：进度变化不频繁，够用且开销小

选择轮询任务表而不是内存订阅者，是因为服务重启后内存订阅者会丢失，
而数据库里的事件还在 —— 前端重连就能补齐。

## 执行

渲染在独立线程池里跑（固定 2 线程，避免同时起多个 Chromium 打爆内存）。
HTTP 请求只负责创建任务并立即返回。

取消是**协作式**的：置位标记 + 打断线程，执行器在每个阶段检查。
不能硬杀 —— 渲染在子进程里，得由执行器自己收尾（包括删掉已产出的文件）。

## 实测

| 场景 | 结果 |
|---|---|
| 正常渲染 | `queued → building 30% → completed 100%`，8 秒出片 |
| 事件序列 | 6 条，accepted → progress×4 → complete |
| 非法请求 | 400 `validation_error` |
| 渲染失败 | `failed` + `render_failed`，保留 Remotion 原始错误 |
| 取消 | `cancelled`，8 秒后未被覆盖，无产物残留 |

## 当前限制

- **只支持 render 一种任务类型**。先让一条链路真正跑完，再横向扩展。
- **没有任务队列**：并发上限由线程池 2 决定，超出会排队在线程池里（不是任务表的 queued 状态）。
- **无版本**：每次渲染产出新文件，旧文件保留但没有版本关系。
- **前端仍走 Mock**：工作台还没接这套接口。
